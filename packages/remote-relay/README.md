# Self-hosted remote relay (V2)

This executable pairs the Desktop and Web remote-control clients over the V2 protocol
(`/api/v1/remote/*` HTTP and `/api/v1/remote/ws2` WebSocket). It issues its own relay
JWTs and needs no account service. Clients prove who they are in one of two identity
modes, chosen by `ZCODE_REMOTE_RELAY_IDENTITY_MODE` (below). It does not serve the
Web frontend or run an Agent: Desktop must stay running to execute commands.

Protocol and client behavior: `docs/web-remote-control/relay-v2-pairing.md`.
Design, owner decisions and the test plan: `specs/relay-v2-migration.md` (sections 10 to 14).

## Identity modes

`ZCODE_REMOTE_RELAY_IDENTITY_MODE` selects how `POST /api/v1/remote/session` authenticates a client.
The relay JWT, routes, `ws2` protocol and pairing flow are identical in both modes.

| Mode         | Clients prove identity with                                         | Needs                                              |
| ------------ | ------------------------------------------------------------------- | -------------------------------------------------- |
| `zai-jwt`    | the z.ai account login JWT                                          | `IDENTITY_ISSUER`, `IDENTITY_JWKS` (public keys)   |
| `device-key` | an Ed25519 key generated by each install, plus an enrollment secret | `ZCODE_REMOTE_RELAY_ENROLLMENT_SECRET` (32+ chars) |

Unset mode: `zai-jwt` when `IDENTITY_ISSUER` or `IDENTITY_JWKS` is set, otherwise startup fails and names
`ZCODE_REMOTE_RELAY_IDENTITY_MODE`. The `IDENTITY_*` variables are ignored in `device-key` mode (one startup
warning names them, never their values).

`device-key` mode in short: an install enrolls its public key once, sending the enrollment secret together
with a signed challenge (proof of possession). Afterwards it signs a fresh timestamp and nonce for every
session (replays and clocks off by more than 60 s are rejected). The relay user id is
`dk:` + sha256 of the public key. Whoever holds the enrollment secret can enroll devices, so treat it like a
password and rotate it by changing the variable (already enrolled keys keep working). To let a phone join
without any account, the Desktop shows a QR that carries a single-use pairing code (`pk`, 128 bits, valid
5 minutes, held in relay memory as a hash only). The phone exchanges it at `/session` and gets a relay JWT
for the Desktop's `dk:` identity (marked `amr: ["pairing"]`, so it cannot mint new codes), valid `ZCODE_REMOTE_RELAY_JWT_TTL_SECONDS`; after that it scans a new QR.
The QR is a credential while it is on screen. A relay restart forgets unused pairing codes and the nonce cache.

Switching modes on a running relay invalidates every relay JWT issued in the other mode.

Client side (Desktop): set `ZCODE_WEB_REMOTE_CONTROL_RELAY_IDENTITY_MODE=device-key` and
`ZCODE_WEB_REMOTE_CONTROL_RELAY_ENROLLMENT_SECRET` (or store the secret in the credential entry
`fork_web-remote-control:enrollment-secret`). The device key lives in the credential store as
`fork_web-remote-control:device-key`.

## Configuration

Startup fails closed: a missing or malformed required value stops the process, and the
error names the variable, never its value.

| Variable                                 | Required   | Meaning                                                                                                                                                                      |
| ---------------------------------------- | ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ZCODE_RELAY_DB_PATH`                    | yes        | SQLite file for device records. Keep it on a persistent volume, readable only by the relay user.                                                                             |
| `ZCODE_REMOTE_RELAY_JWT_SIGNING_KEYS`    | yes        | JSON array of private Ed25519 JWKs (`kty: OKP`, `crv: Ed25519`, `kid`, `d`, `x`). The first signs.                                                                           |
| `ZCODE_REMOTE_RELAY_IDENTITY_MODE`       | see text   | `zai-jwt` or `device-key`. Defaults to `zai-jwt` when ISSUER or JWKS is set; otherwise required.                                                                             |
| `ZCODE_REMOTE_RELAY_ENROLLMENT_SECRET`   | device-key | At least 32 characters. Admits new device keys. Never put it in a client build or a PR.                                                                                      |
| `ZCODE_REMOTE_RELAY_ENROLLMENT_MODE`     | device-key | `secret` (default) or `open`. `open` lets installs enroll by proof of work with no shared secret; the secret becomes optional and keeps granting the owner tier (4x quotas). |
| `ZCODE_RELAY_ENROLLMENT_DIFFICULTY`      | open       | Leading zero bits of the PoW, 8 to 32 (default 22).                                                                                                                          |
| `ZCODE_RELAY_MAX_ENROLLED_KEYS`          | open       | Open-tier key cap, default 10000. Reaching it stops new enrollment; existing keys keep working.                                                                              |
| `ZCODE_RELAY_ENROLLMENTS_PER_HOUR`       | open       | Breaker: open enrollments per rolling hour, default 300.                                                                                                                     |
| `ZCODE_RELAY_MAX_SOCKETS_PER_IDENTITY`   | device-key | Live WebSockets per identity, default 8 (owner 4x).                                                                                                                          |
| `ZCODE_RELAY_BYTES_PER_IDENTITY_PER_DAY` | device-key | Inbound bytes per identity per UTC day, default 536870912 (owner 4x).                                                                                                        |
| `ZCODE_RELAY_KEY_IDLE_EXPIRY_DAYS`       | open       | Open keys idle this long are deleted, default 30.                                                                                                                            |
| `ZCODE_REMOTE_RELAY_IDENTITY_ISSUER`     | zai-jwt    | Exact `iss` value the account login JWT must carry.                                                                                                                          |
| `ZCODE_REMOTE_RELAY_IDENTITY_JWKS`       | zai-jwt    | JWK set (`{"keys": [...]}` or a JSON array) of public keys for EdDSA, ES256 or RS256 login tokens.                                                                           |
| `ZCODE_REMOTE_RELAY_IDENTITY_AUDIENCE`   | no         | zai-jwt only: `aud` the login JWT must carry, when set.                                                                                                                      |
| `ZCODE_REMOTE_RELAY_IDENTITY_USER_CLAIM` | no         | zai-jwt only: claim holding the user id. Default `sub`.                                                                                                                      |
| `ZCODE_REMOTE_RELAY_JWT_TTL_SECONDS`     | no         | Relay JWT lifetime. Default `3600`, maximum `86400`.                                                                                                                         |
| `ZCODE_REMOTE_RELAY_AUTH_TIMEOUT_MS`     | no         | Deadline for `auth_init` after connecting. Default `15000`.                                                                                                                  |
| `ZCODE_RELAY_HOST`, `ZCODE_RELAY_PORT`   | no         | Bind address (default `127.0.0.1`) and port (default `3031`).                                                                                                                |
| `ZCODE_RELAY_ALLOWED_ORIGINS`            | no         | Exact Web origins, comma-separated. Required when binding to a non-loopback address.                                                                                         |
| `ZCODE_RELAY_TRUSTED_PROXIES`            | no         | Exact proxy IP addresses whose `X-Forwarded-For` is honored. Empty by default.                                                                                               |

Limits (defaults): `ZCODE_RELAY_MAX_CONNECTIONS` 2000, `ZCODE_RELAY_REGISTRATIONS_PER_MINUTE` 20
per source address (applies to `/session` and `/device`), `ZCODE_RELAY_MAX_REGISTRATIONS` 100000,
`ZCODE_RELAY_MAX_BUFFERED_BYTES` 2097152, `ZCODE_RELAY_MAX_TOTAL_BUFFERED_BYTES` 67108864.

## Keys and rotation

Generate a relay signing key as an Ed25519 private JWK, give it a `kid`, and put it first
in `ZCODE_REMOTE_RELAY_JWT_SIGNING_KEYS`. To rotate, prepend the new key and restart. Keep
the old key until at least one TTL has passed, then remove it. Keys live in memory only.
This version is single-replica: every replica needs the same key array.

The login identity keys are public only. The relay never fetches them from the network.

## Routes

| Route                               | Auth                                                | Purpose                                               |
| ----------------------------------- | --------------------------------------------------- | ----------------------------------------------------- |
| POST `/api/v1/remote/session`       | login JWT, device-key proof or pairing code in body | Exchange for a relay JWT                              |
| POST `/api/v1/remote/pairing`       | relay JWT                                           | `device-key` mode only: single-use phone pairing code |
| POST / GET `/api/v1/remote/device`  | relay JWT                                           | Register a device (new SID each call) / list own      |
| POST `/api/v1/remote/device/delete` | relay JWT                                           | Delete an offline own device                          |
| POST `/api/v1/remote/token`         | relay JWT                                           | One-time 60 second WebSocket token                    |
| WS `/api/v1/remote/ws2?token=`      | one-time token                                      | Pairing and forwarding                                |
| GET `/healthz`, `/readyz`           | none                                                | Liveness and readiness                                |

## Railway

1. Create a service from the repository. Set `RAILWAY_DOCKERFILE_PATH=packages/remote-relay/Dockerfile`
   and leave build and start overrides empty.
2. Attach a persistent volume at `/data`. Use one replica.
   In `device-key` mode only these are needed: `ZCODE_RELAY_DB_PATH`,
   `ZCODE_REMOTE_RELAY_JWT_SIGNING_KEYS`, `ZCODE_REMOTE_RELAY_IDENTITY_MODE=device-key`,
   `ZCODE_REMOTE_RELAY_ENROLLMENT_SECRET`, `ZCODE_RELAY_ALLOWED_ORIGINS`, `ZCODE_RELAY_HOST`,
   `ZCODE_RELAY_PORT` (no `IDENTITY_ISSUER` or `IDENTITY_JWKS`). In `zai-jwt` mode the account
   variables replace the secret and mode.
3. Set the variables above, using `ZCODE_RELAY_DB_PATH=/data/relay.sqlite`,
   `ZCODE_RELAY_HOST=0.0.0.0`, `ZCODE_RELAY_PORT=3031`, and your Web origin in
   `ZCODE_RELAY_ALLOWED_ORIGINS`. Set `RAILWAY_RUN_UID=0` because the volume is root-owned.
4. Generate a public domain on port `3031`, with health check path `/readyz`. Clients use
   `ZCODE_WEB_REMOTE_CONTROL_RELAY_WS_URL=wss://<relay-domain>` (origin only; the path
   `/api/v1/remote/ws2` is derived).

Origins are exact HTTP(S) origins without paths or trailing slashes. Never put signing keys,
identity keys or the database file in a client build, a `VITE_` variable, a source file or a PR.

## Verification

From the repository root:

```bash
pnpm test:relay
pnpm build:relay
pnpm --filter @zcode/remote-relay test:bundle
docker build -f packages/remote-relay/Dockerfile -t zcode-remote-relay:local .
```

`test:bundle` runs the built `dist/entry.js` end to end: readiness, login exchange, device
registration, pairing, forwarding and restart persistence, then restarts it in `device-key` mode
for enrollment and a phone pairing code.
