## 0. Scope

Closes review findings that already had product and architecture decisions:

1. Account Built-in Provider Config stays a formal Overlay and expresses current-account dynamic facts through
   `enabled`, the account-level Start Plan `builtinModelIds` and structured Account Access.
2. Registry never publishes the intermediate "new ZCode Built-in + old Account Overlay" combination.
3. ZCode Built-in Environment Active/LKG is physically isolated per ZCode Endpoint.
4. CLI `--help` / `--version` no longer start the Provider Runtime; Bootstrap declares `zod`.
5. The orphan ZIP implementation and its dedicated dependencies are deleted.

Not included: semantic port or conflict handling of the latest `origin/staging`, the final Release Checklist, and
any extra Built-in Release business-integrity publish gate.

## 1. Decisions

### 1.1 Account remains a formal Provider Config Overlay

The current account really changes the effective config of account-type Built-in Providers.

```text
ZCode Built-in Provider Config
              |
              v
Account Built-in Provider Config
├─ enabled
├─ Start Plan builtinModelIds
└─ accessId / family / planKind / Team scope
              |
              v
Personal Provider Config
              |
              v
Effective Provider Config
```

```ts
const effectiveBuiltinProviders = zcodeBuiltinProviders.overlay(accountBuiltinProviders);

const effectiveProviders = effectiveBuiltinProviders.overlay(personalProviders);
```

Account reads and constrains only Built-in Providers with `access.type = "zhipu-account"`; it never reads or
constrains Personal-only Providers. Personal stays the last user override layer.

### 1.2 Account availability is `enabled`

Availability is not expressed indirectly by a missing Account Overlay leaving `accessId` incomplete. The Account
Source projects, per relevant Built-in Account Provider:

```text
available   -> enabled: true
unavailable -> enabled: false
unknown     -> previous successful Account Overlay kept; with none: fail-closed, enabled: false
```

`enabled` stays the single Provider execution gate. Settings may keep disabled Providers for display and
diagnostics; Selection, the executable Registry View and ModelFactory all reject `enabled = false`. No parallel
`available`, `eligible` or new execution-state field.

### 1.3 Start Plan model membership is an account-level fact

Different Start Plan accounts can have different model sets; the `billing/balance` model set enters the Account
Overlay:

```text
Start Plan balance
└─ capabilities: model:<id>   (show_name legacy fallback kept for now)
              |
              v
Account Provider Config.builtinModelIds
              |
              v
ZCode Built-in Model Config Rules resolve
```

- Start Plan available with a non-empty model set: the account set overrides Built-in `builtinModelIds` as a whole
  list.
- Individual / Team APIs return no model set: the Overlay writes no `builtinModelIds` and inherits the Built-in
  default membership.
- Start Plan active but no model resolved this round: keep the last successful Overlay when an LKG exists; with no
  LKG, fail-closed. Never fall back to the broad Built-in default set.
- `show_name` is a temporary server-compat input; it is removed once the server guarantees stable `model:<id>`.
- Account changes membership only. It provides no Properties, Reasoning, context or max output; static model facts
  are resolved from ZCode Built-in + Personal Model Config Rules.
- Personal `modelIds` are added after the account-constrained Built-in Inventory; the server still authorizes the
  real request.

### 1.4 Account Access enters the Overlay but carries no real credential

`accessId` is a stable, non-sensitive access identity generated by the client from account identity, Provider, Plan
and Team scope:

- the same account keeps the same identity across Token/JWT/API key/Header refresh;
- switching account, plan or Team scope changes it;
- an Active Model freezes the Account Access at creation; later credential refresh cannot silently switch account;
- the Individual Coding Plan Credential Store is isolated per access identity;
- Team Plan product/organization/project take part in request-time resolution as structured Access fields.

```ts
access: {
  type: "zhipu-account";
  accessId: string;
  family: "zai" | "bigmodel";
  planKind: "start-plan" | "individual-coding-plan" | "team-coding-plan";
  productId?: string;
  organizationId?: string;
  projectId?: string;
}
```

Token, JWT, API key, dynamic Header and credential refresh stay in Request Auth/Credential Service and never enter
Config, Registry or Active Model static config. The server keeps final authorization.

### 1.5 Account Overlay declares its Built-in source revision

Registry subscribes to both the Config Source and the Account Source, so a Built-in change could briefly combine new
Built-in with an old Account Overlay:

```text
B0 + A0
   | Built-in -> B1
   v
B1 + A0  <- forbidden
   | Account refresh
   v
B1 + A1  <- the only allowed new Snapshot
```

No cross-server common version protocol; the Account API does not return a Built-in revision. The source proof is
kept only in client-derived Sources:

```ts
interface ProviderConfigSnapshot {
  readonly revision: string;
  readonly zcodeBuiltinRevision: string;
  readonly personalRevision: string;
  // existing config fields
}

interface AccountProviderConfigSnapshot {
  readonly revision: string;
  readonly basedOnZCodeBuiltinRevision: string;
  readonly providers: ProviderConfigMap;
}
```

Registry publishes only when `account.basedOnZCodeBuiltinRevision === config.zcodeBuiltinRevision`. On mismatch it
keeps the current complete Registry Snapshot and waits for the Account Source to project the new Built-in. Even if
the Provider Map equals the previous round, a changed `basedOnZCodeBuiltinRevision` must publish a new Account Source
revision/change event so Registry can apply the new Built-in. Personal updates do not change `zcodeBuiltinRevision`
and are never blocked by Account network refresh.

### 1.6 Active/LKG isolated per ZCode Endpoint

Endpoint here is the ZCode platform control-plane `zcodeEndpointOrigin` (prod, test, dev/mock), not a model API
Endpoint in Provider Config. Previously only `refresh-control.json.endpointKey` isolated refresh TTL while
`active.json` was shared across Endpoints, so unrelated revisions were compared. Remote Active and the refresh
control file are physically isolated by a stable, collision-safe path segment of the normalized Endpoint:

```text
<environmentConfigRoot>/provider/zcode-builtin/
└─ <platform>/
   └─ <appVersion>/
      └─ <endpointKey>/
         ├─ active.json
         └─ refresh-control.json
```

- `endpointKey` is generated deterministically from the normalized Origin; unsafe URL characters never go into the
  path.
- revision is compared only within the same Endpoint's Bundled/Remote publish semantics.
- After switching to an Endpoint with no Active, use Bundled to become ready, then refresh the new Endpoint in the
  background.
- Endpoint A's LKG is never a candidate for Endpoint B; switching back may reuse that Endpoint's own LKG.
- The `endpointKey` in the control payload stays as a defensive consistency check.
- No dual-read of the old unpartitioned Active path (Todo 18 had no formal release compatibility history).

### 1.7 CLI and dependency

```text
--help / -h / --version / -v
└─ no Provider Config read/persist
   no /client/configs refresh
   no Built-in asset ready dependency
```

Only the entry check and tests change; `doctor` and other commands that never needed the Provider Runtime are
unchanged. Bootstrap production code imports `zod` directly and declares it in its own `dependencies`.

### 1.8 Mechanical cleanup

Deleted zero-reference `packages/zcode-server-cli/src/packaging/zipArchive.ts` and its sole dependencies `yazl` and
`@types/yazl`. `yauzl` (ZIP extraction) and the earlier Linux pre-push fixes for Server ZIP, macOS notarize and
cross-platform `stat` stay. Deletion was proved by `dep:refs`, `knip` and the targeted packaging tests.
`packages/ui/src/hooks/useProviderModelOrder.ts` (new, zero references) was already deleted in commit `01ac05e2be`.

## 3. Implementation outline

Design docs and the Feature Graph (`capability.provider-registry` invariants: Account `enabled`, Start model
membership, Account Access, `basedOnZCodeBuiltinRevision` atomic publish; Endpoint-scoped Active/LKG persistence)
were updated first, tests first, then:

- layered revisions on the Config and Account snapshots (Mutable/Empty/Test Sources share the contract; Account
  revision contains both the source Built-in revision and the Overlay content identity, no string parsing or
  wildcard revision);
- Account Overlay projects `enabled` explicitly (unavailable publishes a sparse `{ enabled: false }`, available
  publishes full structured Access); Start projects exact `builtinModelIds`; Individual/Team do not copy Built-in
  members; `show_name` compat stays inside the Account Source private parse boundary;
- Registry revision barrier: on mismatch no Resolver call, no Registry replacement, no Facade notification; the
  previous complete Snapshot stays; after the matching Account update exactly one final Registry is published;
  generation changes still discard stale rebuilds; Personal-only changes publish on the fast path; refresh failure
  keeps the previous Account Overlay and Registry and emits a diagnosable error;
- Endpoint-scoped Active/LKG with shared file lock, lease, TTL and revision comparison across processes for the same
  Endpoint; Endpoint switch triggers that Endpoint's Built-in refresh and converges Account -> Registry.

## 4. Acceptance scenarios

### 4.1 Account Overlay

- available Account Provider gets `enabled: true` and full Access; unavailable gets `enabled: false` (not via an
  integrity failure);
- unknown: keep LKG, or fail-closed with none;
- two Start accounts with different models get different exact `builtinModelIds`;
- Start active with empty/unparsable model list does not inherit the broad Built-in;
- Individual/Team without models inherit the current Built-in;
- Team product/org/project and `accessId` are generated stably and change when any identity field changes;
- Account Overlay cannot constrain Personal-only Providers; Personal still overrides after Account.

### 4.2 Registry atomic publish

- `B0/A0 -> B1` with delayed Account refresh does not publish `B1/A0`; `A1 basedOn B1` publishes only `B1/A1`;
- same Overlay content with source B0 -> B1 still triggers the final rebuild;
- Personal P0 -> P1 with Built-in still B1 publishes `B1/A1/P1` immediately;
- Account refresh failure keeps the old complete Registry; no refresh hot-changes an already-created Active Model.

### 4.3 Endpoint Active/LKG

- Endpoint A revision 20 and B revision 10 live in separate paths; B is not judged stale by A;
- same revision with different content on A/B causes no publish-protocol error;
- switching back to A reuses A's LKG; B with no LKG and a failing remote uses Bundled, never A's LKG;
- multiple processes on one Endpoint have a single lease owner issuing the network request;
- Endpoint Setting/Environment changes trigger the right Source refresh.

### 4.4 CLI, dependency, cleanup

- `--help/-h/--version/-v` never call Provider Runtime prepare; prompt/TUI/server entries still prepare;
- Bootstrap typecheck/install/packaging resolves direct `zod`;
- after deleting `zipArchive.ts`, `dep:refs` is zero and Server ZIP tests pass; `yauzl` extraction tests and the
  Linux pre-push fixes do not regress.

## 5. Non-goals and invariants

- No staging merge; no real-account/real-artifact/cross-platform Release Checklist verification; no Built-in
  business-integrity publish gate.
- Account Overlay, Start account model sets and `accessId` are not removed.
- Token, JWT, API key, Header never enter Config.
- No change to Model Config Rule order, Model Properties, Reasoning or Adapter facts.
- No change to Off-Peak, Subagent, Compact, Memory Active Model ownership, nor to Desktop continuous, Mobile
  replayable, queue and recovery semantics.
- No second LKG, dual-read or cross-Endpoint revision comparison for the Endpoint cache.

## 6. Completion criteria

- Account Overlay expresses availability with `enabled`; exact Start membership enters `builtinModelIds`; an empty
  result fails closed.
- Account Access stays non-sensitive, complete and freezable; real credentials resolve at request time.
- Registry never publishes an Account Overlay whose source Built-in revision mismatches; Personal-only updates are
  not blocked by Account refresh.
- Active/LKG and refresh control are Endpoint-isolated.
- CLI help/version do not trigger the Provider Runtime; Bootstrap declares `zod`; orphan ZIP code deleted.
- Design, Todo status and Feature Graph match the implementation.

## 7. Impact brief

| State/fact                    | Authoritative owner        | Persistence/cache             | Publish sink     |
| ----------------------------- | -------------------------- | ----------------------------- | ---------------- |
| Built-in revision/content     | ZCode Built-in Source      | Endpoint-scoped `active.json` | Config Service   |
| Account enabled/models/access | AccountProviderService     | in-process LKG Snapshot       | Account Source   |
| Personal Config               | Personal Repository        | `config.json`                 | Config Service   |
| Effective Provider/Model      | ProviderRegistryService    | in-process immutable Snapshot | Registry/Facades |
| Active Model                  | ModelFactory-created Model | frozen for execution lifetime | Adapter request  |

Primary seeds: `AccountProviderService`, `ProviderRegistryService`, `resolveZCodeBuiltinCachePaths`,
`requiresProviderRuntime`. Change layer: option-source / validation / persistence / commit-effect.

Must-preserve invariants:

- Account constrains only Built-in account Providers; Personal overrides last.
- Account Start models are membership facts, not static model capabilities.
- The revision barrier expresses client-derived source only; it creates no server common version protocol.
- Endpoint is Environment config-source isolation, not a model API Endpoint.
- Dynamic credentials never enter Config; the server authorizes.
- An already-created Active Model never changes on Config/Account refresh.

No unresolved product question changes this scope; `show_name` retirement depends on a later server guarantee and
is a stated compat exit condition.

## 8. Implementation record

### 8.1 Landed

- Config snapshot split into combined revision, ZCode Built-in revision and Personal revision;
  `AccountProviderConfigSnapshot` carries `basedOnZCodeBuiltinRevision`.
- Account Resolver projects `enabled` uniformly (unknown fails closed the first time); Start adopts the exact
  account set with LKG/fail-closed on empty; Individual/Team inherit Built-in members.
- Registry has the Built-in/Account revision barrier; Personal-only changes do not wait for Account.
- Environment Source isolates `active.json` and `refresh-control.json` by a SHA-256 path segment of the normalized
  ZCode control-plane Origin; Endpoint switch uses each Endpoint's own Bundled/LKG and a late response from the old
  Endpoint is not persisted.
- Desktop Services resolve the current Endpoint dynamically when reading Settings; Bootstrap, Protocol and Agent
  stdio payloads carry the Account source revision; before the first Account facts arrive, a fail-closed Snapshot
  matching the current Built-in is used.
- CLI `--help/-h/--version/-v` skip Provider Runtime prepare; Bootstrap declares `zod`; `zipArchive.ts`, `yazl` and
  `@types/yazl` removed, `yauzl` kept.
