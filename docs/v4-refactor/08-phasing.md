# Phased Landing and Cleanup

> **Status: historical implementation and cleanup trail.** Branches, commits, phase gates and the deletion ledger of M0-M6 are kept only for traceability and are no longer a progress table. Current architecture and unfinished items follow [README.md](./README.md), the current code and the "current spec" documents. Full pre-compaction trail: `git show b8876e8b:docs/v4-refactor/08-phasing.md`.

The 2026-07-05 execution ruling was to drop the dual-write transition and hard-cut. This document records how that ruling landed through M0-M5; old paths, line counts, branch names and "next steps" reflect only the execution context at the time.

## Milestones M0-M5 (hard-cut version, finalized 2026-07-05)

Core principle: **everything that can be purely additive is done first on main, compressing the destructive hard-cut window to the shortest.** Deletion happens only after the reducer golden tests are all green: the "new truth" is proven correct first, so the UI rewrite always has an authoritative reference.

```text
main --M0 decisions--M1 new protocol pkg--M2 CLI projection+golden tests-------------*--M5 multi-end convergence+cleanup-->
      (docs/rulings)  (pure addition)     (pure addition, old UI unaffected)        ^merge
                                      │                                             │
                          feature branch +--M3 delete wave 1 + vertical slice--M4 feature parity--+
                                         <-- the only "dark period", kept as short as possible -->
```

Exits are all verifiable gates, not dates. M0 and M1 can run in parallel; during M3-M4 mobile remote/web stay on the old main chain.

Ordering rationale:

0. **M1/M2's boundary is "data model draft -> reducer hardening -> freeze -> transport shell"** (corrected 2026-07-05): the protocol has two halves, the data model (snapshot/row/delta, the reducer's output types) and the transport shell (frame/subscription/command envelopes). The data model must exist before the reducer but freezing must come after reducer verification; the transport shell only needs to be in place before M3's channel layer starts. This avoids a schema-first waterfall freezing types wrongly behind closed doors.
1. **M2 precedes any deletion** as the safety belt: all golden tests green means the new fact source is proven correct, so there is no hanging window of "old deleted, new unproven".
2. **The dark period is only M3-M4** (desktop chat unusable on the branch); during M0-M2 main can ship releases and fix bugs normally.
3. **Mobile/web move last**, matching the web remote protection constraint; the mobile App can start once M4 merges, since it is just another projection renderer.
4. **Split panes sit in M5**: not a risk item but the new store's second consumer, not crowding the vertical slice's verification effort.

The old Phase 0-4 capability-layer table (Phase 0 protocol and anchor, 1 CLI projection and inbox, 2 transport and channel layer, 3 new UI shell, 4 cleanup; net deletion over 40k lines) was replaced by M0-M5; the "grayscale" wording of Phase 3 is void (hard cut) and "double write" in Phase 1 is void.

## Legacy cleanup notes

- **Old protocol runtime**: source fully deleted, only historical dist artifacts remain; clean dist and rebuild.
- **task->session adapter layer**: `zcodeTaskServiceAdapter.ts` (5871 lines), `taskIndexRepo` old column-name compatibility, the UI's `legacyTaskService` injection. The layer existed because "the old UI spoke task"; once the new UI speaks session/projection the whole layer is scrapped, deleted last (deleting it earlier would stop the old UI running, against the phasing principle).
- **Old task data file compatibility** (`legacyTaskSessionFile.ts` etc.) is data compatibility, not protocol residue, and is kept until there is no old data stock.
