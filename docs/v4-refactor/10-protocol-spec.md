# ZCode Protocol v4: Field-level Spec

Full pre-compaction version: `git show b8876e8b:docs/v4-refactor/10-protocol-spec.md`.

A read-only query `v4/conversation/backgroundBashOutput` exists: sessionId/workId locates the current runtime's background Bash and returns only kind/workId/status/output/truncated/outputPath, where output is a fixed tail window of at most 8 KiB raw bytes; it carries no command, time, exit code or file size, and generates no topic event and does not resume a session. Field, error and lifecycle contract: [background Bash output details](../background-bash-output-details.md).

- Status: **current fact (2026-07-11 target/action/edit/retry loop closure)**. On top of the existing projection schema this version raises the wire to v3 and wires trusted-connection subscription, physical fragmentation / bounded resync, CLI-authoritative input and `commands/query`, composite row targets and running stable assistant fork. It refines [09-protocol-schema.md](./09-protocol-schema.md); subscription/recovery/backpressure semantics follow [04](./04-sync-and-recovery.md)/[05](./05-transport-and-backpressure.md).
- Absorbs all R/G/D conclusions and two rulings (queue not persisted, inbox in memory) of [design-review.md](./design-review.md).
- §9.2 adopted **option B**: the event log is a bounded in-process log, `logEpoch` changes with the CLI runtime generation; across restarts a new snapshot is produced by hydrating persisted transcript/input facts, never restoring an old epoch.
- A warning mark in the text is a design-time decision marker; §10 records the final rulings and it must not be read as a currently open decision.
- Types are in TypeScript notation as the discussion baseline and implemented as zod schemas; `?` = may be absent, with the absent semantics in comments.

Scope: the connection/subscription common layer + conversation topic + sessions-index topic + command/query layer. terminal/git/workspace and other domains are out of scope; do not infer from this that they migrated to the same topic schema.

## 1. Identifiers and clocks

| Identifier | Type | Generated by | Lifetime | Use |
| --- | --- | --- | --- | --- |
| `sessionId` | `string` | CLI (at createSession) | permanent | session identity |
| `workspaceId` | `string` | host | permanent | workspace identity key (R-16: **not a bare path**; includes SSH/WSL/container identity) |
| `clientId` | `string` | generated by the client on first install, localStorage | persists across connections | command attribution display, telemetry. **Takes no part in routing** |
| `connectionId` | `string` | host (assigned when an attachment is established) | single connection | envelope routing, subscription ownership (R-08: separate from clientId) |
| `clientMode` | `desktop-continuous \| web-remote-replayable` | host (injected by attachment type) | single connection | trusted desktop/mobile boundary; the client cannot override |
| `subscriptionId` | `string` | host (assigned when a subscribe is accepted) | single subscription | frame generation, prevents interleaving old streams (R-01) |
| `logicalFrameId` | `string` | publisher/wire encoder | single logical frame | physical fragment assembly and validation |
| `logicalFrameOrdinal` | `positive safe integer` | publisher (per subscription) | monotonic within one subscription, starting at 1 | evicts late logical replay; same ordinal with a different id = protocol conflict |
| `logEpoch` | `string` | CLI (generated at process start, e.g. ULID) | CLI process lifetime | `base` validity: epoch mismatch -> snapshot only |
| `seq` | `number` | CLI event log | monotonic in a session, valid within an epoch | frame range accounting, resume |
| `revision` | `number` | derived by the CLI reducer (§4.5) | monotonic in a session, **stable across restarts** | command CAS |
| `rowId` | `number` | derived by the CLI reducer | monotonic in a session, never reused, **a deterministic pure function of the event log** (R-04) | row identity, virtual scroll key, cursor paging |
| `turnId` | `string` | CLI | permanent (persisted on message) | row grouping label |
| `commandId` | `string` (uuid v7) | client | unchanged across retries | idempotency identity |
| `interactionId` / `queueItemId` / `workId` | `string` | CLI | object lifetime | `queueItemId` is assigned at admission and unchanged by edit/reserve/drain |

Clock rules (eliminating P1-11-style clock patches):

1. `type Timestamp = number` (Unix ms, **always the CLI clock**). Clients must not subtract the local clock from a protocol Timestamp.
2. Every frame envelope carries `sentAt` (§3.2); the client maintains `clockOffset ~ sentAt - localNow`, and live-ticking values such as "worked N seconds" = `localNow + clockOffset - startedAt`.
3. Authoritative duration (`turnHeader.activeMs`, §4.4) is sent by the CLI at completion; the client's ticking value is only a transitional display and the final value is the authoritative one.

`revision` vs `seq`: `revision` counts "structural events" (defined in §4.5), `seq` counts all events; both derive deterministically from the log, and `revision <= seq`.

## 2. Connection and handshake

```ts
// After a connection is established the host sends the first message
interface HelloMessage {
  kind: "hello";
  protocolVersion: 3; // V4 wire version; the snapshot schema is versioned independently
  connectionId: string;
  clientMode: "desktop-continuous" | "web-remote-replayable";
  deliveryProfile: "continuous" | "replayable";
  serverTime: Timestamp; // first clock calibration
  capabilities: HostCapabilities; // platform capability negotiation (orthogonal to delivery profile, 05)
  auth: { userId?: string }; // auth details belong to G-13; only a placeholder here
}

interface HostCapabilities {
  nativeDialogs: boolean; // desktop native dialogs
  localTerminal: boolean;
  binaryFrames: boolean; // ws binary (probing the relay link)
  compression: "none" | "permessage-deflate";
  workflowRunDeltas?: boolean; // can send the §4.5 keyed workflowRun.* ops; absent is equivalent to false, callers test `=== true`
}

// Client reply (connection-level registration, once)
interface ClientHello {
  kind: "clientHello";
  protocolVersion: 3;
  clientId: string;
  clientKind?: "desktop" | "web" | "mobileRemote" | "mobileApp"; // telemetry/display only, cannot override the trusted clientMode
  appVersion: string;
  capabilities?: { workflowRunDeltas?: boolean }; // strict object: only capabilities the host announced in hello may be declared
}
```

Rules:

1. `connectionId/clientMode/deliveryProfile` come from the host's trusted attachment context: desktop (including SSH/WSL/Docker) = `desktop-continuous/continuous`; mobile remote/WebSocket = `web-remote-replayable/replayable`. Neither the UI nor `clientHello` can choose them.
2. Capability negotiation is a per-connection fact: the host announces in `hello`, the client declares in `clientHello` only what the host announced, and the facade writes the conclusion into that connection's subscribe (§3.1) through the same `clientMode` injection path. It is orthogonal to the delivery profile: both `continuous` and `replayable` can be declaring or non-declaring.
3. Each attachment handshakes independently and has its own subscription registry; desktop/mobile subscriptions of the same session may coexist.
4. Connection health (connecting/reconnecting/degraded) is a **client-local UI state** and must never be mixed into the session semantics of any topic (R-13).
5. The disconnect reason class is carried by the rpc-layer close code: `authFailed` / `kicked` / `serverShutdown` / `unknown`. For the first two the client **stops auto-reconnect** and enters the matching terminal page (G-08); otherwise it reconnects with backoff (0,1,2,5,10... capped at 30s, single entry).

## 3. Subscription common layer (shared by all topics)

### 3.1 Subscription lifecycle

```text
client                    connection facade                    CLI/service domain
  │ subscribe(topic, base?) ────►│                                  │
  │                              │── inject connection/profile ────►│
  │◄─ SubscribeAck{subId, mode} ─│◄───── subscription decision ────│
  │   (after the ACK response is written)                           │
  │◄═ initial/online TopicWireFrame(subId) owned notifications ════│
  │                              │
  │ gap detected -> resync(subId, base={logEpoch, seq})     <- single-flight
  │                              │ same-sub recovery; profile/topic decided by the owned registry
  │                              │ downstream written only to the attachment port of owner(subscriptionId)
```

```ts
interface SubscribeParams {
  topic: TopicKey; // "conversation/<sessionId>" | "sessions-index/<workspaceId>" | ...
  base?: { logEpoch: string; seq: number }; // watermark invariant: only allowed when the client really holds a consistent state at that moment
  visibility?: "foreground" | "background"; // QoS hint, affects scheduling only, not semantics
  // connectionId/clientMode/deliveryProfile must not be passed by the UI; the facade injects them from the trusted connection context.
  workflowRunDeltas?: boolean; // same: the facade injects it from that connection's clientHello declaration; the UI-facing subscribe cannot choose it
}

interface SubscribeAck {
  subscriptionId: string;
  mode: "snapshot" | "resume"; // resume = base valid, continue the increments from base.seq
  logEpoch: string; // current log generation
}

interface UnsubscribeParams {
  subscriptionId: string;
}
interface UpdateSubscriptionParams {
  subscriptionId: string;
  visibility: "foreground" | "background";
}
interface ConversationResyncParams {
  subscriptionId: string;
  base: { logEpoch: string; seq: number } | null;
  forceSnapshot?: boolean; // forced true on a gap after resume / on fragment validation failure
}
interface ConversationResyncResult {
  ack: SubscribeAck; // same subscriptionId; the public response is still ACK-only
}
```

Server ruling (CLI): `base.logEpoch === current epoch` and `base.seq` within the retention window and `forceSnapshot` not requested -> `resume`; otherwise -> `snapshot`. resync regenerates the recovery frame from the client's base and must not guess client state from the publisher's `sentSeq`; it keeps the owned `subscriptionId/topic/profile` and invalidates the old in-flight reservation (an old delayed commit returns false).

Closing a connection must `unsubscribeAll(connectionId)` and release that connection's buffer, fragment assembly and flow-control listeners. After a CLI runtime restart/attachment rebuild the client re-subscribes active topics automatically once the new handshake completes; broadcasting to the workspace and having the receiver drop subIds not its own is forbidden.

The subscribe response may carry only a small `SubscribeAck`. The initial snapshot/resume must not be embedded as a logical `frame` nor placed into the same response as `frames[]`; physical wire frames are sent via owned-port notifications after the ACK is written.

`SubscribeAck.logEpoch` is admission/route metadata and creates no seq=0 base. All three topic kinds keep `hasAppliedBase`: a projection that really existed before the request survives when ACK=`resume` with the same epoch; ACK=`snapshot` invalidates the old base until a complete owned snapshot applies atomically. With no valid base no delta may apply; an initial assembly fault / ACK staging overflow must send `base:null, forceSnapshot:true` (or a fresh snapshot after a generation change); building a fake base from the ACK is forbidden; any complete owned snapshot (including an online overflow snapshot) can re-establish a base. The same holds for sessions-index/config: the cold seed may not be in the incremental log, so an empty resume cannot replace the initial snapshot.

Implementation gate 04B uses a request-scoped post-response outbox to guarantee byte order and watermark: the server dispatch carries `{ack, physicalMessages[], commit}` internally while the public result stays strictly `{ack}`. The connection first takes the outbox of that request id, writes the response line, puts all physical notification lines in order into the current connection-owned write queue, and only then commits the publisher reservation. An encode or synchronous enqueue failure does not advance the watermark; an async EPIPE/close after enqueue ends the whole connection epoch, and the old subscription/outbox is not reused across attachments. Inferring response/initial order from microtasks/timers or lower-layer network packetization is forbidden.

### 3.2 Logical frame and the wire v3 physical envelope

```ts
type TopicKey = string;

interface TopicFrame<S, D> {
  topic: TopicKey;
  subscriptionId: string; // R-01: generation identifier
  fromSeq: number; // range accounting (fromSeq, toSeq]; fromSeq of a snapshot frame is fixed 0
  toSeq: number; // position in the authoritative log this frame covers
  sentAt: Timestamp; // CLI clock, for clockOffset estimation
  payload:
    | { kind: "snapshot"; snapshot: S } // wholesale replacement
    | { kind: "deltas"; deltas: D[] };
}

type TopicWireFrame<S, D> =
  | {
      wireVersion: 3;
      kind: "complete";
      deliveryKind: "initial" | "online" | "recovery";
      logicalFrameId: string;
      logicalFrameOrdinal: number;
      topic: TopicKey;
      subscriptionId: string;
      frame: TopicFrame<S, D>;
    }
  | {
      wireVersion: 3;
      kind: "fragment";
      deliveryKind: "initial" | "online" | "recovery";
      logicalFrameId: string;
      logicalFrameOrdinal: number;
      topic: TopicKey;
      subscriptionId: string;
      fragmentIndex: number; // 0-based
      fragmentCount: number;
      logicalBytes: number; // UTF-8 byte count of the canonical logical JSON
      checksum: { algorithm: "crc32"; value: string }; // transport integrity, not security auth
      dataBase64: string;
    };
```

```ts
interface ReservedTopicFrame<F> {
  deliveryKind: "initial" | "online" | "recovery";
  logicalFrameId: string;
  logicalFrameOrdinal: number;
  frame: F;
  commit(): boolean; // false = stale reservation after unsubscribe/re-subscribe
}
```

Constraints (the full transport rules, fragment limits and reservation commit are in [05](./05-transport-and-backpressure.md); repeated here only as the field-level contract):

1. `TopicFrame` is a logical frame that must apply atomically; a fragment is not an independent seq frame and must not change `(fromSeq,toSeq]`.
2. `deliveryKind` is the publisher reservation's authoritative fact: subscribe initial = `initial`, ordinary online flush (including the publisher's own overflow snapshot) = `online`, explicit same-sub resync = `recovery`. The encoder copies the reservation's value into every fragment, the assembler checks that a complete set agrees and passes it with the complete/fault event to the consumer. A missing field, bogus value or inconsistency within a fragment group is rejected; the UI must not infer it from RPC timing, a Promise continuation or "the first frame after resync".
3. **Every physical JSON/RPC frame including its envelope is strictly `<= maxFrameBytes = 1 MiB`** (R-12). The topic encoder must take the maximum over CLI NDJSON, Channel/Socket binary and the mobile relay base64 outer JSON, deducting the real envelope and base64 overhead before slicing; attachment upload must not reuse a full-data RPC but must be split into independent small requests by the begin/chunk/commit transaction of §6.5, metered on real parameters at both the Channel and CLI NDJSON entries.
4. After profile filter + coalesce the subscriber buffer must satisfy both `<=500 ops` and `<=max(1 MiB, current wire snapshot conservative upper bound)` (reason for the byte-limit revision: 05 §3); on either overflow clear that subscription's buffer, mark resync, and send only the latest snapshot next (never split an oversized delta into several logical frames that may be inconsistent).
5. An oversized snapshot/resume logical frame uses the `fragment` envelope; per assembly up to 16 MiB and 1,024 fragments; each consumer has at most 32 concurrent assemblies and 32 MiB decoded staging, with a 30s timeout from the first fragment. The service only validates a routable outer candidate; the assembler after ownership filtering validates range/base64/checksum/logical schema and produces a typed fault, and silently dropping a bad frame early is forbidden.
6. The publisher assigns each subscription a strictly increasing `logicalFrameOrdinal`; retrying the same reservation keeps ordinal/id unchanged. A late wire below the tombstone is silently dropped; the same ordinal with a different id yields `proto.frameAssemblyOrdinalConflict`; completion, fault, timeout and consumer abort all keep the tombstone until unsubscribe/generation change.
7. publisher `reserve` does not clear the buffer or advance `sentSeq`; commit happens only after all physical wires are admitted by the current connection queue. An initial encode failure must roll back the subscription, in-flight reservation and flush state; a failed re-subscribe must also restore the old subscription/mapping so a client still holding the old subId keeps receiving the stream. After a successful unsubscribe/re-subscribe a late commit returns false.
8. When admitting new input/attachments would push the transmittable projection over 16 MiB the CLI must explicitly `rejected/failed`; large tool output while running becomes an artifact ref / head+tail, and model text still over the limit terminates the turn with an explicit protocol fault. No path may truncate a snapshot silently.
9. **Priority exists only between topics** (control/ACK > sessions-index > conversation rows > terminal scrollback); **frames within one topic are strictly serial by seq**, and no implementation may let a region-A frame overtake a rows frame (R-11).

### 3.3 Client apply algorithm (normative pseudocode)

```ts
function onWireFrame(store, wireFrame) {
  const { frame, deliveryKind } = assembleAndValidateAtomically(wireFrame, {
    maxBytes: 16 * 1024 * 1024,
  });
  if (!frame) return; // store unchanged until complete; an assembly failure is single-flight resynced by this function
  if (frame.subscriptionId !== store.subscriptionId) return; // (1) old-generation frame: silently dropped
  if (frame.payload.kind === "snapshot") {
    store.replaceAll(frame.payload.snapshot); // (2) wholesale replace, never merge
    store.seq = frame.toSeq;
    store.hasAppliedBase = true;
    // An online overflow snapshot can establish a base, but only a recovery envelope proves this flight was delivered.
    if (deliveryKind === "recovery") markRecoveryFrameSeen(store);
    refetchAroundScrollAnchor(store); // R-18: refill the visible range by the anchor rowId
    return;
  }
  if (frame.toSeq <= store.seq) {
    // aligned `(N,N]` / fully-subsumed recovery does not change the projection but still completes the recovery delivery condition.
    if (deliveryKind === "recovery") markRecoveryFrameSeen(store);
    return; // (3) late/duplicate frame: silently dropped
  }
  if (deliveryKind === "online" && store.recoveryFlight) {
    // A non-duplicate online after the recovery applied is recorded as the post-ACK successor; online
    // arriving earlier is covered by the recovery range. online cannot clear the current flight.
    if (store.recoveryFlight.validFrameSeen) markSuccessorRecoveryNeeded(store);
    return;
  }
  if (frame.fromSeq !== store.seq) {
    resyncOnce(store, {
      forceSnapshot: deliveryKind === "recovery" && store.recoveryMode === "resume",
    });
    return;
  } // (4) gap: single-flight; another gap after resume forces a snapshot
  applyDeltasAtomically(store, frame.payload.deltas); // (5) op semantics of §4.5
  store.seq = frame.toSeq;
  store.hasAppliedBase = true;
  if (deliveryKind === "recovery") markRecoveryFrameSeen(store);
}
```

The three branches ((2) wholesale replace / (3) drop / (4) resubscribe) are a closed set; the client has no "cache compensation / out-of-order reordering / gap guessing" code path. After an attachment rebuild or CLI `logEpoch` change the client re-subscribes automatically; old frames before the new subId takes effect are all silently dropped.

Gap/fault recovery flights are isolated per `(topic,subscriptionId)` and last until a logical frame with `deliveryKind="recovery"` is fully validated and accepted; the RPC ACK alone cannot clear the flight. If a `mode="resume"` recovery frame has another gap, the original flight upgrades into one `forceSnapshot=true` request. The watermark/flight of conversation, sessions-index and workspace-config are not shared; recovering one topic cannot replace a sibling subscription.

`markRecoveryFrameSeen` only records that a complete, validated recovery logical frame arrived; the flight closes only when it and the matching ACK are both satisfied. Even when that frame is aligned `(N,N]` or its `toSeq` is already fully covered by a newer authoritative snapshot, the mark must still be done without modifying the projection again, so a zero-change recovery never dangles forever.

When the original subscribe's initial assembly fault turns into same-sub resync, the consumer must first clear that subscription's `awaitingInitial`; the ruling on a recovery frame/fault precedes the initial-subscribe state, else a recovery gap would be misjudged as a fresh subscribe. A late `online` duplicate, even before the resync ACK, is silently dropped as a duplicate and cannot clear or consume the recovery flight.

After the resync ACK there is a separate 30s deadline until the first complete recovery logical frame (distinct from the assembly timeout that starts at "first fragment received"). When zero notifications / a whole batch lost expires, resume may upgrade to force snapshot only once; the UI's force attempt expiring again goes to an explicit ERROR, and task-index fresh-subscribes that topic. If a recovery frame is applied but a residual non-duplicate online gap arrives before the ACK continuation, the ACK may only close the old flight and an ordinary successor resync must immediately start from the new base; the gap must not be swallowed silently nor wrongly upgraded to a recovery-kind force.

A runtime restart is a full re-subscribe boundary: workspace-level frame emitters stay alive on runtime invalidation, and SessionDataLayer's active/keep-warm conversation stores, SessionsIndexStore and task-index each re-subscribe exactly once on receiving the restart epoch. Only a real workspace/service teardown destroys emitters.

### 3.4 Mobile raw Channel transport envelope

One raw Channel message of a mobile shared-host attachment uses an independent transport fragmentation layer; a topic fragment must not be treated as a raw RPC fragment, and WebSocket compression must not be used to bypass admission:

```ts
type RpcTransportPayload =
  | {
      zcode_type: "rpc-frame";
      bridgeSessionId: string;
      bridgeGeneration?: number;
      recoveryId?: string;
      seq: number;
      messageSeq: number;
      fragmentIndex: number;
      fragmentCount: number;
      messageBytes: number;
      checksum: { algorithm: "crc32"; value: string };
      dataBase64: string;
    }
  | {
      zcode_type: "rpc-frame-ack";
      bridgeSessionId: string;
      bridgeGeneration?: number;
      recoveryId?: string;
      ackMessageSeq: number;
    };
```

`seq` is the physical fragment number, `messageSeq` the atomic raw Channel message number; both are safe integers within one bridge identity. The full normative rules (exact outer-byte metering, `<=1 MiB` per piece, `<=16 MiB / 64 fragments` per logical message, one RX message assembly per direction with a 30s timeout, identity-mismatch handling, duplicate/gap/CRC faults, `MAX_SAFE_INTEGER` exhaustion requiring a new bridge generation, cumulative-ACK-only accounting, the production acknowledged adapter with `8MiB/45s/30s` hard caps and `1MiB/256KiB` high/low watermarks, ACK re-entrancy, the `connection-flow-v1` sideband and the `1 MiB` pre-`JSON.parse` gate) live in [05 §7-§8](./05-transport-and-backpressure.md). Field-level points that remain here:

1. A raw cumulative ACK belongs to transport replay accounting only; it is not the §6.2 command ACK nor a transcript fact.
2. A raw gap's execution outcome is unknown and must hard-rebuild the attachment; relay/main must not interpret topics and resync themselves.
3. 04D-3 switched desktop main / mobile web atomically to the bridge-scoped, bidirectional acknowledged adapter; the global app parser formally accepts the new strict fragment/ACK and the legacy single-piece `rpc-frame` branch is deleted. A raw transport payload is handed only to the current bridge adapter and cannot be consumed by an ordinary app requester or the old per-piece Channel route.
4. The public `ConnectionFlowControl` exposes read-only bytes and saturated/drained events; production mobile sends the state to the CLI via the `connection-flow-v1` MessagePort sideband and trusted `v4/connection/flow`. The UI-facing service method must reject a terminal caller; only the host scope's non-RPC control plane and the trusted-host-relay namespace may inject connectionId. CLI `pausedConnections` affects only the matching connection (SAT clears that connection's timer and double-checks before reserve; ingest and sibling connections continue; DRN flushes only that connection and overflow/needsResync naturally sends the latest snapshot; closed clears the pause and owned unsubscribe separately clears publisher state).

#### 4.2.3 SessionConfigState (G-01)

```ts

  model: string; // model id
```

1. Event write path: `switchModelConfig` / `setFollowupMode` / `switchCollaborationMode` (M5 additive) command -> guard -> event (ModelSelected / FollowupModeChanged / SessionModeChanged) -> this field is replaced wholesale and sent down. `ModelSelected` must carry the runtime's `thoughtLevels` and `contextWindow` after the switch, so `provider/model/thought/thoughtLevels` and that model's actual window converge atomically in the same revision. The client selector UI is an optimistic overlay (pending by commandId) closed as soon as the authoritative value arrives; **there is no "locally selected value vs echoed value" merge logic** (eliminating the P2-10 patch family).
2. The timeline hint for a model switch is generated by the CLI at the next turn start as a `modelChange` marker row (R-17); the protocol has no "staged marker" state.
   - **R-17 timing details (2026-07-07 fifth test ruling, thought-only boundary confirmed 2026-07-08)**: the marker's comparison baseline = **the model identity used by the last actually started turn**, and model identity contains only `provider/model`, not `thought`. Corollaries: (1) toggling the selector in draft state / before the first turn produces no marker (the first turn starts with the final selection; "what is used first" is not a "change"); (2) switching A->B->A while editing yields zero net change and the next turn produces no marker; (3) a thinking-depth change alone (e.g. `high -> max`) updates `config.thought` and request parameters but produces no `modelChange`; (4) the immediate feedback of a switch is **pure UI logic** (toast) and does not enter the timeline. Marker position: immediately before the new turn's turnHeader row.
   - **R-17 display details (2026-07-29, copy corrected 2026-07-29)**: the marker's `fromProvider/fromModel/toProvider/toModel` are full model identities and their comparison semantics do not change due to display trimming. The renderer maps provider IDs to `provider.name` using the current provider snapshot; the built-in Z.ai / BigModel providers show only the modelId, other providers show `provider.name/modelId`, falling back to `providerId/modelId` when the config was deleted or not yet hydrated. This matches the model trigger and toast and does not change the marker schema, generation timing or replay semantics.

**config seed semantics (R-19, ruling 2026-07-07; closes the M6 TODO "draft-phase revision-free seed channel")**:

1. **The first snapshot's `config` must equal the runtime truth**: `provider/model/thought` = the runtime's current model selection (including the resolved workspace catalog default model / persisted preference at startup), `thoughtLevels` = the result of `listThoughtLevels()` for the runtime's current model, `mode` = the runtime's current collaboration mode (including the project's persisted permission mode preference). Using an empty `provider/model`, a hardcoded `mode="build"` or the client's generic five tiers as the initial value is forbidden.
2. **The seed channel = snapshot construction, not an event delta**: the seed is read from the runtime and injected at projection initialization (`getModelRef()` / `getMode()` / thought level), producing no `state.updated` and no revision increment, so the draft ruling "no visible delta, no revision bump" (§4.2.1) is preserved. R-04's revision rule is unchanged: only a **change** of config increments; the seed is an initial value, not a change.
3. **Cold recovery uses the same position**: when transcript hydration / cold resume rebuilds the projection, it first seeds from the runtime truth and is then overwritten by replaying ModelSelected / SessionModeChanged from the log (replay order is after the seed; the final value follows the log).
4. **Hydration does not lose the live tail**: the first rebuild is single-flight per session; raw events between reading the memory eventStore snapshot and the publisher replacing it go into a temporary buffer. Raw sequence can arrive out of order because each event awaits persistence, so it must be staged by `sourceEventSeq+1` and drained contiguously; "already saw a larger seq" must not be used to drop a late queue/stream fact. The synthesized sequence and the runtime raw seq establish a monotonic offset via the snapshot cursor; eventId + cursor is used only to remove true duplicates already in the snapshot.
5. **First-subscribe timing must not change the terminal snapshot**: if the first reply completed before the client's first `subscribe`, cold hydration must rebuild from durable message/part the same visible end state as the early-subscribe live path, including persisted user and assistant text. `providerVisibility` and `uiVisibility` / `transcriptVisibility` are orthogonal dimensions; a normal `assistant_response` is visible to provider, UI and transcript at once and must not be classed as provider-context-only because of `providerVisibility=visible`. Desktop `desktop-continuous` and mobile `web-remote-replayable` may have different intermediate-frame delivery policies, but the first complete snapshot of the same durable transcript must be identical. Delayed providers, early subscription, retry or client frame-filling must not be used to mask this invariant.
6. **Seed source by scenario (priority pinned so an implementation does not read the workspace default uniformly and wash out session history)**:
   - New session (draft first send): `createSession.config` (the user's earlier choice) > runtime startup default (workspace catalog default model / project-persisted mode preference).
   - Historical session resume: **the session's own historical selection wins** - `derivePersistedRuntimeSettings` takes, from persisted messages in reverse, the last used model (thought carried in `modelRef.variant`) and mode and writes them back to the runtime via `reconcileResumedRuntimeSettings`. The model must resolve in the current Environment's Registry; Provider Refactor removed the App-delivered `runtimeModel` authoritative override. The V4 gateway chains runtime activation and projection hydration with one READY promise; it must not build or return a legacy full-session snapshot for V4. The legacy `session/resume` keeps compatibility with `activation + legacy snapshot` wrapping. **The seed value must be taken after activation completes** (gateway order: activation -> hydrate); the product semantics: "opening a historical session defaults to the previous model and thinking depth". Full boundary: [17-cold-resume-runtime-activation.md](./17-cold-resume-runtime-activation.md).
   - In-session switch: command events (ModelSelected / SessionModeChanged) override, as in the write path above.
7. **`createSession.config` must be consumed**: when the payload carries a partial config (a draft-state UI's early choice, see m5-composer-parity §5), the CLI at session creation merges the initial value as "requested config overrides runtime default" and then injects it into the projection through the seed channel; omitted fields fall back to the runtime truth. The current implementation only accepts the field in the schema and the handler does not consume it: an implementation gap.
8. **A same-value switch ACK must be distinguishable**: `switchModelConfig` / `switchCollaborationMode` hitting the runtime's current value replies `noop` + `reasonCode="config.unchanged"` and must not be swallowed silently as accepted (no result). With the seed aligned, "UI shown value = runtime truth" holds and the noop semantics are accurate.
9. Known failure modes behind these rules: a missing seed made the new-session model selector show empty (`ModelSelected` was only issued after switchModelConfig) and made a project-persisted mode=yolo show as build in the UI while the handler returned early on the same value, so the UI never converged: same root cause, "same-value check uses the runtime truth while the UI display uses the projection seed, with no alignment moment". Likewise the old snapshot projected only the current `thought` and not which thought levels the current model supports, so a fork child with no legacy task config cache fell back to a hardcoded five tiers; capability is part of the model configuration tuple and must enter the same snapshot/event from the child runtime, never guessed from localStorage, the workspace catalog or a client fallback.

Input conservation and fallback rules:

1. Committed busy/running input from desktop/mobile first enters the same CLI `CommandInbox` FIFO, ordered by `order.admissionSeq`; mobile V4 no longer goes through a host runtime second queue.
2. When guide does not apply, carries attachments, or compact/verifier is busy, the same intent (original text, attachments, clientId, sourceCommandId unchanged) falls back to the ordinary queue and records `delivery.fallbackReasonCode/steer.state="fellBack"`.
3. An eligible guide may wait before a tool call appears; once all sibling tool results (success or failure) of one model step are submitted, the runtime inline-drains at most one guide before starting the next provider request of the same product turn. A single parallel sibling completing must not drain early, and multiple guides cannot be cleared in one batch.
4. When the current turn completes text-only, is stopped or interrupted with no usable tool result batch formed, an undrained guide must be redirected to the queue in place via an explicit delivery/fallback fact; `sourceCommandId/queueItemId/clientId/admissionSeq/payload` all unchanged, with live/cold projection converging identically.
5. Ordinary queue auto-promotion must satisfy `autoDrain=true`, session ready/no active controller, and `target` absent or `target.status=complete`. This guard covers all of text, goal command and compact; a verification marker alone cannot unlock.
6. A verifier's explicit pass and fail-open both first write `passed=true` and update the target to complete, then re-evaluate the queue normally; a manual Stop/abort is cancelled/failed + target paused + `autoDrain=false`, not a pass. `sendQueuedNow`'s reservation + Stop barrier is the explicit exception.
7. empty/oversize/runtime reject returns an explicit `rejected/failed`; the UI keeps text and attachments and must not clear first and fail silently.
8. `editQueueItem` updates in place, keeping ID, position, attachments and source command; `reorderQueueItem/deleteQueueItem/drain` all operate the same intent by `queueItemId`.
9. The drain/guided row/message anchor must reuse the original `sourceCommandId`, not the promotion or send-now commandId.
10. `sendQueuedNow` is fixed as `reserve -> stop barrier -> start/promote -> remove`; remove only after start succeeds. timeout/failure releases the reservation with the original item unchanged; repeated clicks and multi-end clicks may have only one reservation owner.

The `sendQueuedNow` reservation is held by the CLI runtime by `queueItemId`, and `TurnSteerDispatchChanged` projects `queued/reserved/promoting` onto the QueueItem. A reserved head forbids an ordinary roundtrip drain, an ordinary delete must hold the same reservationId, and promotion may only restore the input from the complete QueueItem with `inputId` still using the original `sourceCommandId` (never degrading to text-only or the send-now commandId). A failure before the start barrier returns to queued; if remove throws after start was admitted it stays promoting and must not be released and re-executed.

The `promoted` reason of `remove` only removes from the queue projection and must not set the session-input ledger to cancelled: the text turn's user message is written only in the background start phase, and an early cancelled would recreate the crash window "queue gone -> transcript not yet persisted". The ledger stays admitted until message/parts and the ledger commit in one transaction; after the commit `SessionInputPromoted` is sent, the gateway first invalidates the old transcript query seed and then releases the CommandInbox live pin. If the CLI exits before commit, the recovery sweep explicitly sets admitted to `discarded(session_resumed)`.

The queue is reliable only within the current CLI process. After a CLI restart an admitted input not yet in the transcript is not executed again; a tombstone is left in the discarded-input ledger, and `commands/query` returns `failed/fault.command.inputDiscardedOnRestart` with a persisted `delivery` in the typed result. `queue/guide` and an `unknown` without an authoritative conclusion are settled silently by the client with no UI error; only a `startNow` not in the transcript lets the user confirm a resend with a new commandId.

`ConversationInputIntent` is the only input fact after CLI admission and must be validated against the strict schema; an omitted `attachments` normalizes to `[]`. `inFlight` (executing), `liveInputFacts` (still in queue/guide) and the `settled LRU` (512 per session) are three tables: the first two are pinned and cannot be evicted by LRU churn. The CLI allocates `order.admissionSeq` serially per session; different sessions can run in parallel.

Persistence boundary, frozen: the user message's `metadata.conversationInputIntent` and the session-input ledger's `payload.conversationInputIntent` store the full strict object; `message.anchor.sourceCommandId` stores the fast dedup anchor. An input command first writes the ledger (including startNow/createSession.firstInput) before the business handler runs, then lets the UI receive accepted; the real routing events of Queue/guide idempotently correct delivery/fallback with the same `queueItemId`. Admission before execution is also pinned into CommandInbox and released only by atomic promotion, explicit cancel/failure or discarded; 512-LRU churn cannot evict it. A draft first send must first establish the session foreign key through the runtime's unified persistence boundary and then write the ledger (not rely on the background startPromptTurn creating the session, otherwise admission fails at the FK boundary and loses the authoritative record). The command key of `createSession.firstInput` belongs to the `sessionId=null` global bucket while the ledger/transcript belong to the newly created session; the ledger must additionally store `sourceCommandType="createSession"` and allow recovering the real session with the globally unique `queue_<sourceCommandId>` when the sessionId is unknown. After atomic promotion a retry with the same commandId returns the first `result.sessionId`; if still admitted at restart it is first set to discarded and returns `fault.command.inputDiscardedOnRestart`, forbidding a second session. The early transcript `metadata.inputIntent` is only a compatibility read seed; new writes must not store only the seed. The runtime may use the layered carrier `TurnInputIntentMetadata + input + unresolved attachments` to avoid depending on the wire package, but only through the same canonical adapter that generates the complete object above; projection/hydration must not each infer delivery, steer or dispatch.

A successful side effect with no user message uses `session_entry(type="v4/command_fact")` to store the timeline/child ACK; the compact timeline part also writes `sourceCommandId`. After a CLI restart, an old session-input still admitted is atomically closed as `discarded(session_resumed)` on first persistent query/recovery, and `commands/query` must return `failed/fault.command.inputDiscardedOnRestart`, never unknown nor an automatic replay.

### 4.3 Row paging (cursor-based, R-06)

1. A snapshot carries only the tail window; older history is pulled with `rows/range` (§7.1) by the `beforeRowId` cursor.
2. **No index semantics anywhere**: the total order of rows = rowId ascending; client merges always use rowId as the sort key.
3. A patch hitting an unloaded rowId (scrolled out and evicted by the client / in an unfetched history segment) is a **no-op**; evicted rows can only be retrieved by `rows/range` again.
4. `row.removed(fromRowId)` acts on all rows with `rowId >= fromRowId` in the client's loaded set (including fetched history segments), so truncation is naturally consistent with no seq gating.

The cost is that schema skew between the two sides becomes **silent** (cards quietly degrade to text). The compensation is parity tests between the constructing side and the mirror side, not letting live subscriptions discover it. A required-field skew has no card to drop and still rejects the frame; its backstop is 04-sync-and-recovery closed rule 11. ### 4.5 Delta: seven operations + coalesce + revision progression

```ts
type ConversationDelta =
  | { op: "row.appended"; row: ConversationRow } // append to the tail (99%)
  | { op: "row.upserted"; row: ConversationRow } // whole-row replacement by rowId (state machine transition)
  | { op: "row.removed"; fromRowId: number } // delete this row and everything after (rewind/edit)
  | { op: "row.delta"; rowId: number; path: StreamablePath; append: string }
  | { op: "state.updated"; patch: StatePatch }
  | {
      op: "workflowRun.updated"; // keyed increment by runId; only workflowRuns has it
      runId: string;
      revision: number; // workflowRuns.revision after this change (absolute, non-negative integer)
      run?: Partial<WorkflowRunHeader>; // header keys replaced wholesale, never deep merge
      cleared?: WorkflowRunHeaderKey[]; // header keys that become default (the convention of that key is "empty = default")
      removedActors?: { siteId: string; ordinal: number }[]; // evicted entries, key = (siteId, ordinal)
      removedNodes?: { siteId: string; ordinal: number }[]; // same
      actors?: WorkflowRunActor[]; // whole entries, same key
      nodes?: WorkflowRunNode[]; // same
    }
  | { op: "workflowRun.removed"; runId: string; revision: number };

type StreamablePath = "text" | "inputText" | "output.text" | "summaryText"; // closed whitelist (09 §9)

interface StatePatch {
  // key-level wholesale replacement (Object.assign), closed key set
  revision?: number;
  control?: SessionControl;
  availability?: SessionActionAvailability;
  inputRouting?: InputRouting;
  config?: SessionConfigState;
  usage?: SessionUsageState;
  queue?: QueueState;
  pendingInteractions?: PendingInteraction[];
  pendingCommands?: CommandStateSummary[];
  backgroundWorks?: BackgroundWorkSummary[];
  workflowRuns?: WorkflowRunsState; // whole-key form; still the only form for snapshots and non-declaring subscribers
  goal?: GoalState | null;
  plan?: PlanState | null;
}
```

`workflowRuns` is the only state key with keyed increments too: one engine event changes only a few header fields and a few entries of one run, and resending the whole key per event is O(N^2) bytes. The entry bounds do not vanish: a snapshot still carries the whole key, and the bounds are its budget (see [presentation.md](../dynamic-workflow/presentation.md) "The run state the pane draws"). `WorkflowRunHeader` = `WorkflowRunState` without `actors`/`nodes`, derived by schema `.omit` rather than a hand-copied vocabulary. Semantics:

1. Header keys are replaced wholesale per `run` and removed per `cleared`; small collections inside the header (`reports`/`artifacts`/`phases`/`pendingQuestions` ...) remain wholesale-replaced values with no second-level increment.
2. `removedActors`/`removedNodes` delete entries by `(siteId, ordinal)` (a missing key is a no-op); `actors`/`nodes` upsert by the same key: a hit replaces, a miss appends at the tail. Entries are **not reordered**: the producer evicts only when hitting a bound ([presentation.md](../dynamic-workflow/presentation.md) "Reduction"), the eviction must be stated with these two keys, and order changes beyond deletion are still not expressible in this model. The bounds of the four arrays = `WORKFLOW_RUNS_LIMITS.maxActors` / `maxNodes`.
3. Within one op the application order is fixed as **header -> delete -> upsert**: a key deleted and added in one op lands at the tail of the table, matching the result of applying two ops one by one.
4. apply: with `workflowRuns` absent start from `{revision: 0, runs: []}`. A hit run updates per the rules above; a missing run whose `run` is a **complete header** (all required header fields present) = newly born, appended to the end of `runs`; a missing run with an incomplete header = a well-defined no-op (the same rule as `row.upserted` hitting an unloaded row), no error. `workflowRun.removed` filters that run out, only advancing revision when missing. The container `revision` takes `max(current, op.revision)` (coalesce moves ops of the same run forward, see below). Unchanged runs and entries keep object identity; changed runs and the container are new objects.
5. **The client never enforces bounds** (`maxRuns`, entry bounds, total budget): eviction is done only by the producer and stated explicitly: a whole run with `workflowRun.removed`, table entries with `removedActors` / `removedNodes`.
6. One engine event produces at most one `updated` per run (node, derived actor state, usage and `lastEventSequence` land atomically together), plus `removed` for evicted runs.
7. Neither op enters the profile filter (the same class as `state.updated`, §3.6), and neither increments the conversation revision: `workflowRuns` carries its own monotonic revision and no command's baseRevision CAS reads it.
8. A subscriber that did not declare `workflowRunDeltas` (§2) does not receive these two ops: the publisher degrades the whole batch of `workflowRun.*` into one whole-key `state.updated{workflowRuns}` clamped to the old bounds ([05 §1.1](./05-transport-and-backpressure.md)).

coalesce rules (pure functions in `@zcode/protocol`):

1. Adjacent `row.delta` with the same `(rowId, path)` -> concatenate the append.
2. Adjacent `state.updated` -> shallow-merge the patch keys (whole replacement within a key, safe).
3. A `row.delta` followed by a `row.upserted` with the same rowId -> the former is dropped.
4. `row.removed` is a barrier that no rule may cross.
5. A merged single frame over `maxFrameBytes` -> split per §3.2.
6. `workflowRun.updated` of the same runId merges forward into the **last** same-runId `workflowRun.updated` in the window not separated by a barrier: header keys last-wins and reconciled with `cleared` (a later assignment moves the key out of `cleared`, a later clear moves it out of `run`), entries last-wins by `(siteId, ordinal)` keeping first-appearance order, and `revision` takes the last. Deletes and upserts are derived as "merging equals sequential application": `removedActors` / `removedNodes` take the union of both sides (deduplicated by first appearance), and **every key in the earlier op's upserts that the later op deletes is removed**, then the later upserts are layered on per the rule above; so a key deleted then added lands at the tail, which is exactly the position sequentially applying two ops gives. There are two kinds of barrier: a `state.updated` whose patch contains `workflowRuns` (whole-key replacement), and a same-runId `workflowRun.removed`; `removed` also swallows all `updated` of that run since the previous barrier (born and deleted within one window, the client never saw this run: equivalent). **If any of the four merged entry tables exceeds the wire bound, do not merge**: leave both ops as they are in the same order. Only the two **delete** tables can actually overflow: by the merge rule every key kept in an upsert is still in the table after the op, and the table is bounded; the delete tables lack that guard, since merging cannot tell "a key born and evicted within the window" from "a key the client already holds", and each eviction frees a slot, so in a wide enough window the distinct deleted keys can exceed the table bound (before eviction impossible: the table only grows). All four are checked only because the gate is cheap, not because that argument must keep holding. An oversize payload would not simply lose a key: it would fail the whole patch parse and drop the whole frame. Merging is an optimization and refusing to merge does not change the end state. The target is the **last** op rather than an earlier one precisely for this case: when merging always succeeds only one `updated` remains after the barrier and "earliest" and "last" are the same op; once one merge is refused, merging into an earlier op would make a later upsert jump **before** the middle op's delete and a delete-then-add key would vanish.

The forward move of rule 6 across intervening row ops, ops of other runIds and `state.updated` without `workflowRuns` is commutative: they act on disjoint state, and a newly born run enters `runs` in first-appearance order, which is unchanged. The only non-commutative thing is the container `revision`: when ops of two runs interleave, the last op of the merged output sequence must still carry the highest revision, guaranteed by apply taking `max` (revision is monotonic by contract). The criterion is still the existing golden test equality: `applyAll(s, coalesce(ds))` is byte-identical to `applyAll(s, ds)`. After merging each in-flight run has at most about 2 ops per window (a few more when bound-hitting refuses merge), independent of fan-out width, so the 500-op bound of §3.2 is not threatened by these two ops.

**revision progression rules (R-04, closed definition)**: each of the following events adds +1; the rest (pure `row.delta` text streams, `usage` changes, `pendingCommands` changes, `workflowRuns` changes (including both `workflowRun.*` ops), `ToolProgress` updates) **do not increment**:

| Events that increment revision                                                                                        |
| --------------------------------------------------------------------------------------------------------------------- |
| row.appended / row.upserted / row.removed (any row structure and state machine change)                                |
| any change of control / availability / inputRouting / config / queue / pendingInteractions / backgroundWorks / goal / plan |

Carrying rule: any frame containing a revision-incrementing event must contain `state.updated.revision` in its deltas (naturally satisfied after conflation: at least the revision key is present). CAS (§6.2) thereby becomes well-defined: **revision unchanged <=> no guard-visible state change**.

### 6.2 ACK


| status      | Semantics                                                                                                                                                                                                                                                | UI closeout                                      |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| `accepted`  | The CLI accepted the command; an input command has completed serial admission and entered the input ledger/inbox. **Input is not promised to keep executing across CLI processes**; final closeout is by `sourceCommandId` hitting a QueueItem/row/transcript or an explicit discarded | Keep the optimistic overlay and pending registry, wait for authoritative state |
| `rejected`  | Rejected by a guard                                                                                                                                                                                                                                      | Withdraw optimistic, prompt by reasonCode        |
| `stale`     | baseRevision too old                                                                                                                                                                                                                                     | Withdraw optimistic; the user resends after fetching the latest projection |
| `duplicate` | **The same commandId** was already processed                                                                                                                                                                                                             | Close out with result, do not replay side effects |
| `noop`      | The command is valid but there is nothing to do (R-09): stop-while-stopping, resolveInteraction already answered by another end                                                                                                                          | Close silently; result carries the existing conclusion |
| `failed`    | Execution failed after accepted                                                                                                                                                                                                                          | Show by reasonCode; together with lastError/row state |

Idempotency and retry (position after the §9.3 ruling):

1. Server dedup order: in-memory LRU -> the `sourceCommandId` of transcript user/message anchor, timeline marker and fork child metadata -> discarded input ledger -> `unknown`. A discarded hit returns `failed/fault.command.inputDiscardedOnRestart` and must not degrade to unknown.
2. A query and an execute for the same `{sessionId,commandId}` share a single-flight/mutual-exclusion entry, eliminating the window "execution started, LRU/transcript not yet written"; a concurrent duplicate / fork duplicate may execute the side effect only once.
3. Client 24h pending registry: ordinary text/goal keep a re-sendable payload, sensitive interactions only a digest. A record is deleted as soon as the QueueItem/guided projection appears; on reconnect first reconcile with `commands/query`, discarded `queue/guide` and unknown are settled silently, only `startNow` keeps manual confirmation; every branch **never auto-resends**.
4. The registry is keyed by `{sessionId,commandId}` in renderer persistent storage, and the write must precede the first `v4/command` upstream; the TTL is fixed at 24h from first write and a refresh, attachment rebuild or CLI runtime generation change must not extend it. `sendText`, `sendGoalCommand` and `createSession` carrying `firstInput` keep a re-sendable payload; `resolveInteraction` keeps only a payload digest and must not persist permission answers, freeText or elicitation content.
5. An input command receiving `accepted/duplicate` only proves admission and alone does not delete the registry; deletion happens on the QueueItem/guided projection or transcript user row with the same `sourceCommandId`, explicit rejected/stale/noop/failed/cancelled, discarded `queue/guide`, or TTL expiry. A sensitive interaction can be deleted after a definite ACK; with an unclear ACK delete after the reconnect query returns; `unknown` is likewise deleted silently.
6. Every time a conversation subscribe goes live (including a fresh snapshot after a runtime restart) first query the registry per session in batches of at most 64 items. `unknown` and `failed/fault.command.inputDiscardedOnRestart` with delivery `queue/guide` are settled directly with no UI error; only delivery=`startNow` generates one recoverable notice. The UI submits the saved input payload with a **new commandId** only after the user clicks "Resend". A sensitive interaction without payload meeting `unknown` also settles silently. queryUnavailable keeps the entry for the next connection reconciliation and does not pose as unknown.
7. Frame loss during a live connection is covered by rpc replay; the client does no application-layer timed resend.

### 6.5 Attachment upload (G-07)

```ts
attachment/begin {
  connectionId: string;         // injected by the trusted host, not selectable by the UI
  uploadId: string;
  sessionId: string;
  fileName: string;
  mime: string;
  totalBytes: number;           // 0..20 MiB
  totalChunks: number;
  checksum: `sha256:${string}`;
} -> { uploadId: string; state: "staging"; nextChunkIndex: number }
   | { uploadId: string; state: "committed"; nextChunkIndex: number; ref: string }

attachment/chunk {
  connectionId: string;
  sessionId: string;
  uploadId: string;
  chunkIndex: number;
  dataBase64: string;           // per-chunk decoded <= 512 KiB
} -> { uploadId: string; nextChunkIndex: number }

attachment/commit { connectionId: string; sessionId: string; uploadId: string }
  -> { ref: string }

attachment/abort { connectionId: string; sessionId: string; uploadId: string }
  -> {}

interface AttachmentRef {
  ref: string;                   // artifact store reference
  fileName: string;
  mime: string;
  bytes: number;
  previewRef?: string;           // image thumbnail etc.
}
```

```text
renderer/mobile bytes
  -> begin
  -> chunk[0..N) (sequential, per-chunk ACK, each physical envelope <= 1 MiB)
  -> commit (whole-bytes + sha256 validation)
  -> stable artifact ref
  -> sendText/createSession AttachmentRef
```

The transaction key is at least `(trusted connectionId, sessionId, uploadId)`. A begin retry with the same metadata returns the current `nextChunkIndex` / committed ref; conflicting metadata is rejected. A chunk accepts only the expected next index; the same index + same bytes is a no-op, a conflicting duplicate or future gap fails explicitly. commit writes the artifact atomically only after chunk count, total bytes and whole SHA-256 all match; an ACK-loss retry returns the same ref. abort is idempotent. Active uploads, global staged bytes, TTL, connection close, session close and CLI restart all have hard cleanup boundaries, and a half-finished upload never enters the artifact store.

The UI level is still "put attachment -> ref", but the production wire no longer has a `v4/attachment/put` fallback carrying the full `dataBase64`. An upload failure does not clear the composer text/attachments; after a CLI restart bytes are not replayed automatically. A ref not referenced by any message is reclaimed by TTL (§8).

## 7. Query layer (read-only, stateless, safe to resend on timeout)

### 7.1 rows/range (R-06 cursor-based)

```ts
rows/range {
  sessionId: string;
  beforeRowId?: number;          // fetch rows with rowId < beforeRowId; omitted = backward from the current tail
  limit: number;                 // 1..200
} -> {
  rows: ConversationRow[];       // rowId ascending
  atSeq: number;                 // watermark when the server took the value
  atLogEpoch: string;
  hasMore: boolean;              // whether earlier rows remain in the beforeRowId direction
}
```

Merge rules (client): insert keyed by rowId; naturally consistent with the subscription stream's `row.upserted/removed` (§4.3); a result whose `atLogEpoch` differs from the store's current epoch is **discarded wholesale** (a stale read across a CLI restart).

### 7.2 toolOutput/get, attachment/read and artifactd

```ts
toolOutput/get { ref: string; byteRange?: { start: number; end: number } }
  -> { bytes: binary; totalBytes: number }

attachment/read {
  sessionId: string;
  ref: string;
  offset: number;
  limit: number;       // 1..512 KiB decoded bytes
} -> {
  dataBase64: string;  // NDJSON-safe chunk
  mediaType: string;
  totalBytes: number;
  nextOffset: number | null;
}
```

1. `attachment/read` is a strictly read-only query: the server must first hydrate the session to the current projection and then confirm the ref equals the `previewRef ?? ref` of an image attachment of any user row of that session; non-images, cross-session refs, arbitrary paths and out-of-range offsets all return a structured fault.
2. A single decoded chunk must not exceed 512 KiB, so that base64 does not break the 1 MiB NDJSON envelope; the client pulls in order by `nextOffset` and validates that `totalBytes`/`mediaType` stay unchanged across chunks. The server may keep a 30-second, total-bounded read cache per session/ref, cleaned on session dispose and CLI dispose.
3. The ref lifetime = the lifetime of the matching message (artifact store on disk, valid across restarts). The compact `summaryRef` continues to use `toolOutput/get`; an attachment `previewRef` prefers `attachment/read`. A historical attachment with only `ref` may read that ref but must still be authorized through the current session row.
4. A query adds no conversation event, snapshot, queue or relay/main business state; desktop `desktop-continuous` and mobile `web-remote-replayable` share this read contract.

### 7.3 commands/query (reconnect reconciliation)

```ts
interface CommandKey { sessionId: string | null; commandId: string }

commands/query { commands: CommandKey[] }      // 1..64 items
  -> { results: Array<{ key: CommandKey; result: CommandAck | "unknown" }> }
```

Each key is looked up in the order `in-memory LRU -> transcript/message anchor -> timeline marker -> fork child metadata -> discarded input ledger -> unknown`. query and execute share the same-key single-flight. A discarded-ledger hit returns `failed/fault.command.inputDiscardedOnRestart`; only when all fact sources miss is it `unknown`. Client behavior: §6.2.

Additional constraints:

1. `commands` must be 1..64 items and results strictly keep input order; `sessionId=null` queries only the global / `createSession` idempotency bucket. A create command carrying firstInput finds the new session's ledger exactly via `queue_<sourceCommandId>`; promoted returns the original `result.sessionId`, admitted-on-restart returns discarded.
2. The exact in-memory order is `inFlight -> liveInputFacts -> settled LRU`; the exact persistent order is `message anchor -> timeline marker -> child metadata -> discarded ledger`, hitting only on an exactly equal `sourceCommandId`; guessing by text or timestamp is forbidden.
3. query and execute share the same per-key gate; the fixed locking order is key gate -> per-session admission gate. A concurrent query after execute has pinned must not return `unknown`; admission of different commandIds in the same session is strictly FIFO and different sessions do not block each other.
4. When that session already has a V4 cold READY flight, query/execute must wait first and then query the current persistent facts with the original priority; no querying the old watermark then re-querying, and no actively activating a historical session.
5. A persistent read failure returns a per-key `failed/fault.command.queryUnavailable` and must not degrade to `unknown`; `unknown` is not cached. The persistent index is built lazily per session and updated incrementally; the workspace isolation key is fixed as `workspaceIdentity?.trim() || workspacePath`; a full transcript scan per query is forbidden.

### 7.4 First-screen bootstrap

No aggregation middle layer (05): after the connection is established the client issues **in parallel** `subscribe(sessions-index/<ws>)` + `subscribe(conversation/<active sessionId>)` + settings-class queries, multiplexed over ws and completed within one RTT. There is no dedicated bootstrap method.

### 7.5 Live conversation telemetry feed

Conversation telemetry uses an independent ephemeral live feed, not part of the conversation topic and not participating in snapshot, fragment, recovery or `rows/range`. Facts are split only from the current CLI process's runtime live ingest:

```ts
interface ConversationTelemetryFactBase {
  version: 1;
  eventId: string;
  eventSeq: number;
  occurredAt: Timestamp;
  sessionId: string;
  sourceCommandId?: string;
  turnId?: string;
}

type ConversationTelemetryFact = ConversationTelemetryFactBase &
  (
    | { kind: "turn.started" /* metadata only */ }
    | { kind: "model.request.status" /* allowlisted request fields + hostname */ }
    | { kind: "stream.chunk"; streamKind: "thought" | "text"; chunkLength: number }
    | { kind: "tool.lifecycle" /* ids/status/allowlisted perf; no input/output */ }
    | { kind: "permission.lifecycle" /* request/response timing */ }
    | { kind: "usage.delta" /* token counters only */ }
    | { kind: "turn.terminal" /* success/fail/interrupted */ }
    | { kind: "compaction.terminal" /* old /report compaction fields */ }
  );
```

Mandatory boundaries:

1. persisted hydration, subscribe initial, cold snapshot and gap recovery produce no fact; a live runtime event newly arriving during hydration still produces exactly one.
2. A fact does not enter the transcript, ConversationRow, event log, relay or main business state.
3. Prompt/text chunks carry no body; tools carry no input/output; the model URL keeps only the resolved hostname.
4. The Host opens the subscription according to the attachment's trusted `clientMode`; only a `desktop-continuous` renderer installs the actual reporter; `web-remote-replayable` must not widen the old desktop collection scope through forged fields.
5. The workspace supervisor key is `endpoint + remoteSessionId + (workspaceIdentity?.trim() || workspacePath) + serviceGeneration`; the pane/SessionDataLayer lifecycle must not own this state.
6. eventId uses a bounded LRU of about 2000; terminal and compact are additionally exactly-once by business key.

Full event names, field compatibility and the foreground/background matrix: [`docs/monitoring/conversation-telemetry-v4.md`](../monitoring/conversation-telemetry-v4.md).
