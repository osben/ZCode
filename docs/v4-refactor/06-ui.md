# UI Rewrite: Read-only Projection Rendering and Multi-session Split Panes (Implementation Design)

> **Status: the V4 UI main path and the cross-workspace workbench have landed; the body keeps the implementation-time design and capacity targets.** Current entry points: `packages/ui/src/v4/SessionPane.tsx`, `sessionDataLayer.ts`, `conversationProjectionStore.ts`, `paneLayoutStore.ts`, `workspaceConnectionRegistry.ts` and `V4WorkspaceChatArea.tsx`. Migration trail details (the old root causes, step-by-step landing and deletable line counts) are in git: `git show b8876e8b:docs/v4-refactor/06-ui.md`.

## Current landed result (2026-07-15)

- conversation rows, phase, actions, queue, interaction and config are consumed read-only from the per-session projection store; a snapshot replaces atomically, deltas apply contiguously, a gap/epoch triggers recovery.
- `SessionDataLayer` reuses stores per topic and manages subscriptions with lease/refCount; closing a pane releases only the view and does not stop the CLI session.
- Pane layout uses a tree model supporting draft pane, session pane, split, focused pane and renderer workbench restore.
- `workspaceConnectionRegistry` reuses connections per endpoint/workspace scope; remote panes use their own Host/service and never treat the same workspacePath as the same identity.
- The task/session list reads liveness from sessions-index; pin/archive/group/unread join from tasks-index.
- `zcodeSessionStore` still keeps shell/navigation/task-list/compatibility metadata; "delete conversation zustand" only means removing its ownership of conversation facts, not physically deleting the whole store.

## Projection store design

### SessionPane callbacks and projection release (2026-10-16)

SessionPane validates the lease's owner (layer and the pane's sessionId) before reading the projection. Switching sessions must not render the new identity with the old lease: that would let stable callbacks depending on the new sessionId capture an old snapshot/store and chain generations of render through a shared lexical environment. The lease state lives in a separate hook scope; a mismatched owner is reset within the current render, and the old lease is still released by the original acquire effect's cleanup.

```text
switch session / layer -> lease owner mismatch -> projection empty for this render
                       -> original effect release -> new effect acquire -> new owner's projection
draft first send -> same layer, same prewarmed session -> keep lease and Composer instance
ordinary session drag -> stays in the pane; only the draft controller may upload to the draft header
```

Returning to a draft after promotion must re-decide the owner and must not reuse the already-promoted old lease. SessionDataLayer remains the only manager of refCount / keep-warm: no timed reclamation, capacity threshold or production GC, and no clearing of closed store content to mask a reference problem. Callback caching and the original-session semantics of in-flight commands are unchanged.

Regression: with 8 completed sessions switched 136 times, at checkpoints of 8/40/72/136 switches and an idle control, wait for the existing keep-warm to expire and run GC twice in test, saving raw heap snapshots and closing logs; check whether strong references to old snapshots and closed stores are released. Also verify draft promotion, return to draft and layer switching.

> 2026-07-13 sidebar state ownership: "delete conversation-related zustand" here only means conversation business facts; it does not remove the Zustand library or every renderer-local store. `activeTaskId`, navigation, drafts and scroll/focus continue to use Zustand; the sidebar's phase/activity/attention read sessions-index and pin/archive/group/unread read the tasks-index field join; reading the old runtime/ui/unread/taskListCache fact tables is forbidden. See [V4 left-sidebar task state authority design](../superpowers/specs/2026-07-13-v4-sidebar-task-state-authority-design.md).

> 2026-07-13 startup/entry semantics: app cold start and workspace-only open always enter a draft, do not consume the pane's last-session and do not activate a persisted workbench group/pane; only the first workspace of the same renderer reload may restore the visible session from before the refresh, keeping in-progress output streaming. All desktop workspace/new-task entries share one navigation transaction "exactly activate workspace -> leave the active workbench group -> reset primary pane -> startDraft"; explicit session/task navigation then overrides the draft with the target `sessionId`. Mobile `/remote` does not consume the desktop group/pane persistence and the replayable recovery boundary is unchanged. Full boundary: [Workspace / App entry draft state](../workspace-entry-draft.md).

The replacement is a thin per-session projection store:

```text
Map<sessionId, { projection, optimisticOverlay }>
  - sole writer: subscription push (snapshot wholesale replace / row patch / seq-contiguous apply)
  - UI read-only
local state (stored physically apart from the projection):
  draft / scroll / focus / hover / panel open-close
  draft and in-flight commandId persisted to localStorage
```

The right side pane's `tabs` are a workspace-level renderer-local registry, while the panel's expanded/collapsed state is a per-conversation display preference stored by `workspaceKey + sidePaneOwnerId`. When switching conversations, existing visible tabs must not override the user's deliberate collapse for the current conversation; only the user opening/activating new side-pane content or expanding via the top toggle updates that conversation's expand preference. With no visible tab it is forced collapsed. The preference never enters Host, Agent, session snapshot or remote replayable data.

The client obeys the three rules of [04-sync-and-recovery.md](./04-sync-and-recovery.md) and produces no conversation fact except the optimistic overlay (pending/stopping display). All code where the UI derives control flags itself is obsolete (`useChatViewDisplayFlags.ts`, `lib/chatStatus.ts`, etc.); the projection's sessionControl/actionAvailability drives them directly.

## Split panes: three separated state layers + SessionPane instancing

The old root cause: three concerns welded together (`tabStore.activeTabId` was both "what to show" and "who to operate on"; the store was bucketed per workspace but consumers took a global "current"; `ChatView` was a singleton). Rewritten as three layers with one-way dependency:

```text
(1) SessionDataLayer -- pure data, unaware of "display"
   Map<sessionKey, SessionStore>          sessionKey = workspace + sessionId
   SessionStore = { projection, optimisticOverlay, subscription handle, refCount }
   sole writer: subscription push. Lifecycle = refcount:
   referenced by a pane -> subscribed; zero -> delayed unsubscribe (keep-warm ~30s, to avoid drag jitter)

(2) LayoutLayer -- layout, unaware of session content
   panes: [{ paneId, sessionKey | null, size }]   (1-4 panes in 1-D splits to start,
   persisted -> the whole multi-screen workbench restores after refresh; model extensible to a tree)

(3) FocusLayer -- interaction routing
   focusedPaneId single value (the only "current" in the whole app)
   global shortcuts (stop/send/switch pane) always route to the focused pane
```

Focus points to a Layout pane, the pane points to a Data sessionKey, and Data is unaware of the other two. **No component may read a "global current session"; the concept does not exist**, only "the session my pane is bound to".

```text
<SessionPane paneId sessionKey>          reads data via SessionPaneContext inside the tree
  +-- PaneHeader   (title/status dot/close, split)
  +-- Timeline     (virtual scroll, consumes store.rows, row-level memo)
  +-- QueuePanel   (consumes projection.queue)
  `-- Composer     (consumes projection.inputRouting + actionAvailability)
```

The only things panes share are the SessionDataLayer and the one connection beneath (multiplexed by topic, not one per pane). Opening a new pane is one `subscribe(base=none)`, the same path as refresh or a new device.

### Ownership of local UI state

| State                                                 | key                            | Reason                                                                                                   |
| ----------------------------------------------------- | ------------------------------ | -------------------------------------------------------------------------------------------------------- |
| Scroll position, collapse state, follow-bottom toggle | paneId                         | Two panes view different positions of the same session                                                   |
| composer draft, staged attachments                    | sessionKey                     | A draft belongs to "what I want to say to this session"; survives changing panes                         |
| side pane tabs                                        | workspaceKey                   | Browser/Git/Preview tabs are auxiliary space of the same workspace; not destroyed on conversation switch |
| side pane expand/collapse preference                  | workspaceKey + sidePaneOwnerId | After the user collapses a conversation's side pane it stays collapsed on return                         |

### Split rules

1. **The same session may appear in several panes**: store shared and readonly; the second pane is just one more view (read history while watching new output).
2. **Closing a pane does not stop the session**: it only unsubscribes the view and the session keeps running in the CLI (the same principle as "the CLI keeps running when the web page closes").
3. **Activity awareness of invisible sessions uses a lightweight channel**: sidebar phase/status dot/permission/userInput attention subscribe to the conflated sessions-index summary (latest state, naturally bounded), not full rows for a status mark; unread `unreadAt` belongs to tasks-index membership and is not derived from activity time.
4. **Dangerous operations such as stop always act on an explicit pane**: shortcuts go to the focused pane, buttons to their own pane; there is no ambiguous "act on the current session".

### Visibility QoS

Subscriptions carry a visibility hint (`foreground / background`) and the CLI's per-subscriber flush buffer tiers by it: the focused pane gets the smallest batching window and the highest drain priority; non-focused panes get a larger window; sidebar summaries only send sessionControl conflation. This is not a new mechanism; pane visibility is just one input of the existing priority scheduling ([05-transport-and-backpressure.md](./05-transport-and-backpressure.md)).

### Boundary decisions

- **Empty pane / new session**: a pane may bind `null`, showing the new-session composer; the first send creates the session and binds in place (the protocol `draft` phase).
- **Cross-workspace split**: phase 1 was only within one workspace. sessionKey already contains the workspace and the data model supports it, but cross-workspace needs the UI shell to hold multiple host connections (`Map<workspaceKey, Connection>`). Phase 2 is planned as a "multi-pane cross-workspace workbench" (binary split tree, 1-4 panes + `workspaceConnectionRegistry` reusing connections per `endpointKey + workspaceKey`); design spec: [v4-split-pane-workbench.md](../v4-split-pane-workbench.md).

### Acceptance

Performance baseline: **4 panes streaming simultaneously with no dropped frames in interaction**. Matching e2e: two panes stream independently without interference; stop in pane A stops only A's bound session; after refresh layout + each pane's content + watermark fully restore; two panes of the same session show strictly identical content with independent scroll.

## Rendering: virtual scrolling + row-level updates

1. The message list uses `@tanstack/react-virtual` (already a repo dependency; `GitPane.tsx` and workspace-grouped-tasks are reference implementations). The old chat area had zero virtualization and rendered all via `map`, relying on `content-visibility: auto` as a fallback (`ChatConversationContent.tsx:41`).
2. The virtualization unit is the projection's `rows[]`: rows are computed in the CLI with stable keys, and the client no longer recomputes turn grouping per frame (the old `buildChatMessageTurnGroups` plus the three-layer memo patch chain is obsolete).
3. Streaming updates patch only the matching row, combined with row-level memo, so multiple streaming panes do not affect each other.
4. **Row-level subscription**: components subscribe to their own row by rowId (selector granularity = row); the list container subscribes only to rows length/window changes.
5. **No second layer of message merging on the client**: the only merge point is the server flush (the frequency budget chain in [05](./05-transport-and-backpressure.md)); the client applies a frame as it arrives, at most aligning render cadence to rAF.
6. **Markdown re-parsing of long-text rows is an owned render hot spot**: a streaming row appends every 30 ms and must not re-run a full markdown parse each time: use incremental streaming parsing / re-render only tail blocks (`packages/stream-animate` is the ready landing place); off-screen rows are not rendered as a fallback. This is the render layer's second performance acceptance item alongside virtual scrolling.
