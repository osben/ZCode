# Deletion and Reuse List (Historical Execution Record)

> **Status: file-level trail of the V4 hard-cut migration.** Old paths, line counts and "to delete" in the tables come from the 2026-07-05 to 2026-07-06 execution context; many files have since been deleted, re-homed or shrunk and the tables cannot be used to judge current dependencies. Current code entry points and remaining boundaries: [README.md](./README.md) and [06-ui.md](./06-ui.md). Full pre-compaction file lists: `git show b8876e8b:docs/v4-refactor/11-deletion-plan.md`.

The execution path at the time: delete the UI chains that hold/derive conversation state, let the CLI projection supply the facts, and switch directly without dual write. This document keeps the deletion rationale, the waves and the close-out ledger, to explain why the existing V4 modules are layered as they are.

The single criterion:

> **Code that "holds or derives conversation state" is deleted (the responsibility moves into the CLI projection); pure display code that "takes data and draws it" is kept and changed to consume rows.**

Related: [06-ui.md](./06-ui.md) (new store / SessionPane design), [09-protocol-schema.md](./09-protocol-schema.md) (new protocol schema), [08-phasing.md](./08-phasing.md) (the original phasing; this list executed the "delete and rewrite" path, equivalent to moving Phase 3/4's deletions earlier with no old-chain dual-write period).

## Wave 1: UI chat state management and event assembly chain (delete entirely)

Replacement: a per-session read-only projection store + `apply()` (see 06-ui.md and 09 §delta), expected new code under 1000 lines. Scope (about 36k lines deleted in total):

1. The zustand conversation store (`packages/ui/src/store/zcodeSessionStore*`, ~5,072 lines: task slice, workspace slice with the "current task" single value, types, selectors, renderer-local queue slice (queue now lives in CLI projection), navigation, entry).
2. The whole chain "reduce events into a message timeline" in lib (~4,680 lines): `zcodeChatMessages.ts` (3,089, the root of the disease: a renderer-side event reducer), helpers/cleanup, timeline identity/runtime/groups, turn steer queue, `taskStreamChunkBatch` (client batching; the new architecture forbids a second merge layer, the only merge point is the CLI flush), `taskStreamMirrorGap` (mirror gap compensation; the only gap action becomes resubscribe), and runtime derivation/merge/monitor files (~1,500 lines, all replaced by the projection's `control`/`availability`).
3. The stream-event hooks chain (~6,970 lines): `useTaskStreamEvents`, `taskStreamEventHandlers/SnapshotSync/TerminalHandlers/ConfigUpdate/Helpers`, `taskSnapshotRuntimeStateSync`, `useTaskRestore`.
4. Chat business hooks (~7,950 lines, rewritten thin on the new command/projection model): `useZCodeChatSendPrompt` -> `sendText` command + optimistic overlay (expected <200 lines); `useChatComposer` (input routing startNow/enqueue/guide reads projection.inputRouting; editor interaction folds into the kept input components); `useZCodeChat` -> `subscribe(base)`; `useZCodeChatHistoryActions` (fork/edit as commands, availability reads row.actions); `useChatTaskControlActions` (stop as a command, availability reads projection.control); `useWorkspaceActiveTaskState` (the "global current task" concept does not exist in the new architecture, only pane binding) and small helpers.
5. The ChatView assembly layer (~11,540 lines, rewritten as SessionPane): `ChatView.tsx` (singleton assumption), `ChatView/` (47 files: turn assembly, placement, scroll restore, timeline diagnostics all deleted; small pure-display parts such as `ChatScrollToBottomControl`, `FlipMetricValue` may move into the new pane after evaluation).
6. Single-value navigation/cache stores (rewritten, not kept as-is): `tabStore.ts` (the `activeTabId` single value is a direct obstacle to split panes; rewritten as Layout/Focus layers), `taskQueryCacheStore.ts` (replaced by the `sessions-index/<workspace>` topic), and the remote parallel caches (`remoteWorkspaceSessionStore` / `remotePinnedTaskStore` / `remoteTimelineTaskStore`, no reason to exist after multi-end convergence).

> **M5 (2) wrap-up (2026-07)**: the last residue of this wave was cleared. `zcodeChatMessages.ts` (3,089) + `zcodeChatMessageHelpers.ts` (781) were deleted (the TaskChatMessage/TaskChatToolCall types re-homed to `lib/taskChatMessageTypes.ts`, consumed type-only by retained components such as ToolCallBlocks/PermissionDialog/treemapping); bot broadcast message replay is now carried by the v4 conversation projection; TreemappingPane reads snapshot rows. The three zustand store slices were not deleted wholesale but lost all their dead surface (taskSlice 1,752->906 / workspaceSlice 1,223->811 / types 860->480 / selectors 403->312). What remains is the **non-conversation-content** live surface, with its blocker and deadline:
>
> 1. `activeTaskId` + navigation history: v4 has no native active-session surface (at the pane layer only split has paneLayoutStore); deadline = shell selection state moves to v4.
> 2. Sidebar optimistic list/unread (optimisticTaskListByTaskId / taskUnreadByTaskId / taskListCache / taskListVersion / groupedDraftTask): sessions-index carries no pin/archive/unread/optimistic creation, still fed by legacy zcodeTaskService (sqlite) + this store's optimistic layer; deadline = membership surface completed.
> 3. Runtime state taskRuntimeByTaskId + taskUiByTaskId (permission/question pending): bot broadcast and remote shard multi-end scenarios still write it (useBotBroadcastEffects / remoteWorkspaceSessionRuntime / useGlobalTaskList); deadline = bot/remote surfaces become v4 subscriptions.
> 4. Config surface (configOptions / slashCommands / taskConfigOptionsByTaskId / model switch state): the workspace-config topic has no renderer hook yet and the model catalog of V4ComposerToolbar still reads this store (the file header notes the deadline = config surface moves to v4).

## Wave 2: `@zcode/protocol` rewrite

1. Protocol body: `packages/shared/src/zcode-protocol/index.ts` (3,788) deleted and rewritten. The new protocol = topic frame envelope + ConversationSnapshot/Row/Delta + command/query (see 09, 10), holding **only schema types + coalesce pure functions; no runtime in this package**.
2. Derived types inside shared (shadows of the old protocol), handled with it: `task-realtime.ts` (delete: owner/mirror/deliveryKind semantics vanish entirely), `zcode-task-types.ts` (delete / fold into the new schema: task->session concept convergence), `zcode-session-visible-content.ts` (delete: "visible content" derivation moves into the CLI projection), `zcode-session-task-status.ts` (delete: state derivation moves into projection.control), `zcode-agent-model-state.ts` (evaluate: delete if model state enters projection region A).
3. Blast radius (consumers that must change with the rewrite): `apps/zcode-cli/packages/bootstrap/src/zcode-protocol-entrypoint.ts` and the CLI-side protocol ingress/egress (now produce ProductProjection frames + command inbox, the landing point of 02/03); CLI-side per-client seq state tables such as `protocolEventSequences` (moved up/refactored per 01-topology); related tests (`packages/shared/test/zcodeProtocol.test.ts`, `apps/zcode-cli/packages/bootstrap/tests/zcode-protocol*.test.ts`) rewritten with the new schema, with the golden test (same event sequence x two profiles with identical end state) as the new test backbone.

## Execution order and guardrails

> The authoritative execution pacing is the M0-M5 milestones of [08-phasing.md](./08-phasing.md) (steps 1-6 here correspond: step 1 ~ M1, 2 ~ M2, 3-4 ~ M3, 5 ~ M4/M5). Wave 1 deletion happens on the M3 branch; waves 2/3 happen in M5.

1. **Establish the new protocol first**: land the new `@zcode/protocol` schema + coalesce pure functions + type tests per 09/10 (old and new coexist; old code not yet deleted).
2. **CLI side produces the projection**: ProductProjection reducer + command inbox + `subscribe(base)` (02/03/04), all golden tests pass.
3. **New UI skeleton**: SessionDataLayer + `apply()` + single-pane Timeline (virtual scroll) first run a "subscribe -> render -> send" vertical slice.
4. **Delete wave 1**: once the new slice is usable, delete the old UI chains in one batch (1.1-1.6 above), stripping store references from retained components in the same batch.
5. **Delete waves 2/3**: delete the old protocol body and derived types, converge the transport layer; delete `zcodeTaskServiceAdapter` last.
6. After each deletion wave run `pnpm typecheck && pnpm lint`; conversation e2e follows the "E2E and test asset disposition" section above: case-catalog semantics unchanged, old specs downgraded to manual-review explicitly (never silently skipped), new evidence rebuilt on the golden-test / WDIO dual track.

Risk note: this path abandons the dual-write period of 08-phasing, and between deleting wave 1 and the new UI being usable desktop chat is unavailable, so **the work must be completed on an independent branch up to a usable vertical slice before merging**; mobile remote and web keep the old chain untouched until wave 3 is done.
