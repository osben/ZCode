# V4 Command Model: Current Spec

Updated: 2026-08-25

All conversation write operations enter the CLI through `v4/command`. The schema is in `packages/shared/src/zcode-protocol-v4/command.ts`, admission in `apps/zcode-cli/packages/bootstrap/src/zcode-protocol-v4/command-inbox.ts`, business handlers in `apps/zcode-cli/packages/bootstrap/src/zcode-protocol-v4/commands/handlers/`.

## Envelope and single writer

```text
client command
  { commandId, clientId, sessionId, baseRevision?, baseLogEpoch?, type, payload, issuedAt }
       |
       v
CLI CommandInbox
  -> schema / epoch / revision / row target / product guard
  -> per-session FIFO admission
  -> native V4 handler
  -> ACK
  -> canonical fact + projection delta
       |
       `-> all subscribers converge in the same authoritative order
```

1. `commandId` is generated by the client and stays the same on retry.
2. `issuedAt` is for telemetry only and takes no part in ordering or conflict resolution.
3. CAS commands must carry `baseRevision`; row-targeting commands must also carry `baseLogEpoch`.
4. `createSession` has `sessionId` of `null`; the successful ACK returns the real session id.
5. Clients propose intent; the CLI is the only writer. Commands from different clients are serialized in the CLI's actual admission order.

The full command set is `commandPayloadSchemas`, currently: session create/delete/rename, input and goal, stop, compact, fork/edit/retry/file rewind, queue operations, interaction answer and snooze, model/mode/followup switch, goal pause/resume and background work cancel. Documents must not present legacy `session/*` operations as V4 UI write entries.

## ACK semantics

ACK status: `accepted` (accepted by the current CLI), `rejected` (schema, guard or target disallowed), `stale` (epoch/revision/row target expired), `duplicate` (same command already has a result), `noop` (legal but fact already in target state), `failed` (execution failed).

An ACK is not a projection snapshot and does not replace later topic updates. Long-term UI state must converge via the projection; `sourceCommandId` aligns authoritative rows/markers with the local overlay. Commands needing immediate navigation or result display (fork, create session, interaction) may return a minimal result in the ACK `result`.

## In-memory inbox and persisted facts

CommandInbox itself is in-memory: in-flight and live input are always pinned; settled ACKs go into a bounded per-session LRU; a CLI restart restores no "pending command inbox table" and never blindly replays commands.

Cross-restart idempotency relies on persisted facts the command already produced, not a persisted inbox: (1) `sourceCommandId` on the transcript message anchor; (2) `sourceCommandId` on the timeline part; (3) child/fork command fact; (4) terminal states promoted/cancelled/discarded/failed of the `session_input` ledger.

`v4/commands/query` first checks in-memory pinned/LRU, then looks up exactly by the sources above. A miss returns `unknown`; the client shows it and lets the user decide whether to resend. Silently resending side-effecting commands (stop, fork, input) is forbidden.

`session_input` is the input lifecycle ledger, not a recoverable execution queue. `startNow`, `queue` and `guide` all durably admit before execution; promotion and user-message persistence are atomically linked. On CLI restart an input still `admitted` becomes `discarded(session_resumed)` explicitly, so input never silently evaporates or auto-reruns.

## Queue and blocking interactions

Accepted running input is carried by the CLI runtime command queue; the renderer no longer builds a second busy queue. A queue item keeps `sourceCommandId`, attachments, client, admission order and dispatch state; desktop and mobile share facts but still follow the continuous/replayable delivery boundaries.

permission, elicitation and AskUserQuestion are projected as `pendingInteractions`. Clients answer with `resolveInteraction`; the first answer wins, duplicate or late operations close idempotently. owner/lease still handles cross-host command routing, blocking responses and stale-run protection and must not be removed because shared-host attachment exists.

### Prompt admission and turn scheduling

`CommandInbox` owns per-session command FIFO, idempotency and `session_input` admission; it does not decide whether the runtime can start a turn. That decision is made atomically only by the corresponding `AgentRuntime` instance:

```text
Session A                         Session B
  CommandInbox -> Core admission    CommandInbox -> Core admission
       idle -> reservation/start         idle -> reservation/start
       busy -> existing Core FIFO        busy -> existing Core FIFO
```

1. A session has at most one foreground turn at a time. `activeTurn`, `activeTurnStartReservation`, `activeForegroundExecution`, runtime command drain and existing runtime commands all belong to Core's busy boundary; Bootstrap must not query them and then decide start vs queue itself.
2. Different sessions use their own `AgentRuntime` state and runtime FIFO and can run in parallel; one session's stuck provider/network cannot block another.
3. Core admission returns a `started`, `queued` or `rejected` receipt. `started` only means a reservation is established and the prompt command entered that runtime's execution queue; model execution, the `TurnStarted` event and projection updates continue asynchronously through the existing event stream.
4. `TurnStarted`'s `inputId/sourceCommandId` correlates later events; `messageId` may be absent from the initial ACK. Projection commit is neither the boundary of the prompt admission ACK nor the fact of session busy/idle.
5. Reservation, active turn and foreground execution are released uniformly in the Core turn's `finally`. The Bootstrap controller must not be used to infer Core is idle; Stop calls Core's `stopActiveForegroundExecution` first.
6. Desktop `desktop-continuous` keeps consuming Core's live event stream; mobile `web-remote-replayable` recovers the same Core queue via snapshot/gap. They differ only in delivery/recovery semantics; neither keeps its own prompt queue, and queue state is not pushed down to relay or renderer.

## Optimistic overlay discipline

1. The overlay exists only in the initiating client's local UI and never enters the projection store.
2. The overlay is superseded only by authoritative facts keyed by `commandId`; it is not merged with authoritative rows.
3. The initiating client must also consume its own subscription frames.
4. The `accepted|duplicate` ACK of `sendText` only starts one projection confirmation window: it closes when a queue item or real-user `userInput` row with the same `sourceCommandId` appears; on timeout it reuses only the current owned subscription's same-sub resync. Fabricating messages, building a second queue or auto-replaying the command is forbidden.
5. On disconnect the draft is kept but no offline command queue is accepted.
6. Transport recovery must not change a command's admission/queue order.
