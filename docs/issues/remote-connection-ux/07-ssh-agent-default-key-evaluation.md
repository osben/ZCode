## Comments

### 2026-09-27 — Evaluation conclusion, awaiting user decision

**Recommendation: schedule in phases and keep the existing ssh2 Transport.** Phase one connects the macOS/Linux Unix agent, the Windows OpenSSH agent, ordinary default private keys and explicit `IdentityFile`, estimated at **7-10 person-days**; Pageant is an optional second phase adding **1-2 person-days**. This is not just adding an `agent` parameter: the main work is authentication selection, config semantics, Profile persistence and the recovery gate. All of this is a recommendation; implementation is not approved.

"One-click connection" is limited to: the target is reachable, an ordinary public key is authorized by the server, and either the agent can already sign or the file private key needs no passphrase / its passphrase is saved. When a first passphrase entry, agent confirmation, installation or identity confirmation is needed, the flow continues into the existing wizard; full equivalence with the system `ssh alias` is not promised.

### External capability basis and platform differences

Conclusions come from official documentation and source; the lock file and the locally loaded version are both `ssh2 1.17.0`; no three-platform real agent / packaged app verification was run.

- **config semantics cannot be satisfied by adding one socket field.** `IdentityAgent` overrides `SSH_AUTH_SOCK`; `none` disables the agent, the literal `SSH_AUTH_SOCK` and `$VAR` reference an environment variable, and paths also allow `~`, tokens and `${VAR}` expansion. `IdentityFile` may appear several times and accumulates, and also allows `none`; without a local private key a public key file can select the same identity in the agent. `IdentitiesOnly yes` filters agent public keys by the configured identities and must not iterate all agent keys; where these semantics are not supported, report a compatibility problem explicitly. Basis: [OpenSSH ssh_config](https://man.openbsd.org/ssh_config#IdentityAgent), [IdentityFile / IdentitiesOnly](https://man.openbsd.org/ssh_config#IdentityFile).
- **Default files should be an explicit candidate set.** OpenBSD 7.7 defaults are `id_rsa`, `id_ecdsa`, `id_ecdsa_sk`, `id_ed25519`, `id_ed25519_sk`; the current upstream manual also lists `id_mldsa44_ed25519`, and platform-shipped versions differ. Phase one should auto-probe only `~/.ssh/id_ed25519`, `id_ecdsa`, `id_rsa`, with the order as a product contract; arbitrary `id_*` must not be globbed into usable private keys; `*_sk`, new algorithms and certificates must be listed as unsupported boundaries. Basis: [pinned-version manual](https://man.openbsd.org/OpenBSD-7.7/ssh_config.5#IdentityFile), [current upstream manual](https://man.openbsd.org/ssh_config#IdentityFile).
- **The existing library has authentication orchestration.** `authHandler` of `ssh2 1.17.0` can return `publickey` (each with its own `key/passphrase`), `agent` or `password` per attempt; the default order is none → password → private key → agent, so the default cannot express "non-interactive first, prompt for password last". A top-level `privateKey` is parsed before connecting and an encrypted key without a passphrase throws; an agent-first candidate design must avoid early parsing of that key blocking the agent. Basis: [pinned-version API](https://github.com/mscdex/ssh2/blob/v1.17.0/README.md#client-methods), [client.js](https://github.com/mscdex/ssh2/blob/v1.17.0/lib/client.js).
- **The agent does not fill in all algorithms.** In this version the agent identity list goes through `parseKey` and unsupported types are skipped; binary public key parsing accepts only RSA, DSA, ECDSA and Ed25519, not `sk-*` or OpenSSH `*-cert-v01@openssh.com` types. FIDO security keys and agent certificates therefore cannot be listed in phase one, and the regex matching of file certificates does not mean complete certificate authentication. Basis: [agent parsing and skip logic](https://github.com/mscdex/ssh2/blob/v1.17.0/lib/agent.js#L539-L585), [keyParser support range](https://github.com/mscdex/ssh2/blob/v1.17.0/lib/protocol/keyParser.js#L1249-L1406).

Suggested authentication policy rules for the implementation ticket:

1. **Compatible with existing explicit choices.** Password mode still forbids implicit agent/default key; an explicit single private key keeps its path and passphrase semantics. Only auto enters the config/agent/default candidate flow; `IdentityAgent none` must override the environment fallback and must not accidentally re-enable the agent through `undefined`.
2. **Candidates have source and order.** Under auto, first try agent identities or silently usable files corresponding to configured identities; `IdentitiesOnly yes` strictly filters out other agent keys. Only when no identity is configured and not explicitly disabled is the ordinary default file allowlist above used; configured order takes priority, and a file/agent matching the same public key counts as one identity. For unrestricted agents, other identities are tried in a deterministic order with a cap, so hosts with a low `MaxAuthTries` do not exhaust the attempts before a valid key.
3. **Encrypted private keys take two paths.** When the agent already has the same identity loaded, only signing is delegated and ZCode does not need to save its passphrase. For direct file authentication, read the saved passphrase first; a missing/wrong passphrase enters an explicit supplemental credential flow and is not mistaken for the SSH login password. Automatic candidates should not repeatedly pop a passphrase dialog per file: exhaust the other silent candidates first, then let the user choose the identity to unlock.
4. **Passphrases are isolated per candidate.** One passphrase reference per Profile does not cover several encrypted keys. Keep using `ICredentialService` with an independent reference for the selected identity, and verify ownership by canonical path plus an obtainable public key fingerprint; never broadcast one passphrase to all keys. Old single-path references stay readable. Save timing keeps the existing "credential actually used" semantics; changing key, cancel, switching authentication mode and failure rollback must handle old references. The existing store is reusable, but this ticket does not upgrade it to a system keychain and does not promise to read Apple `UseKeychain` items.
5. **Silent and manual are separate.** Manual connection may prompt for a passphrase or wait for agent approval; auto recovery must keep the non-interactive requirement of [R3 §7.1](../../architecture/r3-source-server-remote-architecture.md). The ordinary agent protocol has no generic "signing never pops a dialog" pre-check: locked agents and confirmation constraints such as `ssh-add -c` must be listed as scenarios without a silent guarantee, and a timeout must not simulate confirmation success. If phase one cannot guarantee an agent is non-interactive, stop at a user-action result and do not trigger that signing path automatically.
6. **Explicit compatibility range.** Phase one supports ordinary RSA/ECDSA/Ed25519 identities; FIDO/security-key, certificates, PKCS#11, ProxyJump/ProxyCommand, full system ssh config compatibility, Keychain auto-unlock, and auto-start / privilege-escalated agent configuration are not in the estimate. The current alias-reading entry can be reused but must report these unsupported conditions; it must not advertise that every Host reachable from a terminal connects in one click.

Suggested timeline and ownership (to be implemented; not a new runtime):

```mermaid
sequenceDiagram
    participant UI as Desktop wizard / mobile remote entry
    participant H as Local Host: Directory / Manager
    participant R as Local auth resolution
    participant B as SSHBackend / agent
    UI->>H: connect Profile (or manual temporary credentials)
    H->>R: current policy + local config/env + interaction mode
    R-->>H: ordered candidates / credentials needed / unsupported
    H->>B: try candidates within the current operation
    B-->>H: authenticated / rejected / user action needed
    H->>H: on success continue the original Source handshake, identity confirmation and credential commit
    H-->>UI: original state events and classified errors
    Note over H,B: cancel invalidates this operation; late signing/connection results must not be persisted or publish online
```

config, home, socket/pipe and file reads all resolve on the **controlling machine**, never looking for keys on the remote Source or the phone's file system. The phone keeps shared-host attachment; task recovery after authentication stays desktop `continuous` and mobile `replayable`, with no change to session, queue, snapshot/gap or provider-delivery protocol, and SSH credentials are not added to Provider Provisioning.
