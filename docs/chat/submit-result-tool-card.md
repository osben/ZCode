# submit_result Tool Card ("已提交结果")

## Release state

Design finalized; implemented in commits following this spec. Prior facts:

- The actor side pane is not a separate transcript renderer: `WorkflowActorSessionSidePane` mounts a nested read-only `SessionPane` (`packages/ui/src/app-shell/WorkflowActorSessionSidePane.tsx`; live stream, cold recovery and review all use the existing SessionPane chain). So `submit_result` arrives as an ordinary v4 `toolCall` row rendered by the main session's ToolCallBlocks registry.
- `submit_result` is not in the UI's known tool table (`ZCODE_KNOWN_TOOL_NAMES` in `packages/shared/src/tool-identity.ts` ends at `CreateWorkflow`), so it resolves to family `"unknown"` and `FallbackToolCallBlock`: wrench icon, the capitalized label "Submit_result", and a bare `<pre>` of `JSON.stringify(…, null, 2)` of the whole toolCall object (`renderers/fallback.tsx`, using the off-token `text-ui-xs`).
- The payload is entirely on the input side: the tool output schema is only `{status: "accepted"}` (`apps/zcode-cli/packages/contracts/src/tools/submit-result.ts`); the input is the single key `{result: <unknown>}`. The per-ask JSON Schema travels in the instruction tail, not the tool declaration (the declaration is frozen to keep the prompt cache).

User ruling (2026-09-01): the rejected-state card is a non-expandable flat row. The per-field violation panel is removed entirely (including `parseSubmitResultViolations` and the `violationsHeading` entry); the rejection text stays reachable through the failed-state `statusTooltip` (copyable on hover). Accepted/stopped expand behavior is unchanged.

## Boundary decisions

| Boundary                    | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Route registration          | `packages/shared/src/tool-identity.ts`: add the literal `"submit_result"` to `ZCODE_KNOWN_TOOL_NAMES` and map it to family `"workflow"` in `TOOL_FAMILY_BY_NAME` (the Record is total, so TypeScript forces the pair). `resolveRenderer.ts` dispatches the new renderer by `identity.toolName` inside the `workflow` case. Matching is case-insensitive already (`normalizeZCodeToolName` uses a lowercase table), but the underscore must be literally present: the wire name is `submit_result`, the only snake_case tool in the repo. No new family (precedent: `RespondToCoordinator` in the `message` family, dispatched by name within the family); the CLI side is not renamed. |
| Data source                 | The renderer reads `toolCall.input.result` directly. The accepted output is always the uninformative "The result was accepted." and is not read. `input` is already a parsed object via `toolCallRowAdapter.ts`; the first streaming frame may be `{}` or half-built (`inputPreviewComplete: false`). No new display union member: that would need contract + v4 + UI parser + producer in lockstep (missing one silently degrades), while the payload is already entirely on the input side.                                                                                                                                                                                          |
| Result normalization        | A string first gets one tolerant `JSON.parse`; if it parses to an object/array use the parsed value, otherwise treat it as prose. This is the read-side mirror of the engine behavior (`engine/scheduler.ts` documents that real models often serialize `result` as a JSON string and does the same single tolerant parse; the UI's `toRecord` in `respond-to-coordinator.tsx` is the same idiom). Normalize only at read time, never rewrite data, no multi-level recursive parse.                                                                                                                                                                                                    |
| Body: prose branch          | A normalized string renders as body text (pre-wrap, semantic tokens, not mono), because human text is prose (the same DESIGN.md argument `WorkflowRunSidePane.tsx` cites for run error copy: mono is for paths/commands/code/identifiers/terminal data). No markdown rendering (the result string has no markdown contract).                                                                                                                                                                                                                                                                                                                                                           |
| Body: JSON branch           | Object/array/other non-string -> `JSON.stringify(…, null, 2)` in `CodeBlock language="json"` with the `mcp.tsx` container idiom (`max-h` scroll + `rounded-xl border border-border bg-card`). CodeBlock honors the user's code font size setting (DESIGN.md), and this also fixes the fallback's off-token `text-ui-xs` (DESIGN.md reserves xs for badges/counters). No hand-built `<pre>`.                                                                                                                                                                                                                                                                                            |
| Collapse and streaming gate | Collapsed by default (`canToggle`). `hasDetails` gate: the expand affordance / `renderContent` exists only when the `result` key is present in `input` (verbatim `send-message.tsx` idiom). The collapsed header shows a one-line truncated summary (the normalized result compressed to one line). `ToolSnapshotFieldNotice` is kept (fixed pairing of every non-fallback renderer with ToolLayout). No expand entry for an empty first frame; do not use `summaryAction` (it short-circuits the whole body).                                                                                                                                                                         |
| Label by phase              | New i18n block `chat.toolCall.submitResult.*`, both locales next to the `respondToCoordinator` block: completed -> `submitted` "已提交结果" / "Result submitted"; pending/in_progress -> `submitting` "正在提交结果" / "Submitting result"; failed -> `rejected` "提交被驳回" / "Submission rejected"; stopped -> `stopped` "提交已停止" / "Submission stopped". A missing key silently renders the bare key (`messages[id] ?? id`), so both locales must land in the same commit. Do not reuse respondToCoordinator keys (different semantics).                                                                                                                                       |
| Rejected-state body         | When `failed` the card is a non-expandable flat row: no toggle, no body. The rejection text stays reachable through the failed-state `statusTooltip`. The UI does not restate the schema.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Test ownership              | New `packages/ui/test/submitResultToolCallBlock.test.tsx` (render each state) + extended tool-identity assertions in `packages/shared`. No existing e2e fixture contains a submit_result row; unit tests build the toolCall themselves; e2e is out of scope.                                                                                                                                                                                                                                                                                                                                                                                                                           |

## Data flow

```
actor session (real persisted session)
  → v4 toolCall row {toolName: "submit_result", input: {result: <JSON | JSON-string>}, output: {text: "The result was accepted." | violation text}}
  → toolCallRowAdapter (input passed through; streaming frames rebuilt via preview, inputPreviewComplete=false)
  → resolveToolCallIdentity: ZCODE_KNOWN_TOOL_NAMES hits "submit_result" → family "workflow"
  → resolveRenderer: workflow case dispatches by toolName → SubmitResultToolCallBlock
      label: phase → chat.toolCall.submitResult.{submitting|submitted|rejected|stopped}
      body (behind hasDetails gate, collapsed by default):
        normalize(input.result): string that parses to object/array → parsed value
        ├─ string → prose body (pre-wrap, not mono)
        └─ object/array/other → CodeBlock language="json" (mcp.tsx container idiom)
      failed branch: non-expandable flat row; rejection text via failed-state statusTooltip (no expanded body)
```

## Invariants

- Pure UI projection: writes no state and changes no CLI/protocol/display union; one fix in the registry covers both the main session and the actor side pane.
- Normalization happens only at read time: `JSON.parse` at most once (same tolerance as the engine); failure means treat as string; never throw and break the card.
- Empty/half-built streaming frames never offer an empty-panel expand entry (`hasDetails` gate).
- Both locales' `chat.toolCall.submitResult.*` land in the same commit.
- Mono is for data (JSON branch); human text (prose branch) uses body tokens.
