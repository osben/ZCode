# Goal Verification Divider

Goal-mode completion verification is shown in the conversation as a compact synthetic divider. It is a post-turn boundary, not an assistant worklog item, so it is never folded into the "worked for xxx" history area. Clicking the divider opens the summary panel. The divider text is generated by the UI from structured timeline metadata; verifier text is not rendered as assistant message content.

## Visible states

- `started`: verification is running.
- `completed` with `passed: false`: goal incomplete, the task continues.
- `completed` with `passed: true`: goal complete, the task ends.
- `failed_closed` with `passed: true`: verifier infrastructure failed open; goal complete, the task ends.
- `failed_closed` with `passed: false`: legacy or explicit failed-closed data is treated as continuing.
- `cancelled`: the verifier was interrupted; the UI shows the interruption instead of completing the task.
- Malformed verifier JSON: the attempt is invalid, but contracts fail open to `passed: true` and preserve the parse-failure reason.

## Persistence

The source of truth is the durable goal verifier lifecycle record. Runtime emits `target_completion_verification` lifecycle events with `targetId`, `verificationId`, `status`, `goalIteration`, optional `anchorTurnId`, optional `anchorAssistantMessageId` and an optional verifier result. These facts must be recoverable after a cold restart.

The session reducer projects them into `targetCompletionVerificationTimeline`; bootstrap exposes it as `runtime.goalVerificationTimeline`; the UI restores it into synthetic assistant messages when building a task snapshot.

Normal completed summaries still come from the existing `model_complete` event with `querySource: "target_completion_verification"`. Failed-closed and cancelled lifecycles add their verification result to the summary ledger because those paths have no successful `model_complete`; failed-open records keep `passed: true`, cancelled records stay cancelled.

## Iteration ownership

- The verifier lifecycle owns the goal iteration count. A new iteration is counted only when a `target_completion_verification` lifecycle starts. User interruptions, manual "continue" prompts, normal runtime turns, TodoWrite snapshots and model-only `goal-continuation` turns never advance the displayed iteration by themselves.
- UI row identity is `goal:${targetId}:iteration:${goalIteration}`. `verificationId` is an attempt id and must not create another visible row for the same iteration. A started event and its terminal completed / failed / cancelled event update the same divider.
- The divider is anchored after the assistant output the verifier evaluates. New lifecycle events include `anchorTurnId` and, when available, `anchorAssistantMessageId`. Old data without anchors may fall back to timeline time and nearest assistant output, for compatibility only.
- When a model-only goal-continuation turn starts, the UI may create a local streaming assistant container so live chunks do not merge into the previous assistant message. It uses a UI-only stream group and must not provide `goalIteration`. If a live lifecycle event lacks `goalIteration` for compatibility, the divider falls back to the existing verifier divider count, not to assistant message numbering.
- Goal-continuation turns can reuse the original user `inputId` across automatic iterations. The projected `goal_iteration_started` event therefore carries the runtime `turnId` when available, and the UI uses `turnId` before `inputId` as the streaming boundary key, keeping adjacent iterations in separate assistant containers without changing visible input ownership or verifier-owned numbering. Mirror/replay paths without a `turnId` fall back to `inputId` or `traceId`.
- `goalStats.iterationCount` follows the same rule, but consumers distinguish the last verified iteration from the currently open one. Before the first verifier, active-goal work is iteration 1. After verifier N fails and the goal continues, subsequent work belongs to iteration N+1 until the next verifier, even if the user sends visible prompts in between.
- Todo groups describe where TodoWrite items first appeared. A todo stays under its original iteration when a later snapshot marks it complete.

## History impact

No old task history file schema change. Existing sessions keep their previous verification summaries but gain no divider rows retroactively unless the event log contains the new lifecycle events. New sessions persist the lifecycle facts, so refresh, reopening history and replayable recovery restore the same divider status.

## Remote compatibility

The divider is projected from session runtime state and synthetic timeline chunks; there is no new renderer-local queue or relay-owned task state. Desktop `desktop-continuous` keeps direct live delivery. Web remote `web-remote-replayable` restores the divider through the existing snapshot and replayable event paths; session, stream, queue and snapshot ownership stay out of the relay and main process.
