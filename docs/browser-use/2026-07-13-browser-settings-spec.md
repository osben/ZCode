# Browser settings page spec

## Summary

The settings page adds a "浏览器" (Browser) section after "索引库" (Indexing). It holds Browser Use availability and local browser data management:

1. "内置浏览器控制" (built-in browser control) reads and writes the enabled state of the official plugin `browser-use@zcode-plugins-official` directly; no second switch is added.
2. "导入 Chrome 登录状态" (import Chrome login state) sits on the same card as "开启内置浏览器控制" in the "浏览器控制" group, as the first companion action after enabling control. The "浏览器数据" (browser data) group keeps only destructive clear actions. User-facing copy leads with the user benefit (AI can open logged-in sites directly) and never uses internal data structures (Cookie / LocalStorage / Profile) as the main description.
3. **Import on macOS/Linux** first confirms an executable Chrome/Chromium exists on the machine, then discovers Profiles. If none is installed it immediately returns `chrome_executable_not_found` and shows "Chrome 未找到" (Chrome not found), touching no Profile and modifying no built-in browser data. Executable discovery covers, in order, an explicit environment variable, running processes, system registration (macOS Spotlight app registration, Linux XDG desktop entry/PATH) and standard directories, supporting non-default install locations; there is no whole-disk scan. After the install is confirmed, the source is chosen in the order `Local State.profile.last_used` -> `Default` -> the only usable Profile, and one click performs a one-time import of Cookies and LocalStorage. There is no Profile selector, no continuous sync, and the password store is not read.
   - **Windows desktop** temporarily renders no import row but keeps clear-cache and clear-all. The existing App-Bound `v20` native import implementation, manual build script and tests are kept; once the entry returns it still follows the explicit-UAC, one-time `LocalSystem` service and fail-closed boundary. Default Windows development, CI and release builds must not compile, sign or package the helper; only explicitly setting `ZCODE_ENABLE_WINDOWS_BROWSER_IMPORT=1` restores the helper asset chain, and that build switch alone does not restore the UI entry.
   - **macOS**: when Chrome Safe Storage keychain access is requested, an explicit user denial or cancel must terminate the whole import, write no Cookie, not start the LocalStorage import and show an unauthorized hint.
   - **Linux** `v11` cookies are decrypted by a same-brand Chrome/Chromium helper through the current desktop session's Libsecret/KWallet; ZCode does not read the keyring itself.
   - Import does not refresh open pages; the user refreshes manually or opens a new tab to read the new data. Recoverable Chrome session Cookies stay recoverable in the built-in persistent partition so login state is not lost right after a ZCode restart.
4. "清除浏览器缓存" (clear cache) clears HTTP cache, Cache Storage, Service Worker and shader cache of the built-in browser partition, keeping Cookie, LocalStorage and IndexedDB.
5. "清除全部浏览器数据" (clear all) is a secondary dangerous action that, after a second confirmation, clears all site data of the built-in browser partition.
6. The Browser data action buttons use the same `lg` size as the Terminal font action controls at the same settings level: height `32px`, `rounded-lg`; different actions are still distinguished by outline/destructive semantics, not by size.

The built-in browser partition stays `persist:zcode-embedded-browser`. Data management is a desktop host capability; the Web/mobile settings page keeps the same information structure with the actions disabled and a hint to use the desktop app, and creates no new Browser Use runtime or business state outside relay/desktop main.

## Domain scope and high-risk cross-products

Main domains:

- Plugin / skill / MCP: the official plugin is the only source of the switch state.
- Desktop lifecycle / native capability: Chrome Profile discovery, system credential access and Electron session clearing run only in desktop main.
- Persistence / auth: Chrome Cookie, LocalStorage and `persist:zcode-embedded-browser` are different persistence sources; Cookie/LocalStorage values and decryption material must never be recorded.
- Theme / locale / responsive: the settings page reuses existing Settings card, Switch, Button, Dialog and i18n, compatible with the narrow icon sidebar.

High-risk cross-products:

- Plugin switch x existing draft / running session: only later capability resolution follows existing plugin semantics; running tasks are not terminated.
- Chrome running x SQLite WAL: support the new `<profile>/Network/Cookies` and the old `<profile>/Cookies`; prefer a consistent snapshot from a read-only connection via the SQLite Online Backup API. If Windows does not allow a new connection to join the running Chrome's WAL/SHM lock protocol, copy the main DB and the persisted `-wal` (never the `-shm`, which holds no database content and may be locked), rebuild SHM in a temp dir and run Online Backup again; only a snapshot that passes a SQLite read check enters the import. Source files are read-only.
- Chrome running x LocalStorage LevelDB: first copy a `<profile>/Local Storage` snapshot, then discover origins from the snapshot and read them with an isolated, network-less Chrome helper; write to target origins through a hidden same-partition Electron page, never modifying the running target LevelDB directly.
- Windows App-Bound Encryption x native broker: ordinary renderer/main cannot unwrap `v20`. After user confirmation, main submits a one-time request only to the verified native broker; the elevated controller only creates/cleans a temporary `LocalSystem` service, and the original non-elevated broker connects to the service directly so the service impersonates the original user owning the Chrome data for SYSTEM DPAPI -> user DPAPI -> SYSTEM post-processing. When a standard user enters another administrator account in UAC, the ordinary broker must not try to open the high-integrity controller across accounts to read its image path; the broker binds the connection with an administrator-restricted pipe ACL, the exact controller PID returned by `Process.Start` and a one-time random token, the controller still verifies back the broker PID + helper image path, and the SYSTEM service still verifies broker PID + helper image path + token. This neither uses the administrator account's DPAPI identity by mistake nor treats a cross-integrity unreadable process path as required. Plaintext master keys/Cookie values must not enter renderer, argv, environment variables, disk, logs or IPC results; they flow only through restricted named pipes and desktop main's short-lived memory and are zeroed after use.
- Windows native pipe wait x bounded timeout: every server named pipe that implements bounded waiting with `BeginWaitForConnection` / `EndWaitForConnection` must be created with `PipeOptions.Asynchronous`; the client connection can stay synchronous. The fix must not widen the pipe ACL, remove the timeout, loosen PID/image path/token verification, or change the broker -> controller -> `LocalSystem` service identity boundary; a native source contract must block regression of the combination "synchronous creation mode + asynchronous wait API".
- Windows helper failure diagnostics x sensitive info: on entering the generic App-Bound failure branch, desktop main may log only these thirteen fixed allowlisted reasons: `helper_failed`, `broker_initialization_failed`, `controller_handshake_failed`, `service_channel_failed`, `elevation_failed`, `timeout`, `peer_verification_failed`, `service_failed`, `validation_failed`, `unsupported_key`, `cng_failed`, `decryption_failed`, `service_cleanup_failed`; an unknown or malformed response is logged uniformly as `invalid_response`. The first three phase reasons only tell broker initialization, elevated controller handshake and SYSTEM service channel apart and carry no exception text, path, PID, pipe/token or runtime text. Never log helper raw stdout, requests, Chrome paths, keys, Cookie or LocalStorage content; the UI, IPC and `BrowserDataImportError` still expose only `chrome_cookie_app_bound_decryption_failed`.
- UAC / service lifecycle x partial success: unconfirmed, UAC cancelled, service creation failure, helper signature/version/architecture failure all write no Cookie; LocalStorage continues with the existing partial-success semantics. The ordinary broker and the elevated controller each have independent parent-process monitoring and a hard timeout; even if Electron exits, JS timers vanish or the SYSTEM service hangs, the controller must stop, terminate the exact service PID if needed, delete it and verify no residue.
- Windows build gate x current release flow: default builds keep only TypeScript/C# source, unit tests and the manual `prepare:browser-import-helper` script; the helper is not a required local runtime asset and does not enter electron-builder `extraResources`, signing or signature verification. Only after explicitly enabling `ZCODE_ENABLE_WINDOWS_BROWSER_IMPORT=1` is the full asset chain restored; the UI entry is controlled by a separate product boundary.
- Linux `v11` x Libsecret/KWallet: when `v11` is detected, read the isolated snapshot with the same-brand Chrome/Chromium executable matched during Profile discovery; if the running Chrome explicitly carries a supported `--password-store`, the helper must forward it, otherwise let Chrome choose by the current desktop environment. When the helper is unavailable this process may continue importing `v10`, count `v11` as skipped and keep the LocalStorage import.
- OS credential protection x import result: a single Cookie that cannot be decrypted skips the protected item; on macOS an explicit denial or cancel of Chrome Safe Storage keychain access must end the whole import before any target write and must not continue importing LocalStorage.
- Install discovery x custom dir: use only user-explicit environment variables, running-process command lines, the OS registration index, PATH/XDG desktop entry and known standard dirs; every candidate must exist and be executable. Arbitrary disk paths that are unregistered, not running and not in these safe sources are not traversed; users can specify one explicitly through `CHROME_PATH` or `CHROME_EXECUTABLE`.
- Desktop continuous x Web remote replayable: data operations do not enter the task stream, snapshot or relay; the phone starts no browser runtime of its own.

Chrome install discovery and import order:

```text
macOS/Linux click import
        |
        v
env vars -> running processes -> OS registration/PATH/XDG -> standard/Snap/Flatpak
        |
        +-- no executable --> return chrome_executable_not_found --> show "Chrome 未找到" --> no Profile read/no target write
        |
        +-- found and executable --> discover and choose Profile --> Cookie/LocalStorage import

Windows settings page
        |
        +-- no import row rendered --> clear cache / clear all still usable

Windows dev / CI / package
        |
        +-- default ---------------------------> helper not compiled, signed or copied
        |
        +-- ZCODE_ENABLE_WINDOWS_BROWSER_IMPORT=1 --> build/sign/package the helper (UI stays hidden)
```

macOS authorization and import order:

```text
click import
   |
read Chrome Cookie snapshot
   |
request Chrome Safe Storage keychain authorization
   +-- Allow ------> write Cookies ------> import LocalStorage ------> return success/partial
   |
   +-- Deny/cancel --> write no target data --> do not start LocalStorage --> return unauthorized, show cancelled hint
```

Linux Cookie decryption order:

```text
read Cookie snapshot
   |
check encrypted_value prefix
   +-- v10 --------> ZCode decrypts with the Chromium basic-compatible key
   |
   +-- v11 --------> same-brand Chrome/Chromium helper
                        |
                        +-- explicit --password-store --> forward a known safe value
                        +-- not specified --------------> auto-select by GNOME/KDE
                        |
                        +-- success --> CDP returns Cookies --> write to the built-in session
                        +-- failure --> v11 skipped, continue v10 and LocalStorage
```

Windows App-Bound authorization and import order:

```text
settings page     desktop main        native broker          temp system service        Electron session

  |                  |------------------->| UAC                 |                         |
  |                  |                    |--cancel------------>|                         |

  |                  |                    |--allow/create service->|                      |
```

No undecided product semantics remain. This feature reads the Chrome Cookie database and `Local Storage` snapshot, does not discover, open or copy `Login Data`, and neither the platform return value nor the UI contains password fields. Decisions by date: 2026-07-16 user confirmed to implement only the Windows App-Bound Cookie, keep the existing LocalStorage, import no passwords, confirm explicitly with UAC every time, delete the temporary service after use, and stay compatible with Stable/Beta/Dev/Canary/Chromium. 2026-07-17: helper detailed failure reasons go only to the local log, not shown to users and no IPC or public error type extension. 2026-07-20: Windows temporarily hides the Chrome import entry; macOS/Linux discover Chrome before importing, cover non-default install dirs through system registration, and show "Chrome 未找到" when not installed; the Windows native implementation may be reused later, so source and tests are kept while default dev, CI, signing and packaging stop using the helper, leaving only the explicit asset switch `ZCODE_ENABLE_WINDOWS_BROWSER_IMPORT=1`. 2026-08-21: the import row moved from "浏览器数据" to the "浏览器控制" group, on the same card as "开启内置浏览器控制" after the switch; the title is "导入 Chrome 登录状态" and the description is user-benefit oriented (bring over login state once so AI can open logged-in sites directly), no longer using Cookie/LocalStorage/Profile as the main description. Feature boundary, error codes, import scope and the Windows hiding policy are unchanged by this adjustment.

## E2E handoff notes

- No conversation E2E is created; this feature does not modify task/session realtime semantics.
- Desktop E2E fixtures carry no real user Cookies or LocalStorage. Automation uses a temporary Electron partition, synthetic SQLite fixtures and synthetic LocalStorage snapshots; real Chrome import is only a local manual smoke.
- Windows App-Bound automation has three layers: pure protocol/verification uses synthetic ciphertext and a fake broker; Windows local integration uses a test-only double-layer DPAPI fixture and reads no real Cookies; real Chrome is a manual smoke only. On the current machine a real x64 helper was compiled and executed with `--version` (protocol, x64, app version, commit). 2026-07-17, with user authorization, a local `APPB` ciphertext was read and the installed signed helper run; lifecycle monitoring confirmed that with the standard-user broker started and UAC switched to another admin controller it returned `helper_failed` before creating the `ZCodeBrowserImport_*` service, never reaching the Chrome key format/CNG stage; helper residue from diagnostics was cleaned and service residue is 0. The latest signed-package log further localized the failure to `controller_handshake_failed`; an isomorphic .NET runtime probe with synthetic ciphertext confirmed that a server pipe created with `PipeOptions.None` throws "Pipe is not opened in asynchronous mode" when calling `BeginWaitForConnection`, without creating a temporary service, reading real Cookies or writing keys/Cookies to logs. The server pipe is now `PipeOptions.Asynchronous`, the BS-030 source contract passes 14/14 and the x64 helper was recompiled; local application control still blocks running the unsigned workspace helper, so release completion still needs x64/arm64 helper signing, standard-user credential-switch UAC allow/cancel, service/helper residue checks and real Chrome `v20` verification. Real authorization behavior of macOS Keychain and Linux Secret Service continues to be verified manually per platform boundary; Linux must cover at least GNOME + `gnome-libsecret`, KDE + `kwallet5/kwallet6` and `basic/v10`. A single item that cannot be decrypted safely must stably count as skipped or return a clear failure; an explicit macOS keychain denial/cancel must end the whole import; Cookie/LocalStorage values or decryption keys must never enter logs or IPC.
- Web/mobile verification only checks the disabled state and no mutation; creating a separate Browser Use runtime for tests is not allowed.
