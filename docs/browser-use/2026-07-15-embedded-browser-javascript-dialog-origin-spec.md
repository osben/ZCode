# Embedded Browser JavaScript Dialog Origin Spec

## Background

The ZCode desktop embedded Browser uses the standard Electron 41 `<webview>`. When a page calls `alert()`
/ `confirm()`, the native Chromium dialog shows only the message body, not the source site, so users
cannot tell page content from a ZCode prompt. The desired form is a dialog titled like `www.runoob.com
says`.

Standard Electron has no switch to add an origin title to `<webview>` native dialogs, so the guest
installs a fixed isolated preload that synchronously asks main to show a system MessageBox before the
page's native `alert` / `confirm` runs.

## Goals

- In the desktop user-visible embedded Browser, `alert()` and `confirm()` use a system native MessageBox.
- The first MessageBox line is always `<host> says`, resolved by the main process from a trusted Chromium
  URL; the second line is the page message.
- `alert()` still returns `undefined`; `confirm()` still returns a boolean.
- Buttons follow the app language: Chinese "取消 / 确定", English `Cancel / OK`.
- During browser tool execution the native Chromium JavaScript Dialog is kept, so existing CDP `getDialog`
  / `handleDialog` can still observe and handle it.
- Web, mobile and remote-control paths are unchanged; they do not host Electron `<webview>`.

## Non-goals

- `prompt()` is not taken over. The Electron system MessageBox has no synchronous text input, so replacing
  it would break the synchronous return semantics; it keeps the native Chromium implementation.
- `beforeunload`, HTTP auth, permission requests and file pickers are not taken over.
- No system-lookalike dialog is rendered in the renderer/UI layer; color, radius, theme and accessibility
  belong to the OS native component.

## Origin and security boundary

- The preload exposes only a synchronous `alert` / `confirm` request bridge, with no generic IPC, Node API
  or filesystem ability.
- Normal navigation, `src` and `srcdoc` iframes each load the fixed preload via
  `nodeintegrationinsubframes`. An inherited `about:blank` iframe without `src` produces no document-level
  navigation and Electron does not run the preload for it alone; the top-level preload uses a
  `MutationObserver` to find such frames and installs the same wrapper only when the browser same-origin
  policy allows access. A cross-origin frame cannot be read by the parent and is handled by the preload
  loaded at its own navigation.
- The origin title is first generated by main from Electron `event.senderFrame.url`. Electron 41 may
  return an empty value or `about:blank` for same-origin iframes. A frame URL is used directly only if an
  HTTP(S) host can be parsed from it; otherwise fall back to the guest main-document URL maintained by
  Chromium `WebContents.getURL()`. Both come from Electron/main; never trust a page-supplied URL, DOM
  title or hand-built origin text.
- `http:` / `https:` URLs use `URL.host`; only when neither the frame URL nor the guest URL yields a host
  is `This page says` used.
- Only a user Browser guest that the renderer bound through `BrowserViewAttachGuest` and whose tab id
  starts with `browser:` may enter the customized dialog path.
- For an unbound guest, the browser-use `iab-tab:` tab, a non-`alert` / `confirm` type, an automation
  window, or a failure to create the system dialog, main returns `handled: false` and the preload must call
  back into the native Chromium API.

## State and order

User clicks and Agent/CDP operations share one guest, so "user interaction" and "automation window" must
be distinguished explicitly:

```text
User clicks page (automation = idle)
  page alert/confirm wrapper
        |
        v
  preload sendSync(type, message)
        |
        +--> main validates browser: guest + senderFrame
                  |
                  v
            compute host from frame URL / guest URL
                  |
                  v
            showMessageBoxSync(parent)
                  |
                  +--> return { handled: true, value }
                  |
                  +--> wrapper returns synchronously, native API not called

Agent browser command (automation = active / grace)
  main marks the owning window as native-dialog passthrough
        |
        v
  page alert/confirm wrapper -> preload sendSync
        |
        +--> main return { handled: false }
        |
        +--> wrapper calls the Chromium native API
                 |
                 v
        BrowserGuestManager pendingDialogs
                 |
                 +--> getDialog / handleDialog
```

When an automation command starts the window enters passthrough; after the command ends a 3-second grace
remains to cover dialogs fired later through microtasks or short timers after a click. Concurrent
commands are reference counted, and grace starts only after the last command ends.

Design flaw of the old CDP approach: when intercepted, the Chromium Dialog was already created. Even after
`Page.handleJavaScriptDialog` reported closed and `confirm` had returned, macOS could still draw the
queued NSAlert. The new path decides before the native API is called; the user path creates no Chromium
Dialog, so there is no second native box paint race.

## Platform and compatibility

- macOS, Windows and Linux share Electron `dialog.showMessageBoxSync`, with the parent fixed to the ZCode
  window owning the guest.
- The icon reuses the desktop app icon; if unsupported or empty it may degrade to no icon.
- Both themes use the system native theme; no new UI token.
- The guest keeps `sandbox: true`, `contextIsolation: true`, `nodeIntegration: false`.
  `nodeIntegrationInSubFrames: true` only lets the fixed preload enter each iframe's isolated world; the
  page main world gets neither Node nor `ipcRenderer`.
- `<webview>` creation explicitly declares `nodeintegrationinsubframes`, and main `will-attach-webview`
  pins the same preference and preload path. Setting it only after guest attach is not enough, because
  existing subframes do not get the preload backfilled.
- When the Electron sender frame has a valid HTTP(S) URL the initiating frame's host is shown; when
  Electron returns `about:blank` the guest main-document host is shown.
- Mobile `/remote`, Web, and the continuous/replayable semantics of desktop/phone task realtime do not go
  through this path.

## Acceptance

1. In the result iframe of `https://www.runoob.com/try/try.php?filename=tryjs_events`, triggering
   `confirm("123 来之内置浏览器")` shows `www.runoob.com says`, the body and cancel/OK buttons.
2. `alert()` offers only OK and the call returns `undefined`.
3. `confirm()` cancel and OK return `false` and `true`.
4. A page cannot forge the origin title; changing `document.title` does not affect it.
5. After a browser tool triggers a dialog, `getDialog()` can still read it and `handleDialog()` can still
   accept or dismiss it.
6. `prompt()`, Web/mobile and ordinary ZCode native dialogs behave as before.
7. After closing the customized system box, the same dialog does not produce a second Chromium native box.
8. A same-origin result iframe without `src`, written by the parent via `document.write`, also shows
   exactly one system box with the host.
