# Feedback Diagnostic Log Upload Boundaries

Feedback archives are owned by the services feedback domain; Desktop only injects CLI/CUA log sources. Compact/full fallback uses the same allowlist and redaction policy. Manual local export and upload use different collection scopes; manual export continues to show the result in the file browser.

Feedback includes app `logs/`, CLI `log/`, CLI `rollout/`, and `*.exit.log` files from CUA: supported-encoding text logs from the current day, an explicitly non-sensitive projection of CLI `config.json`, and a version/system summary that contains no host name or user directory. Only this explicitly designated file may be collected from CLI configuration. If configuration parsing fails, omit the configuration. Regardless of whether parsing succeeds, exclude unknown fields, plugin options, MCP, networking, and hooks from the upload package. The retained projection, like rollout data, is redacted as diagnostic text. Databases, other configuration files, sessions/snapshots, secrets, binaries, and symbolic links must not enter the upload package. The per-file limit is 8 MiB, and the total input limit is 32 MiB (2 MiB for compact archives). Skip expired, oversized, undecodable, or unreadable files; never fall back to copying raw data. CLI `config.json` is not restricted to the current-day window; rollout and CUA logs still include only files from the current day.

Calculate the date range in the local timezone at archive start and filter by file modification time in `[today 00:00, tomorrow 00:00)`. Do not use a rolling 24-hour window; handle year boundaries and daylight saving time as calendar dates. Check the modification time again after opening a file. This rule filters files: a file that continues to receive appended data may contain older records; do not split it by per-line timestamp. Keep the existing contract for the date range of manually exported local logs.

For logs that are still being appended to, perform bounded reads using the byte size returned by `fstat` after opening the file. Data appended during the current read is left for the next archive; do not discard the entire file because of a benign append. Skip files that reach EOF before the expected length. The result must still pass encoding checks and full redaction; raw text must not be uploaded. `about.txt` records the number of collected files and the number of skipped log candidates by reason category. Do not additionally record the names or paths of skipped files.

Redaction covers nested JSON, body/message/tool input and output fields, common credentials, URL credentials, private keys, and user directories. Regular expressions cannot guarantee detection of arbitrary natural-language personal information. Log upload is enabled by default; the form retains scope and possible residual business-information notices, and users can disable it before submission. Users must add and review screenshots themselves.

URL paths may also contain credentials. In diagnostic text, keep only the URL scheme, host, and port; replace every non-empty path with `[REDACTED]`, and continue removing userinfo, query, and fragment. In user-provided text, keep paths for ordinary troubleshooting links, but hide the entire path for webhook, reset, invitation, callback, download, verification, and token paths, as well as links with authentication/signature parameters. Path detection must include percent-encoded forms; hide conservatively when decoding fails. Apply this rule consistently to ticket titles, descriptions, supplemental comments, and diagnostic ZIPs. Do not modify contact information the user entered explicitly. Acceptance must verify at three levels—shared text output, every entry in full/compact ZIPs, and create/comment request bodies—that path-based mock credentials do not remain, while ordinary links in user text remain useful for troubleshooting.

Write the archive to a feedback temporary directory. The feedback service cleans it up after upload; the builder cleans it up if packaging fails. Existing ownership of ticket creation, cancellation, and background-job state remains unchanged. See the [implementation plan](plans/2026-09-18-feedback-upload-privacy.md) for acceptance scenarios.

## Redaction in local manual export

Manual export (help menu, system menu "Export logs") goes through `packages/desktop/src/main/exportLogs.ts`. Its collection scope differs from the upload archive, and redaction works line by line in a stream:

- A line that parses as a whole with `JSON.parse` (CLI `rollout/model-io-*.jsonl`, CLI JSONL logs, and lines that are one JSON string) is redacted structurally and reserialized: strings under a sensitive key family (substrings such as `token`, `auth`, `secret`, excluding an allowlist such as LLM token counts) become `***REDACTED***`, and an object/array under a sensitive key inherits that as a whole (its keys also become placeholders, see the next item); other strings follow the text rules, and JSON nested in a string is processed recursively. A line with nothing sensitive is output unchanged. Every line is still valid JSON after export.
- Object keys under a sensitive parent are always replaced by `***REDACTED***`, with a ` (2)` style suffix on collisions (each object remembers the next free suffix per placeholder, so tens of thousands of keys cost linear time and cannot block the export): in a token-keyed map (`{"token":{"tok_...":{...}}}`) the key itself is the credential and need not look like a connection string, URL or Bearer. Values still follow the original rules (strings and numbers become placeholders, booleans and null are kept), so field count and switch states remain.
- Object keys under a non-sensitive parent follow the text rules: a connection string, a URL with a token or `Bearer ...` used as a key is redacted too (whether the key name itself is sensitive is still judged by the original key); two keys that become equal after redaction get a ` (2)` style suffix on the later one and do not overwrite each other. A pure-identifier key cannot match a text rule and is skipped.
- A rewritten line keeps original literals: numbers are written back from their source text (`JSON.parse` source text + `JSON.rawJSON`), so integers above 2^53 and forms like `1.50` are unchanged; objects are rebuilt without a prototype so a `__proto__` key is not swallowed by the prototype setter. This fidelity parse runs only for lines that hit redaction.
- Scalars follow the sensitivity of their key:
  - Numbers under a sensitive key (including inherited from a parent, such as array elements of `{"token":[123456]}`) become the string `"***REDACTED***"`: a numeric-only passcode or PIN is itself a credential. The staging text rule also replaces them, so structural redaction must not regress here.
  - Booleans and null under a sensitive key are kept: they have only three values and cannot carry a credential, and keeping them lets troubleshooting see states such as `hasAuth` or `token: null` (not configured).
  - Numbers under a non-sensitive key are kept. Count keys in model usage contain the substring `token`, so the allowlist names the count fields one by one: provider usage `cache_read_input_tokens`, `cache_creation_input_tokens`, `ephemeral_5m_input_tokens`, `prompt_tokens_details`, `completion_tokens_details`, `max_completion_tokens`, `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`, `*TokenCount`, and ZCode internal camelCase `maxOutputTokens`, `cacheReadTokens` and so on. The allowlist prefixes consist only of counting words and do not let arbitrary `*_tokens` through: `access_tokens`, `session_tokens`, `read_token` are still redacted. `buildSnapshot` is a snapshot duration wrongly flagged by the `dsn` substring and is also allowlisted.
- Structural redaction recurses to at most 256 levels, and JSON nested in a string shares that budget with the outer one. A line deeper than that is replaced whole by `{"exportRedaction":"line replaced: JSON nested deeper than 256 levels"}` (still valid JSON) and the export continues; recursing 5000 levels would overflow the stack and abort the whole export.
- Other lines (app `logs/*.log`, formatted `config.json`, truncated JSONL) follow the text rules, and ordinary strings in the structural branch use the same text rules:
  - A bare value under a double-quoted key becomes a quoted placeholder.
  - An object/array value under a sensitive key is matched by brackets (aware of brackets and escapes in strings) and replaced whole by a quoted placeholder, so inner keys that are not sensitive do not leak (`{"token":{"value":"..."}}`). If the brackets do not pair within the line (truncated), replace to the end of the line. A line that has only an opening bracket and nothing after it is the start of multi-line formatted JSON and stays as is; later lines are still handled key by key, and the file structure is not broken.
  - Values of Bearer, URL query and connection strings (`scheme://user:pass@host`) match the staging rule, and quotes and backslashes always count as content: passwords such as `p"a"s`, `ex'ample`, `ab\cd` are replaced whole. Earlier these rules stopped at quotes and backslashes to protect JSON embedded in text, and passwords were exported whole or in part (reproduced in two reviews); that was reverted. The cost is that JSON embedded in a text line may lose one extra segment (for example a connection string swallowing up to the `@` of the next field), which costs context only and leaks nothing.
  - Known limitation (also in staging): line-by-line processing cannot see cross-line structure, so a value whose key is not sensitive under a sensitive parent key in multi-line formatted JSON is not replaced; a connection-string rule does not match a password containing an unencoded `/`.
- Reason for the fix: text regexes edited JSON text directly and produced unquoted placeholders, swallowed the backslash of `\"`, and cut object values in half, so whole model-io lines could not be parsed. Acceptance: the formal E2E `packages/desktop/test/e2e/feedback/logs/export-logs-jsonl-redaction.test.ts` (ELR-01, promoted from manual-review/pending on 2026-11-09 into the default E2E and the MR incremental E2E) puts samples into the rollout directory and CLI log directory of an isolated HOME, exports through the real menu, parses every line, and confirms the simulated secrets (numbers under sensitive keys `{"password":123456}` and `{"token":[123456]}`, connection strings whose password has single quotes, double quotes or backslashes, passwords and query values with two double quotes in the raw text, object values under sensitive keys, Bearer with a backslash, connection strings / queries / Bearer used as object keys, a top-level JSON string line, and a line nested 5000 levels) appear in no entry of the archive, usage counts are kept as they are, big integers / `1.50` / `__proto__` in rewritten lines are kept, and the extra-deep line is replaced by the placeholder line.
