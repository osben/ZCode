# Single Owner Stream Rendering

> Status: Currently only describes non-owner content filtering under replayable subscriptions.
>
> The desktop `continuous` subscription still consumes direct dynamic stream events, not the empty batch
The mobile Web remote control `replayable` subscription needs this strategy to reduce the risk of interleaving disconnection recovery with snapshot alignment.

## Background

After sharing the host process, the desktop and mobile clients are still independent renderers. The mobile browser may be in the background, disconnected, or discarded by the system for extended periods. If all renderers directly consume the same streaming chunks, disconnection recovery can intersect with snapshot alignment, producing duplicate tail chunks or runtime forks.

## Solution

Each prompt is generated by the sending renderer and passes `clientId`. The host process remains the sole ZCode runtime and persistence fact source; `task_stream_mirror_batch` carries `ownerClientId`.

Replayable subscriptions filter ordinary content-class batches by the subscribing `clientId`:

- The sending end matching `ownerClientId` receives complete streaming `ops`, responsible for real-time rendering of body text, tools, permissions, and other fine-grained state.
- Other replayable renderers can filter ordinary body text, thought, and tool chunks to avoid redundant rendering.
- `permission_request`, `elicitation_request`, their corresponding responses, `task_complete` / `task_error`, and snapshot invalidation must not be swallowed by ordinary owner-only content filtering; they must be visible to online clients of the same task, or trigger snapshot alignment.
- Final messages, file changes, and task metadata are still aligned through `getTaskSnapshot()`.

## Stability Boundaries

This ensures that observer renderers no longer repeatedly consume intermediate chunks due to mobile disconnection, reconnection, or task switching. If the sending end is the mobile client, the mobile render may still lose the real-time view, but the host process will continue to consume the provider stream and persist the final snapshot. After the mobile recovers, the snapshot should be used as the authoritative source.

## UI Behavior

The replayable observer can skip rendering streaming body text during operation, displaying only a "another device is sending messages..." loading prompt. After the task ends, the snapshot alignment replaces it with the final message block. The desktop continuous end continues to maintain real-time body text rendering through the direct stream.
