# Release Candidates Hosted by the Packaging Platform

- Status: Proposed
- Date: 2026-08-18
- Related specification: `docs/specs/release-platform/release-platform-api-v1.md`

## Context

z-code's builds and releases are split, but candidate manifests, approval artifacts, and build outputs still rely on a GitLab runner shared directory. An independent packaging platform cannot consume that boundary reliably, and it gives no unified retry, audit, idempotency, or cross-platform state.

## Decision

Introduce a versioned `release-candidate.v1` contract. The packaging platform is the single source of truth for Release Candidate state:

```text
z-code worker                    Packaging Platform
build/sign/notarize              candidate state machine
upload immutable artifacts  ---> object storage + manifest
submit build result         ---> approval / publication
                                  final latest*.yml + rollout
```

The z-code worker must not write stable feeds directly, invoke the production release API, or hold long-lived OSS credentials. The only final `latest.yml` is generated by the platform from the immutable `update.base.yml`, artifact digests, and approved notes revisions; localized logs are unified under `releaseNotesByLocale`.

Cross-system contracts:

- JSON Schema `release-candidate.v1`
- REST API `release-platform.v1`
- CloudEvents-style status events
- `Idempotency-Key` and request ID
- OIDC/short-lived token scopes

## Alternatives (all rejected)

- **Keep extending GitLab CI**: lowest cost, but state stays tied to runners, shared directories, and CI YAML; platform handoff needs re-interpreting internal scripts; retry/audit boundaries stay unclear.
- **Upload archives only, no standard manifests**: the platform cannot reliably verify version, platform, digest, base update metadata, or provenance.
- **Platform handles only approval, z-code keeps publishing**: the production feed/API stays under worker control, so no permission isolation or unified publish state.

## Consequences

Benefits:

- Build workers are swappable between GitLab, Buildkite, or self-hosted runners.
- Candidate artifacts can be re-published; log edits do not trigger repackaging.
- The platform manages approvals, retries, audit, and gray/stable rollouts uniformly.
- Runners no longer need long-lived OSS/release API credentials.

Costs and risks:

- A candidate state service and object-storage lifecycle management must be maintained.
- The v1 contract needs a migration period compatible with the legacy z-code CI.
- The platform must handle digest verification, idempotency, and publish failure recovery.

## Rollback

During migration, keep z-code's compatible publish path toggle. If the platform is unavailable, fall back to the legacy CI release pipeline. The fallback must not let test/sandbox pipelines bypass production guards and must not reuse platform-confirmed notes revisions.
