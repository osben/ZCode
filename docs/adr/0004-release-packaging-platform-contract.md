# Release Candidates Hosted by the Packaging Platform

- Status: Proposed
- Date: 2026-08-18
- Related specification: `docs/specs/release-platform/release-platform-api-v1.md`

## Context

z-code's builds and releases are already split, but candidate manifests, approval artifacts, and build outputs still rely on a GitLab runner shared directory. This boundary cannot be stably consumed by an independent packaging platform, nor can it provide unified retry, audit, idempotency, and cross-platform state management.

## Decision

Introduce a versioned `release-candidate.v1` contract and designate the packaging platform as the single source of truth for Release Candidate state:

```text
z-code worker                    Packaging Platform
build/sign/notarize              candidate state machine
upload immutable artifacts  ---> object storage + manifest
submit build result         ---> approval / publication
                                  final latest*.yml + rollout
```

The z-code worker must not write stable feeds directly, invoke the production release API, or hold long-lived OSS credentials. The sole final `latest.yml` is generated by the platform based on immutable `update.base.yml`, artifact digests, and approved notes revisions, with localized logs unified under `releaseNotesByLocale`.

Cross-system contracts are fixed to use:

- JSON Schema `release-candidate.v1`
- REST API `release-platform.v1`
- CloudEvents-style status events
- `Idempotency-Key` and request ID
- OIDC/short-lived token scopes

## Alternatives

### Continue Extending GitLab CI

Lowest implementation cost, but state remains tied to runners, shared directories, and CI YAML; platform handoff requires re-interpreting internal scripts, and retry/audit boundaries remain unclear. Rejected.

### Upload archives only, skip standard manifests

The platform can store files, but cannot reliably verify version, platform, digest, base update metadata, or provenance. Rejected.

### Platform handles only approval, z-code continues publishing

Marginal improvement to the human experience; the production feed/API remains under worker control, preventing permission isolation and unified publish state. Rejected.

## Consequences

Benefits:

- Build workers can be swapped between GitLab, Buildkite, or self-hosted runners.
- Candidate artifacts can be re-published; log modifications do not trigger repackaging.
- The platform can uniformly manage approvals, retries, audit, and gray/stable rollouts.
- Runners no longer need long-lived OSS/release API credentials.

Costs and risks:

- Requires maintaining a candidate state service and object storage lifecycle management.
- The v1 contract needs a migration period compatible with the legacy z-code CI.
- The platform must handle digest verification, idempotency, and publish failure recovery.

## Rollback

During migration, retain z-code's compatible publish path toggle. If the platform is unavailable, fall back to the legacy CI release pipeline; the fallback must not allow test/sandbox pipelines to bypass production guards, and must not reuse platform-confirmed notes revisions.
