Evidence vocabulary used below: service synthetic, real Host/CLI, Desktop DOM, mobile replayable, live tenant. They are never substituted for one another. Platform HTTP and model calls in E2E are isolated stand-ins unless a live run says otherwise. A narrow Desktop viewport is not mobile remote validation. ## Fixture contract

- `feishu-streaming-card-lifecycle.json` is a case-local synthetic stream fixture. The other five cases use same-named case-local synthetic metadata under `fixtures/bots/`; every fixture declares `syntheticReason` and a timing class.
- Class `synthetic`, because external provider replay supplies only model SSE and cannot control the step-by-step observation window in which the Bot consumes task events; the fixture generates deterministic ZCode stream events.
- Mock Feishu API must record requests, not just return success: request count, URL, method, reaction id and Card JSON are the evidence.
- `bot-automation-result-delivery` records mock Feishu requests and uses a controlled task stream to prove the scheduler listens before prompt dispatch; fixed sleeps must not replace event gates. Weixin `/sendmessage` is covered by the shared watcher/provider service integration test in `packages/services/test/botsService.messageFlow.test.ts` and is not reported as Desktop E2E.
- Formal cases passed manual review and left `manual-review/pending/`. The Bot domain has no dedicated Docker preset; the default Desktop WDIO run is the formal entry.
- CF-01 uses case-local synthetic metadata; the missing credential only deterministically triggers a runtime error, and `syntheticReason` must say it stands in for real Feishu fault injection. CF-01 keeps the dialog open and waits for the background connection-state projection (the visible-period serial status polling) rather than closing and reopening to refresh. It passed Desktop manual acceptance.
- Promotion uses the existing Bot formal-directory convention (the generic promotion dry-run only supports conversation-session). No Docker admission was added.

## Bot receive-event rules (fix of 2026-10-08)

- Receive callbacks arrive with `sender_type=bot` (normalized internally to `app`); history interfaces keep `app`.
- An ordinary group must be enabled and the message natively @-mentioning the bot. An already-attached topic keeps processing every bot message the platform actually pushes. Own echoes, duplicate events, not-enabled groups and left topics are blocked.
- Bot slash commands and selection text in the main chat and in topics are plain messages and never enter control dispatch.
- Evidence: provider/group-service/mention-gate unit tests (205); two real-CLI topic regressions (native bot event stops the old round, continues, replies); four Feishu/Lark x group/topic regressions (ordinary-group bot callback, command text, dedup). Still unverified: real-tenant bot event permissions and live notifications (the group-enable message now documents the include_bot permission).

## Mention-only, explicit reference and cold-task admission (2026-09-08)

- A group mention-only input (empty text after removing the bot mention) is preserved instead of discarded by the provider before reference/topic handling. Verified text/post/card references are kept separate from command parsing and fetched text references are retained; referenced images are prepared in the same input. Empty requests with no authorized background get guidance and are not admitted. Quote-only mentions implicitly ask the model to answer or carry out the quoted request; command parsing stays on the server.
- Topic history is prepared once before task creation, with the same admission-time authorization check and accepted-input checkpoints.
- Cold-task admission: the adapter obtains the existing background subscription snapshot before attachment upload/admission (same task and workspace identity), fixing `proto.sessionNotFound` for a task still in the CLI database; group stream setup waits for the same authoritative snapshot before subscribing and rechecks the subscription map after the await to avoid duplicate startup/input listeners. Old inputs are never resubmitted; recovery failure refuses submission.
- Standalone mention token validity: the Feishu/Lark token cache honors the interface's remaining `expire` instead of a fixed 90 minutes (a real interface returned `expire=4187` s). A standalone @ in the main chat replies "请补充需求，或回复要处理的消息并 @我。" and admits no task; a failed earlier message is not auto-replayed. Natural token expiry in a real tenant was not waited out (controlled-clock tests cover it).
- Evidence: 122 provider/service tests, TP-01 Desktop E2E (empty mention returns guidance with zero queued inputs; explicit quoted text enters the real CLI queue with the existing input/attachment and can be cancelled without stopping the task), native verification of bare mention guidance and quote-only mention answered `12` for a quoted "7 plus 5" in the original task with CheckMark and delivery `sent`. Native Lark, mobile Web and other OS unverified.
