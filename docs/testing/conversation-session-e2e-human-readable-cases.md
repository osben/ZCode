# Conversation Session E2E Manual Acceptance Cases

This document organizes the A-J main path of the conversation session, plus the dedicated matrices for goal, fork, queue, compact, model, edit and subagent, into a reader view for product, development and QA. Each case keeps only three things: how the user operates, what should be seen, and where to track the automation status. Environment faults, pure display UI, the full tool cross product and performance stress remain in their own dedicated catalogs and are not mixed into this main-path manual acceptance list.

The authoritative case definitions are still in the [Conversation Session Case Catalog](../conversation-session-case-catalog.md), and the automation status is still in the [Conversation Session E2E Coverage Matrix](./conversation-session-e2e-coverage-matrix.md). This document does not redefine product semantics; when the original documents change status, update the notes here.

Status words in the notes: "covered" (已覆盖) maps to `covered`, "partial" (部分覆盖) to `partial`, "planned" (已计划) to `planned/pending`, "to add" (待补) to `missing`, "pruned" (剪枝) to `pruned`. A note that says only "product accepted" means the product semantics are confirmed, not that E2E covers it. When one row merges several equivalent cases, the note keeps all original IDs.

```text
Draft first send -> running -> follow-up input queued -> current turn completes
                         |               |
                         |               +-> auto consume / Goal continues / auto compact
                         +-> Stop -> queue paused -> resume / send now / withdraw and edit

Parent session -> Agent/Subagent child -> background completion notification -> parent session continues
   |              |
   |              +-> right-side read-only detail / subagent directory
   +-> fork copies only stable history, not the queue or background runtime state
```

## 1. Session basic lifecycle

| Operation path                                                       | Expected result                                                                                                                                                           | Note                          |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------- |
| New conversation -> type ordinary text -> click send                 | Creates a session and enters the formal session page; the user message is visible and the session goes into warm-up or running                                           | Source: A01; covered          |
| First message just sent, still warming up -> send another ordinary text | The second input enters the queue and does not interrupt the first turn                                                                                                  | Source: A02; covered          |
| Draft first send accepted -> sessionId bound but the first authoritative message has not arrived | The input box only moves from the centered layout to the bottom, with the editor instance and content continuous; the timeline does not fake a user message and shows no empty-state hint | Source: A11; partial          |
| Session running, queue empty -> wait for the assistant to complete normally | The session enters the completed state and the input box is sendable again                                                                                         | Source: C01; covered          |
| Completed session, queue empty -> keep sending ordinary text         | Starts the next turn immediately                                                                                                                                          | Source: C03; covered          |
| Running, queue empty -> click stop -> send ordinary text             | The current turn closes as "interrupted"; the next message starts a new turn immediately and is not wrongly queued by the old running state                               | Source: B01, B05, B12; covered |
| Session A running -> switch to Session B -> send a message in B      | A continues in the background and B also runs independently; the timelines, queues and states on both sides do not overwrite each other                                    | Source: J01, J02, J04; covered |
| A and B both running -> create or switch to C and send               | C can also run; the product does not limit the concurrency of different sessions                                                                                          | Source: J03; covered          |

## 2. Queue and Stop

| Operation path                                                                              | Expected result                                                                                                                                                                  | Note                                         |
| ------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| Current turn running -> send 1, 2, 3 or more ordinary texts consecutively                   | Each input is appended to the same FIFO in admission order; the current turn is not interrupted; `3+` can be shown collapsed                                                      | Source: A03-A06; covered                     |
| Current turn running -> send `/goal ...`                                                    | The command is first shown as a goal-type queue item; the goal is set or updated only when its turn comes                                                                         | Source: A07, H03, H04; covered               |
| Current turn running -> send `/compact`                                                     | `/compact` is queued as a compact-type maintenance item with a queued notice; it does not show as an ordinary user message and starts no parallel compaction                       | Source: A08, M04, G1-03; planned             |
| Current turn running -> send ordinary text, `/goal ...`, `/compact` in turn                 | The three inputs share one admission order; on consumption each follows its own text, goal or compact semantics and types cannot mix                                               | Source: M05, G1-09; planned                  |
| Running with 1, 2 or `3+` queue items -> click stop                                         | The current turn is interrupted; all queue items are kept as they are and auto-consumption is turned off                                                                           | Source: B02-B04; covered                     |
| Current turn running, queue non-empty and auto-consume on -> current turn completes normally | The queue head is promoted automatically and starts the next turn; the consumed text must become a visible real user message, not just vanish from the queue                      | Source: C02; covered                         |
| Paused queue exists -> send ordinary text in the input box                                  | A queue-disposal confirmation pops up: clear the old queue and send, or keep the old queue and send immediately; after cancel the draft and attachments are not lost              | Source: B06, C08; partial                    |
| Paused queue exists -> send `/goal <new goal>`                                              | Shares the queue-disposal confirmation with ordinary text; goal control commands such as `/goal resume` skip this confirmation                                                     | Source: B07; partial                         |
| Paused queue exists -> click "Send now" on a queue item                                     | First lock the target item, then start across the stop barrier; the original item is deleted only if the start succeeds, and stays in place on failure or timeout; the relative order of the others is unchanged | Source: B08, M07a, M07b; partial       |
| While running, quickly click "Send now" twice                                               | The same queue item is sent at most once; no duplicate request and no wrong deletion of a neighbouring item                                                                        | Source: M07g; currently failing, needs regression |
| Queue paused, input box completely empty -> click "Edit" on an ordinary-text queue item     | It is first deleted from the authoritative queue; on success the full original text is restored only in the input box of the originating session, without auto-send                 | Source: B09; partial                         |
| Queue paused, input box empty -> edit a goal queue item                                     | Restored as the full `/goal ...` text; sending again gets a new queue identity                                                                                                     | Source: B09a, B09e; covered                  |
| Paused queue item with several attachments -> click edit -> resend directly                 | The original attachment order and references are restored completely, without re-upload or adopt; the resend produces a new commandId and queueItemId                              | Source: B09b, B09e; covered                  |
| Queue item is `/compact` -> look at the available actions                                   | Delete, reorder or run immediately are allowed, but there is no text-editing entry to withdraw into the input box                                                                  | Source: B09f, B13; pruned                    |
| Input box already has text, attachments, web context, a selection quote or content being uploaded -> click "Edit" on a queue item | Withdraw is refused and no delete command is sent; the existing draft and queue stay unchanged, with a hint to handle the current draft first                    | Source: B09c; covered                        |
| After clicking queue "Edit", the other end consumes or deletes the item first, or this end switches session/workspace | On stale/noop/failure the old draft is not restored; it is restored idempotently only if accepted/duplicate and still in the original session and workspaceKey      | Source: B09d; partial                        |
| Queue-disposal confirmation open -> the other end adds, deletes or withdraws queue items -> this end confirms send | The old confirmation is invalid and does not clear new queue items the user has not seen; confirm again on the latest projection. Only reordering the same set of IDs does not invalidate the confirmation | Source: B16; planned                |
| Paused queue -> drag to reorder or delete an item                                           | Only changes the authoritative queue order or deletes the target item, without triggering consumption                                                                              | Source: B10, B11; covered                    |
| Paused queue, target completed or non-existent -> click "Resume"                            | Turns auto-consume on and consumes from the head in FIFO order until empty; goal and compact keep their own types                                                                  | Source: B14; partial                         |
| Main turn still running, queue paused -> click "Resume"                                     | Only turns auto-consume on, without preempting the current turn; consumption from the head resumes after the current turn closes                                                   | Source: B15; covered                         |
| Desktop and mobile submit input to the same busy session at the same time                   | All accepted input is serialized by the same CLI queue; desktop continuous and mobile replayable only affect the delivery mode and do not form two queues                          | Source: PV4-03; full formal evidence to add  |
| Before a CLI restart there is accepted input that has not reached a terminal state -> reconnect or query the command result | The input is explicitly marked discarded; `queue/guide` settle silently, and only `startNow`/`unknown` not yet in the transcript may be resent with a new commandId after confirmation; automatic replay is forbidden | Source: PV4-06, PV4-25; protocol-specific |

## 3. Goal

| ---------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Completed session, no goal -> send `/goal 修完登录流程` ("finish the login flow")                    | Creates the goal; the timeline immediately shows a real user message identical to the original command, and the goal summary shows the parsed objective | Source: C04, H01, G0-01; covered                                                      |
| Existing goal -> send `/goal replace 修完登录流程`                                                   | Replaces the goal, the objective drops the command prefix and `replace`; the original command is still shown verbatim as the user message           | Source: H02, G0-02; covered                                                           |
| Manual or auto compaction in progress -> send `/goal ...`                                            | The goal input enters the future queue; the target is updated and the real user message shown only when compaction completes and its turn comes     | Source: H05, G2-01, G2-07; main path covered, the auto-specific case once had a failing record and needs ongoing regression |
| Goal continuation or verifier running -> send ordinary text, `/goal ...`, `/compact`                 | All three enter the future queue and start no parallel request in the same session                                                                   | Source: H06, H12, G1-14; H06 covered, H12 planned                                     |

| active/paused/budget-limited goal not complete, queue non-empty -> a verifier round ends or click queue "Resume" | The queue is still not consumed; explicit pass or fail-open must first update the target to complete, and only then does FIFO consumption start; a manual cancel does not count as a pass | Source: H08, G1-10; to add                                             |
| Goal verifier requesting -> click stop -> send ordinary text                                         | The verifier ends and the main runtime state is cleaned; the new text immediately enters a new provider request, not blocked by the leftover verifier | Source: H09; covered                                                                  |
| Stopped goal verifier -> manual `/compact` -> send ordinary text after compaction                    | Compaction and the later send are allowed and not locked by the old verifier or the old active goal                                                  | Source: H10; covered                                                                  |
| guide mode, goal verifier running -> send guide text                                                 | The verifier cannot be steered; the same input keeps its identity and falls back to the future queue, not lost, goal not stopped, no parallel request | Source: H11, G1-14; partial                                                           |
| Active goal -> click pause in the summary                                                            | The goal becomes paused and the accumulated time freezes; any current goal work is terminated, but the queue is neither cleared nor consumed per ordinary Stop rules | Source: H13, G0-07; covered                                                       |
| Paused goal -> click the triangle to resume                                                          | The goal becomes active again, accumulated time is not reset, and it continues along the original goal continuation                                  | Source: H14, G0-08; covered                                                           |
| Goal completed -> open or restore the status panel                                                   | Shows the frozen time and a green completed icon and no longer pause/resume; desktop live and the restored result agree                              | Source: H15, H16, G0-09, G0-10; partial                                               |
| Plan mode -> submit `/goal` or an alias in the composer                                              | Only a hint that goal is unavailable in Plan mode; the input text is kept, no session created, no history written, no goal command sent             | Source: PG01, G0-11; covered                                                          |
| Session A has an active/queued goal -> switch to B -> switch back to A                               | B does not show A's goal or queue; back in A its own target and queued goal are restored; a new session does not inherit a historical goal/queue    | Source: G4-01-G4-04; covered                                                          |
| Queued goal waiting for consumption -> switch the model or thinking depth in the current session     | When the goal actually executes it uses the latest model configuration of the current session                                                       | Source: G1-08, N02; covered                                                           |

## 4. Fork

| Operation path                                                                                       | Expected result                                                                                                                                                  | Note                           |
| ---------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------ |
| Completed session -> click fork on a stable final assistant message                                  | Creates a child session; copies the visible history up to and including the fork point and the fork-point configuration; the child queue is empty                 | Source: C06, E01, FX01; covered |
| Assistant streaming reply stopped -> try to fork the interrupted partial                             | The fork entry is unavailable or the command is rejected; no child is created and the parent queue stays paused                                                  | Source: E02, E03, FX02; covered |
| Try to fork a user message, tool block or timeline marker                                            | No fork entry is offered and no child is created                                                                                                                 | Source: E04, E05, FX05; covered |
| Parent session running, but an earlier stable assistant exists -> fork that stable message           | The child copies only the stable prefix; the parent's current primary/subagent/goal work, queue and workspace keep running as is                                  | Source: A09, E06, FX06; partial |
| Parent session had a goal before the fork point and still has a queue -> fork a stable assistant      | The child inherits the target, iteration and verifier timeline before the fork point; the parent queue is kept and the child queue is empty                      | Source: E07, FX03, G3-07; covered |
| Assistant has only a failed/error partial and no stable completed state -> try to fork               | The fork entry is unavailable or the command is rejected; no fork timeline written                                                                               | Source: E08, FX04; to add      |
| Edit the last user message and finish the rerun -> fork the assistant of the new branch              | The child contains only the edited active branch, not the old user/assistant branch that was rewound                                                             | Source: E09, FX07; covered     |
| Within one logical turn there are tool calls and file changes first and assistant text only at the end -> fork the final visible assistant | The child copies the final reply, the matching tool blocks and the file facts produced by that turn together on the logical-turn boundary, without truncating at an intermediate raw assistant | Source: E10, FX08; covered |
| Parent session has a running background Bash/subagent or an unconsumed background result -> fork a stable assistant | The child does not copy live background work, a pending result or a continuation inbox; a background completion wakes only the parent session                 | Source: FX09, K02; to add      |
| Compact is running -> try to fork; or try to fork the current unclosed assistant                     | The compact operation lock rejects fork; the current streaming/interrupted/failed/middle assistant is also not forkable, while the rule for an earlier stable target is unchanged | Source: FX10, PV4-14; partial |

## 5. Edit and conversation reset

| Operation path                                                                  | Expected result                                                                                                                                       | Note                                            |
| ------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| Completed session -> click Edit on the last real user message -> modify -> send inline | The original session reruns from that input and later history is replaced by the new active branch; the main input box draft takes no part in this edit | Source: C07, D01; covered                     |
| Current active work running -> edit the last real user message and submit       | First cross the Stop barrier so the current work reaches a terminal state, then rerun in the original session with the original input type; the existing queue is kept and not auto-consumed | Source: A10, PV4-13; planned          |
| Assistant stopped -> edit the matching sent user message and submit             | Finds the original message by stable messageId and reruns immediately; the interrupted reply is replaced by the new branch, with no turnIndex parse error | Source: D02, D10; covered                      |
| Session interrupted with a paused queue -> edit the last real user message      | Edit reruns; queue IDs, order and content are kept as is and auto-consume stays off                                                                   | Source: D03, PV4-20; covered                   |
| Edit rerun in progress -> send ordinary text, `/goal ...`, `/compact`           | The three inputs enter the future queue and do not interrupt the current edit rerun; compact executes only when its turn comes                       | Source: D04-D06; text/goal covered, compact planned |
| Edit rerun in progress -> edit the last real user message again                 | First stop the current rerun, then rerun with the latest edited text; the queue is kept                                                               | Source: D07; covered                           |
| Try Edit on a non-latest real user input                                        | The UI offers no entry or the command is rejected; the active branch cannot be rolled back to an older input                                          | Source: D11, PV4-10; formal UI + command evidence to add |
| Try Edit on an assistant or tool message                                        | No Edit entry offered                                                                                                                                 | Source: D08, D09; covered                      |
| Latest input is `/goal ...` -> click the unified Edit -> modify and submit      | Still replayed by goal intent, updating target/iteration; it cannot degrade to ordinary text and produces no extra goal marker                       | Source: PV4-12, PV4-13; planned                |
| Latest input already covered by one or more compact summaries -> Edit and submit | An append-only branch cut in the original session: old records are kept but leave the active projection, and invalidated compact-derived state no longer enters the model context | Source: PV4-11, PV4-19; covered         |
| Latest input covered by compact has attachments -> Edit the text and submit keeping the attachments | The complete attachment intent is replayed: no workspace re-read, no attachment lost, no child created                                          | Source: PV4-18; covered                        |
| Latest turn has a safe file checkpoint -> choose "conversation + file reset" (对话 + 文件重置) | Restores files in reverse order, trims the conversation and resends in the original session; no child is created and no intermediate workspace-only success state appears | Source: PV4-21; covered           |
| Files modified externally or checkpoint unsafe -> try the combined reset -> choose "reset conversation only and send" (仅重置对话并发送) | The first operation is blocked in a structured way and files/conversation are unchanged; the downgrade uses a new commandId, resets only the conversation and resends | Source: PV4-22; partial       |
| The trimmed turn started a background Bash/subagent -> Edit the latest input    | First cancel that turn's cancellable background work; if cancellation cannot be confirmed the whole operation fails; a late completion must not enter the new branch, queue, UI or model context | Source: PV4-23; covered               |

## 6. Compact

| Operation path                                                                   | Expected result                                                                                                                                                    | Note                                                          |
| -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------- |
| Completed or interrupted session, queue empty -> manual `/compact`                | Enters manual compaction and shows a started marker; on success the marker becomes success and the session is continuable                                         | Source: C05, F01, F02, F08; covered                           |
| Paused queue exists -> manual `/compact`                                          | compact is appended to the tail of the queue and stays paused; no text queue-disposal confirmation and no immediate compaction request                            | Source: B13, C09, F03; planned                                |
| Current turn or foreground subagent/goal work running -> manual `/compact`        | Enters strictly in FIFO as a compact-type queue item and does not stop the current work; enters the compact lifecycle only when its turn comes                    | Source: A08, H12, compact worksheet; planned                  |
| Manual compact running -> send ordinary text or `/goal ...`                       | The new input enters the future queue and does not interrupt compaction                                                                                            | Source: F04, F05; covered                                     |
| Compact running or a compact already in the queue -> send `/compact` again        | Explicitly rejected with a hint that compaction already exists; no new queue item, no second request, no ordinary user message shown                               | Source: F06, G07; covered                                     |
| Manual compact running -> click Stop                                              | The marker is marked interrupted; the session enters completed(interrupted), the queue is kept as is and auto-consumption stays paused                             | Source: F07; to add                                           |
| Manual compact request fails                                                      | No automatic retry; returns to the completed state before compact, keeping the queue and autoDrain; shows a failed marker and a retry entry, and text/goal/fork/edit/compact again are all restored | Source: F09; product ruled, E2E to add            |
| Ordinary send, head text, queued goal or edit rerun is about to run -> the system decides auto compact is needed | Auto-compress first; after success continue the original pendingAction, the order must not be reversed                                                | Source: G01-G04; partial, the real trigger window still needs a stable fixture |
| Auto compact running -> send ordinary text or `/goal ...`                         | The input enters the future queue; after the pendingAction completes it is consumed in FIFO order                                                                  | Source: G05, G06; covered                                     |
| Auto compact summary invalid the 1st and 2nd time, succeeds the 3rd               | At most 3 retries; the pendingAction is kept throughout and continues after the 3rd success                                                                        | Source: G08-G10; covered                                      |
| Auto compact fails 3 times in a row                                               | The retrying/failed marker is kept but the pendingAction continues without compaction; the circuit breaker takes effect and a successful manual compact resets the count | Source: G11; product ruled, E2E to add                  |
| Auto compact running -> click Stop                                                | Aligned with ordinary Stop: the pendingAction is kept as the current turn's interrupted user input and not copied back to the queue; all explicitly appended queue items are kept and consumption is paused | Source: G12; product ruled, E2E to add     |
| Auto compact just happened before a queued manual compact's turn                  | It still executes by the user's explicit intent; the runtime may return a noop marker but must not silently delete that queue item                                 | Source: compact worksheet; accepted, to be verified with the typed queue case |
