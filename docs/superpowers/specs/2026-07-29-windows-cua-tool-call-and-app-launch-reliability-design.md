# Windows CUA Tool Call and App Launch Reliability Design

> Date: 2026-07-29 (tool-name approach revised 2026-07-30)
>
> Status: confirmed
>
> Scope: Windows local desktop continuous source-development chain
>
> Related repositories: `z-code`, `C:\Users\dev\zcode-cua`

## 1. Runtime evidence and root cause

The model I/O and Agent logs of two failed sessions show that the official `zcode-cua` MCP was connected and
all 30 tools registered; neither the Helper nor the plugin-host was the cause.

- The current upstream baseline generates the provider-visible canonical name
  `mcp__plugin_zcode-cua_computer-use__*` from the generic MCP descriptor, but the provider/model returned
  `mcp__plugin_zcode_cua_computer_use__*` (both hyphenated segments turned into underscores), a name not
  declared in the request tool set. The registry looks up exact names and returned `Tool not found` before
  permission, hook and MCP dispatch.
- The alias added by the Windows port assumed the canonical name was `mcp__computer-use__*`, matching neither
  the current namespaced descriptor nor the authority set it requires from the production runtime: dead code.
  The upstream short-name descriptor belonged to a stabilization merge later rolled back (`9a80589fbd`); the
  current baseline is `0b0a27f92a` and later, and the old descriptor special case must not be cherry-picked
  from a rolled-back commit.
- `open_application({app:{name:"calc"}})` really launched Calculator, but its visible window is hosted by
  `ApplicationFrameHost.exe`; the Windows resolver allows only an exact launcher-executable match with the GUI
  candidate, so it safely refused the wrong rebinding. `Microsoft.WindowsCalculator_8wekyb3d8bbwe!App` is a
  usable AUMID, but the Windows system surface accepts only `name`.

Two independent gaps result: (1) the model response boundary validated "non-empty" instead of "an exact name
declared in this request"; (2) Windows packaged apps lack AUMID launch and exact window resolution.

## 2. Goals

1. Use the current remote upstream implementation as the only baseline: provider-visible names keep being
   generated by the generic descriptor; the current official CUA name is `mcp__plugin_zcode-cua_computer-use__*`.
2. Remove the short-name/underscore Registry alias added by the Windows port; no name not declared exactly in
   this request's tool set may reach permission, hook, event, history or MCP dispatch.
3. If and only if a wrong name uniquely corresponds to one canonical name under a "diagnostic-only comparison",
   and no model/tool-visible event has been committed, one corrective retry is allowed; the retry response must
   still hit the request tool set exactly.
4. When there is no unique match, the stream commit boundary was crossed, or the second response is still
   wrong, fail closed as a recoverable invalid model response with no alias routing.
5. Windows `open_application` accepts an AUMID and activates the packaged app through the native
   `IApplicationActivationManager`.
6. Resolve the target HWND/PID exactly through the window's `PKEY_AppUserModel_ID`; fail closed on no
   candidate or multiple-PID candidates.
7. Windows provides case-insensitive exact name aliases for a few built-in packaged apps; the first batch has
   only Calculator: `Calculator`, `Windows Calculator`, `calc`, `calc.exe` and `计算器` (Chinese for
   "calculator"), all converged to `Microsoft.WindowsCalculator_8wekyb3d8bbwe!App` before entering the same
   AUMID activation and read-back chain.
8. Keep the existing Win32 executable-name launch, full path validation, prelaunch snapshot, live
   revalidation and unique-new-candidate rule.
9. Fix the Windows skill copy: the AUMID is the packaged app's launch identity; later actions prefer the PID
   returned by `open_application`, and `ApplicationFrameHost.exe` is never treated as an AUMID.

## 3. Non-goals

Not changing `computer-use` to `computer_use`; no global hyphen/underscore normalization for arbitrary MCP
servers; no rewriting of an underscore wrong name into the canonical name; no change to the upstream
maintainer's `packages/ui` CUA renderer, Core result display, generic MCP descriptor, manifest or runtime
authority; no guessing apps by window title, running-app display name, basename, active state or enumeration
order (built-in packaged apps use only the code-maintained exact alias -> AUMID table); no change to the
30-tool manifest, MCP schema or macOS/Linux launch; no shell, PowerShell, `explorer.exe shell:AppsFolder` or
shortcut fallback; no SSH, WSL, Docker, remote workspace, mobile `/remote` or replayable change; no installer,
signing, auto-update or release loop.

## 4. Design choice

### 4.1 Tool names

- **A. Keep the Windows port's Registry alias** - rejected. It rests on the short name `mcp__computer-use__*`
  and cannot hit the current remote `mcp__plugin_zcode-cua_computer-use__*`; the production runtime also does
  not pass the authority set it needs. Even if matching were fixed, a direct Registry alias would turn
  out-of-contract model output into an executable call and hide the provider/model contract error.
- **B. Restore the rolled-back upstream short-name descriptor** - rejected. The short-name descriptor of
  `babdbd5e4c` belongs to the stabilization merge explicitly rolled back by `9a80589fbd`; the current upstream
  baseline `0b0a27f92a` did not reintroduce it. Cherry-picking only the descriptor would bypass the rollback
  boundary and leave two contradictory naming facts on one remote baseline.
- **C. Exact request-contract validation with one side-effect-free corrective retry** - selected. The model
  adapter already holds the exact `tools[].name` set when building the request; every tool name in a response
  must be byte-identical to a set member. The hyphen-to-underscore comparison is used only to decide whether a
  unique corrective candidate exists; it must not change the tool call, query the Registry, or form a
  permission or persisted name.

  If the first response hits a unique candidate before any visible text, reasoning, tool block or provider
  retry boundary is committed, abort and clean up the original physical request and re-issue one request with a
  non-persisted system corrective instruction. The instruction lists only the allowed exact canonical names and
  no tool arguments. The second response gets no spelling-correction budget and must hit exactly; otherwise it
  fails as `InvalidModelResponse`.

  If a streaming response has already committed non-replayable events, no automatic retry happens and it fails
  directly, avoiding duplicated text or tool blocks. A non-streaming response has not yet committed anything
  externally and can use the same one-shot corrective rule.

```text
current upstream descriptor
    |
    +-- mcp__plugin_zcode-cua_computer-use__list_apps
    |
provider request tools[] (exact name set)
    |
model/provider response
    |
    +-- exact hit --------------------------> tool event -> permission -> MCP
    |
    +-- name outside the request
            |
            +-- unique spelling candidate and no event committed yet
            |       |
            |       +-- discard this response, zero tool side effects
            |       +-- temporary corrective instruction, at most one retry
            |       +-- only an exact hit on the second response may execute
            |
            +-- ambiguous / committed / second response still wrong
                    |
                    +-- InvalidModelResponse, fail closed

upstream UI/result-display name comparison
    |
    +-- handles only already accepted canonical tool events, not routing, unchanged
```

### 4.2 Windows packaged app

- **A. Match by name/title/basename after launch** - rejected. Window titles are localizable, duplicable and
  controllable by the target app; `ApplicationFrameHost.exe` hosts several packaged apps at once and is not a
  stable identity for Calculator.
- **B. Accept the launcher PID or the first active candidate directly** - rejected. The launcher may exit, hand
  off or be reused; active/first-enumerated cannot prove it belongs to this call.
- **C. Native AUMID activation and exact HWND property lookup** - selected. The native addon adds two
  Windows-only internal ABIs:
  - `activateApplicationByAumid(aumid)`: calls `IApplicationActivationManager::ActivateApplication`;
  - `applicationInfoByAumid(aumid)`: enumerates visible top-level HWNDs, reads `PKEY_AppUserModel_ID`, matches
    the AUMID case-insensitively and exactly, and dedups by PID.

  An already-present unique visible app with the same AUMID may be returned directly; otherwise activate, then
  poll within a bounded budget. Zero candidates keep waiting; multiple-PID candidates or an exhausted budget
  fail. This branch does not conflate the AUMID with an executable path.

```text
open_application({bundle_id: AUMID})
    |
exact HWND PKEY_AppUserModel_ID lookup
    |
    +-- unique live PID --> optional explicit activation --> return PID
    |
    +-- none/ambiguous
            |
            +-- native IApplicationActivationManager
            |
            +-- bounded poll exact AUMID
                    |
                    +-- unique live PID --> return PID
                    |
                    +-- none/ambiguous --> fail closed

open_application({name: "notepad.exe"})
      |
existing Win32 full-executable identity path remains unchanged
```

#### Calculator exact name aliases

A restricted exact alias table is used instead of guessing windows after launch. `Calculator`,
`Windows Calculator`, `calc`, `calc.exe` and `计算器` are normalized to the Calculator AUMID in the Windows
broker before any side effect; the rest fully reuses choice C. This fixes the first failure where the model
treated a display name as an executable, and avoids a false failure when `calc.exe` has already opened a window
whose launcher executable differs from `ApplicationFrameHost.exe`.

Alias comparison only trims and case-folds; no substring, edit distance, window-title search or enumeration-order
fallback. Unknown names keep entering the ordinary Win32 executable branch with the original validation.

## 5. Component boundaries

### `z-code`

- The MCP descriptor and the provider-visible contract keep the current upstream hyphenated namespaced names.
- `registerMcpTools` sets no alias for model spelling errors.
- Allow/deny still decide on the canonical descriptor name.
- The adapter validates streaming and non-streaming tool calls against the exact set of this request's tools.
- The one-shot corrective prompt exists only in the physical retry request and is not written to conversation
  history.
- The upstream comparison logic of the UI renderer and Core result display does not take part in execution
  routing and is unchanged.

### `zcode-cua`

- `windowsSystemSurface` distinguishes an executable name from an AUMID.
- The Windows broker normalizes supported built-in packaged app exact name aliases to AUMIDs before launch;
  the table reads no window state and does not change non-Windows semantics.
- `helperMain` injects into the system surface only the Windows native ABI already loaded by the current
  process.
- The native addon owns Windows COM activation and HWND property-store queries.
- backend/resolver keep the bounded wait, uniqueness, live revalidation and unified result.
- The public MCP schema gains no Windows-specific field; `app.bundle_id` carries the AUMID input.

## 6. Safety and compatibility invariants

- No CUA or third-party MCP has a hyphen/underscore execution alias.
- A name outside the request contract cannot enter allow/deny, permission, hook, scheduler, event, history or
  MCP.
- Multiple candidates in the diagnostic comparison must not be guessed; fail.
- The corrective retry happens at most once, and only on an attempt that has not committed non-replayable
  events.
- Logs record only the wrong name, the unique candidate and request/trace identifiers, never tool input or
  credentials.
- An AUMID must be one non-empty identifier without control characters; never concatenated into a shell
  command.
- An exact name alias maps only to a code-fixed AUMID; identity is never derived from window title, the
  current active app or `ApplicationFrameHost.exe`.
- AUMID lookup accepts only exact property evidence; the `ApplicationFrameHost.exe` path alone is not success
  evidence.
- The Win32 path branch does not weaken the existing full-path, snapshot, uniqueness and TOCTOU protections.
- Windows AUMID activation may bring the window to the foreground by the OS; the implementation sends no extra
  mouse, keyboard or focus events and does not promise a background launch equivalent to macOS `open -g`.
- The mapping between `urls` and an AUMID is not guessed in this phase; their combination fails closed.
- Tool-name validation belongs to the shared model adapter; desktop continuous, subagent and web remote
  replayable must keep the same exact contract. Snapshot, queue, owner, lease, workspace identity and remote
  transport semantics are unchanged.

## 7. Tests

**Exact model tool-name contract:** the current upstream descriptor keeps generating
`mcp__plugin_zcode-cua_computer-use__list_apps`; names in the request tool set pass streaming and non-streaming
validation; `mcp__plugin_zcode_cua_computer_use__list_apps` is rejected before Registry, permission, hook,
event, history and MCP; a unique candidate with no event committed retries once and executes once after the
second response returns the exact name; a second wrong response, no candidate, multiple candidates or committed
non-replayable events fail closed; third-party MCP gets the same validation with no CUA special case; main
agent and subagents share it, and desktop continuous / web remote replayable add no synchronized state.

**Windows AUMID:** `windowsSystemSurface` accepts a bundle ID/AUMID and calls the injected native activator; the
five Calculator exact aliases enter the AUMID branch and never call Win32 `openRunner(["calc"])`; case and
surrounding whitespace normalize while substrings, unknown and similar names do not hit; AUMID + URLs, an empty
AUMID and a missing native activator fail; the backend prefers a unique live app with the exact AUMID and after
a fresh activation accepts only a unique exact-AUMID PID (zero, multiple PIDs and property read failure fail
closed); existing Win32 full executable identity tests keep passing; compiled addon exports match the source
contract.

## 8. Acceptance

- Remove the ineffective CUA alias added by the Windows port, the short-name constant usage and the matching
  wrong tests.
- Targeted tests, `pnpm typecheck` and `pnpm lint` pass in both repositories.
- The `zcode-cua` Windows native addon is rebuilt on this machine.
- After source desktop starts, the latest model request declares only the upstream namespaced hyphenated names;
  if the first response returns an underscore wrong name, the log shows one side-effect-free corrective retry
  and it no longer ends in the Registry `Tool not found`.
- A direct broker smoke can open or reuse Calculator through its AUMID and read `get_app_state` with the
  returned PID.
- Cleanup terminates only test processes started this round, not the user's existing apps.
- No SSH, WSL, Docker, remote workspace or mobile remote control is started or modified.
