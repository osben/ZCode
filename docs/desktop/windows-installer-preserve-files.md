# Windows Updates: Preserve Files in the Installation Directory

## Goal

Managed in-place updates may remove only files declared as owned by the ZCode release package. Unrelated files placed in the installation directory by users or other programs must be preserved. The installer must not use `RMDir /r $INSTDIR` to clean up this update path. This specification does not guarantee preservation for legacy upgrades without a manifest.

## Ownership Manifest

- During packaging, generate `.zcode-install-manifest` at the root of the Windows app output directory. It contains one relative file path per line, uses backslashes, is UTF-8, and ends with a newline. The manifest lists only files actually included in the release package.
- Install the manifest with the app package so the old uninstaller can read it during the next update. The manifest itself is also a ZCode-owned file, but the cleanup walk skips its self-referencing entry so the currently open metadata is not deleted; a later install still writes a new manifest.
- `customRemoveFiles` deletes files listed in the manifest only; it must not remove the installation directory root or any unlisted files/directories. On deletion failure, immediately stop the old uninstaller and preserve remaining files for the installer to report the failure.
- If the manifest is missing or unreadable, use a migration-safe policy: the current uninstaller deletes no files from the installation directory, continues installation, and leaves old-version files in place. Note that an initial upgrade from a version without a manifest still runs the old uninstaller first; that uninstaller may recursively delete the entire directory. This specification does not promise preservation of unrelated files on that path; a separately implemented, rollback-capable legacy migration is required.
- The packaging process generates the manifest; it is not user input. The implementation must still reject absolute paths and paths containing `..` to prevent a malicious or corrupted manifest from deleting files outside its scope.

## Version Boundaries

- The manifest marks availability of ownership-based cleanup. In-place updates between versions are covered by the strong guarantee starting with the first version that includes a manifest.
- During the first upgrade from a legacy version without a manifest, the old uninstaller may still clean up the entire tree or return a native error message. This specification adds no migration backup, recovery, or rollback for that path; users can upgrade by uninstalling and reinstalling or manually migrating files.
- As versions advance, add protection and diagnostics only for failures that remain reproducible between new versions. Do not attempt one-time compatibility with every historical installation state.

## Compatibility and Boundaries

- Ordinary uninstallation (without `--updated`) continues to use electron-builder's default flow; this specification changes only the cleanup phase for in-place updates.
- Data directories outside the installation directory (for example, `%USERPROFILE%\.zcode`) are outside the manifest and are not cleaned up during updates.
- The manifest lists files only and does not actively delete empty directories, so unrelated files and directory structures remain intact.

## Verification Requirements

- An isolated NSIS fixture must verify: listed old app files are deleted when a manifest is present and unlisted `user-data.txt` is preserved; all old files are preserved when the new uninstaller cannot find a manifest; and if a Windows file handle blocks deletion, the process returns nonzero and writes `cleanup-failed` with a numeric PID. Legacy recursive cleanup by the old uninstaller is outside this phase.
- Use the real NSIS compiler corresponding to electron-builder in the fixture. Do not write to a real installation directory, desktop, Start menu, or product registry.
- The compile fixture keeps the production header order: the custom include loads first and the uninstaller constants of `common.nsh` are defined afterwards; functions that reference the constant are deferred until `customHeader` expands, and the fixture must not define the constant early to mask packaging warnings.

## Recovery from an old-uninstaller cleanup failure

Before calling the old uninstaller, the new installer must, through a native helper shipped with the package, check for main-program processes under the actual old installation directory by full path, terminate leftover same-image processes such as Crashpad/renderer and confirm their exit; it must not blindly kill by name or parent PID. Candidate paths are identified with query access first; terminate access is requested only after a path matches the target. The termination handle must re-verify the path, and the same handle is then used to terminate and wait. A same-named process in another directory must not block installation by refusing terminate access. When a candidate process's path cannot be read, the target process cannot be terminated, or the recheck finds a leftover, stop before the backup and record the stage and PID. The check does not depend on PowerShell or Add-Type; log writes are best-effort, a failure does not change the process-check outcome, and diagnostics stay on stdout/stderr.

The installer then reads the old manifest from that uninstaller's actual `InstallLocation` and copies the managed files that still exist to a unique backup directory beside the install directory. The manifest is saved separately once first; even if the manifest lists itself, the walk must not copy it exclusively again. No old file may be deleted before the backup attempt ends. The backup is optional protection, not a precondition of installation: on backup failure, log it, delete this run's partial backup on a best-effort basis and discard its restore reference, then continue with the old uninstaller and the rest of the installation. A partial backup must not be used for restore; if cleaning up a partial backup fails, record the actual path without a dialog and without exiting. A legacy installation without a manifest keeps following the legacy boundary above.

When the old uninstaller exits nonzero, restore the deleted files only if a complete backup succeeded; originals that still exist are not overwritten, to avoid touching locked files again. When this run has no complete backup, do not attempt a restore and do not claim the old version is intact; follow the old uninstaller's own failure handling. When restoring, verify relative paths against the files still present in the backup; Windows NSIS path normalization may return empty for a deleted target, and that must not skip a file to restore or falsely report restore success. After a successful restore the backup is cleaned up and the cleanup failure is reported; after a failed restore the backup path is kept and reported, and the installer must not claim the old version was fully restored. After the old uninstaller succeeds, this run's cleanup backup is removed. If that deletion fails, keep the backup path and record `cleanup-backup-delete-failed` — log only, no dialog blocking installation, and never claim it was deleted; a failed deletion of a partial backup likewise records the path, and its restore reference must be discarded. Do not enumerate or wildcard-delete `ns*.tmp` beside the install directory, because ownership cannot be proven from the name. Reclaiming historical backups after the installer is force-killed or after a power loss is not guaranteed this round. The protection targets the uninstall cleanup stage and promises no full install transaction for later extraction failure or power loss.

```text
old InstallLocation -> process close-out by handle + second enumeration -> try manifest backup -> run old uninstaller
                                               |                                    |            |- success -> best-effort backup deletion -> extract new package
                                               |                                    |            `- failure -> restore only with a complete backup -> report the error
                                               |                                    `- failure -> log, discard the partial backup, continue with the old uninstall
                                               `- failure -> original directory not deleted, not backed up; report PID and stage
```

The prompt for exhausted old-uninstaller retries must describe a cleanup failure and the exit code and must not be replaced by "application cannot be closed"; that prompt stays only for a real process-check failure. Interactive retry/cancel is kept; the prompt differs by whether a complete backup exists: with a backup it promises that cancel restores the deleted files; after a failed backup has been discarded, cancel only exits the installer and the prompt must state clearly that no automatic restore is possible — it must not promise a restore that does not exist. A silent install cancels by default. Both paths keep the installer log. The retry prompt and the final cleanup-failure prompt after cancel follow the installer language and must not show fixed Chinese at the end of an English installer flow.

Acceptance uses an isolated install directory: the manifest lists the main program first, then a deletable file, and last a file opened exclusively. After the old uninstaller runs, assert nonzero, the first two restored byte for byte, the locked file unchanged and unrelated files unchanged; after the handle is released a retry can finish the cleanup. Also test that after a backup write failure, once the faulting handle is released, the old uninstall and the new payload write still succeed; that with no complete backup and a failed old uninstall the partial backup is not restored; and that a backup-deletion failure after a successful cleanup still writes the new payload. Additionally test no manifest, successful cleanup, an unwritable restore destination and the exhausted-retry prompt.

The self-referencing manifest regression must include normal cleanup, recovery when the old uninstaller fails after the backup, and deleting the backup after a successful cleanup.

### Self-reference compatibility of old uninstallers

The uninstaller of an old full package may not skip the manifest it is reading. The new installer must first keep the original manifest and the managed files; after a successful backup it atomically replaces the manifest for the old uninstaller with one that has only the self-reference removed; if the backup or replacement fails, discard this run's backup and continue with the old uninstall, without promising restore protection for that run. When a complete backup succeeded and the cleanup fails, the original manifest bytes are restored even if the manifest file still exists. The full-package regression covers an upgrade with the original old uninstaller's self-referencing manifest and byte-for-byte identity of the original manifest after a failure.

Isolated Windows 11 x64 full-package verification this round: after adding a self-reference to the manifest of the original 3.16.2, the old implementation's upgrade returned 2; with the fix, the full NSIS installer restored 1,430 files and the original manifest bytes when the auto-update cleanup failed, then the original upgrade succeeded, and a reinstall over it with the new self-referencing manifest also succeeded. The managed main program, app.asar and tools match the full payload hashes, unrelated files are kept, and the temporary backup is cleared on success. The installer is not configured with the official signature, so this result says nothing about the official signing trust chain, power loss or extraction-failure rollback.
