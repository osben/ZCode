# Windows Update Install Handoff

## Goal

Windows desktop keeps using `electron-updater` to download and verify updates, and hands off to the NSIS installer generated by `electron-builder 26.8.1` through `quitAndInstall()` for an in-place install. There is no custom downloader, delta algorithm or install engine. This spec only closes the boundary between ZCode's multi-process exit and the NSIS shortcut-preservation policy.

## Handoff Order

```text
update-downloaded
  -> renderer keeps "Restart to update" pending; no fixed short timer may re-enable it
  -> main marks update_install
  -> stop app-level background services
  -> Cron Scheduler and local/SSH/WSL/Docker/Bot Hosts enter the unified exit barrier in parallel
  -> wait at most 9 s (forced kill triggers at 7.5 s)
  -> live-scan runtimes still referencing bundled resources, taskkill the matches
  -> electron-updater.quitAndInstall()
  -> NSIS CHECK_APP_RUNNING does the final install-directory process check
  -> NSIS overwrites, preserving existing shortcut identity
  -> finish page launches ZCode.exe in the new install directory directly
```

Main must not kill by the whole install directory before `quitAndInstall()`, because the renderer, GPU process and main itself also run from that directory. Main only handles host/agent/runtime it owns. The final install-directory check after the app exits stays with NSIS's native `CHECK_APP_RUNNING`.

## Behavior Constraints

- Update install reuses the single reclamation barrier of normal app exit. The local Host, Hosts being released, and SSH/WSL/Docker/Bot Remote Hosts use an explicit `update-install` policy: wait at most 9 s, covering the 7.5 s forced-reclaim point. Normal Windows exit uses a separate 4 s force-kill / 4.5 s total wait budget; that short budget must not be applied to the first-entry update install. If an update request races an already-started normal exit, the existing short timer is not rebuilt; the update waits on that barrier, then continues with the live resource scan and installer handoff, and does not reject the update because of leftovers or mixed budgets. The 4 s Windows normal-exit budget applies to the Local Host only; Remote Hosts always keep the 7.5 s force-kill and 9 s wait upper bounds so their serialized service/remote-connection shutdown is not cut short by an ordinary window close. The Cron Scheduler's 1.5 s shutdown fallback runs in parallel with Host cleanup inside the same 9 s barrier; it is not appended serially before the Host barrier. After shutdown starts, no CronRun is dispatched to a Host. Windows-specific cleanup must not append another Host wait. It performs one centralized `taskkill` only for processes the post-barrier live scan still finds referencing bundled resources, and keeps 750 ms for Windows to release install-resource handles. Host/Agent PIDs registered before the exit barrier are historical transient numbers and must not be used as kill identity across the async exit boundary.
- Bundled-runtime leftovers found before the update must be recorded with PID, executable path and command line, and a best-effort process-tree reclaim attempted. A scan failure, nonzero `taskkill`, or leftovers after a rescan log a warning and the upgrade continues; auxiliary cleanup must not become a new blocker for the user's upgrade.
- After the user clicks "Restart to update", the renderer must not release the button lock with a fixed 5 s ACK timer. Exit preparation and the Windows installer handoff can exceed that time. On the success path the button stays disabled until the app exits. When the ready state is invalidated or exit preparation fails before the installer is called, main must reject the renderer IPC. The renderer restores the button on reject, or when it observes the update state leaving `update-downloaded`, avoiding a permanent pending state and repeat clicks.
- The PowerShell process scanner must exclude the PowerShell process running the query. The resource path appears in the scanner's own command line as query script text; it must not be misread as resource usage, and the scanner PID must not be handed to the later `taskkill`.
- NSIS's final running-app check is not bypassed. That check does not promise to cover every independent runtime. The product accepts the residual risk that in rare cases a persistently running runtime leaves install resources incomplete, and keeps evidence through the new version's startup integrity diagnostics.
- In-place updates preserve the user's choice about shortcuts: a shortcut the user deleted is not recreated.
- Running the installer manually over an existing version (including a downgrade) has no `--updated` argument. In an assisted installer that allows changing the install directory, electron-builder 26.8.1 therefore skips `KeepShortcuts`; the old uninstaller then calls `UninstShortcut` and unregisters the Windows pinned item, and a same-name `.lnk` recreated by the new installer does not restore the pin. After the install-directory page is generated, the preprocess switch used only for that page must be removed so the later old-version uninstall handoff tries to pass `--keep-shortcuts` on both the manual-overwrite and auto-update paths. The guarantee covers only an overwrite install into the original install directory. When the user changes the install directory, electron-builder creates shortcuts to the new location and migration of the old pin is not promised.

  ```text
  manual overwrite (no --updated)
    -> keep old shortcuts and run the old uninstaller with --keep-shortcuts
    -> install the new version
    -> keep the original .lnk / pinned identity
    -> if the inherited target is invalid, repair the .lnk in place
  ```

- On an in-place update, Start menu and desktop shortcuts are first preserved by electron-builder's `KeepShortcuts`. ZCode's `customInstall` must read the existing `.lnk` target: when it already equals this run's `$appExe` it is kept as is and `CreateShortCut` is not called again; only when the target differs, is empty or is unreadable is it repaired in place to `$appExe`. Rationale: unconditionally overwriting a `.lnk` changes the shortcut object the Shell observes and, on some Windows 11 versions or cache states, loses the "All apps" index or the user's pin, while never repairing leaves historical wrong targets broken after upgrade.
- After a conditional shortcut repair the stable AUMID must be rewritten and Windows Shell notified with `SHCNE_UPDATEITEM`; a shortcut the user deleted is still not recreated.
- When a shortcut name or menu folder must be migrated, electron-builder's built-in flow keeps doing the rename, AUMID write and `SHChangeNotify`; the `.lnk` must not be silently modified after it notifies the Shell.
- The assisted-installer finish page must not depend on a `.lnk` that may have been kept from an old version; it launches `$INSTDIR\ZCode.exe` directly.
- `config.json.lock` is the service layer's cross-process atomic-write lock, not part of the Electron updater. A waiter's own wait duration only decides when to return a timeout and is not evidence that the current lock is stale. An owner whose PID is alive must not be forcibly taken over by a runtime waiter; normal concurrent writes stay serialized.
- A crash before the unique owner file is written can leave an empty lock directory. An empty directory, or a corrupted directory without a valid unique owner, uses a short default grace of 100 ms, and the effective grace must not exceed half the current wait budget, so it is reclaimable within one write wait. After the creator writes the owner it must verify the directory is still the instance it created, so a resumed pause cannot write into a lock directory rebuilt by a later writer.
- The PID and creation time in lock metadata are untrusted input. The creation time is accepted only if finite, non-negative and at most 5 minutes ahead. An invalid value falls back to the equally validated owner-file mtime; if both are invalid, staleness is counted from the current observation time. That observation time must be bound to the current lock instance and reset when the instance is replaced; it must not reuse the waiter's startedAt from when it began contending on an old lock, and must not restart on every poll. Corrupted or future timestamps must never cause a permanent lock.
- The current update install handoff does not enumerate or delete `*.lock` in the data directory. If a PID is reused, an old lock may keep timing out; this is an accepted residual risk. If update-time lock cleanup is added later, it may run only after the relevant processes are confirmed exited and must not become a general runtime force-unlock rule in `atomicWriteText`.

## Failure Boundaries

- Installer handoff admission and recovery (upstream 3.15.3 parity): quit-and-install admission tracks an explicit phase (idle/preparing/installing/recovering) instead of an in-flight boolean. With electron-updater 6.8.9, `quitAndInstall()` does not throw: synchronous `doInstall()` failures and asynchronous Windows NSIS launch failures arrive through the generic `error` event (the latter after `quitAndInstall()` has already returned). While the phase is locked, new checks are blocked, the check already in flight at admission is awaited before the handoff, and its error event is suppressed as check-originated noise. Any remaining `error` event is treated as an installer handoff failure: main clears the ready state, reports it, and relaunches the app ("install failed after shutdown started: relaunch app") instead of leaving a quitting app that never installs. The resolved release channel is kept while the phase is locked; a failed exit preparation resets the phase so a later install request stays retryable.
- Download, signature, SHA verification and installer-launch failures stay with `electron-updater`'s error state.
- host/agent exit details go to the main log. When NSIS cannot close a process it does not continue overwriting the install directory.
- The Windows bundled-runtime scan and force kill are fail-open: a PowerShell query failure, timeout, kill failure or leftovers after rescan only warn and do not interrupt `quitAndInstall()`. Upgrade reachability takes priority over a hard integrity gate for auxiliary scanning.
- The atomic-write lock must not expose the brief `EEXIST` of the underlying `open(..., "wx")` directly to the user; first reclaim locks left by exited owners. Normal contention waits at most 8 s; an active owner past that returns a lock timeout. Takeover is allowed only when the owner has exited, or the lock lacks a valid PID and the current lock itself is stale. The waiter's wait time on an old lock must not be used to judge a later new lock. Insufficient delete permission returns a clear error; infinite retry is forbidden.
- An exhausted wait budget always returns `ZCODE_FILE_LOCK_TIMEOUT`. The code is defined by `@zcode/shared`, and UI/service consumers recognize transient lock contention by code, not by the message happening to contain `config.json.lock`.
- The sessions-index subscription is an idempotent read and the UI layer may retry it on lock timeout. provider/settings writes already wait and recover inside the atomic-write entry; non-idempotent writes are not blindly replayed by upper layers, and a failure keeps a clear error for the caller.
- On new-version startup the bundled-runtime integrity diagnostic keeps running, to distinguish missing install resources from invalid shortcuts.

## Verification Scope

- Windows `installer.nsh` must be compiled in an isolated test using the real NSIS compiler, include and plugin directories matching electron-builder 26.8.1. Source-string assertions alone are not enough to judge that macros work.
- The NSIS isolated fixture runs the in-place update macros in a temporary install directory: desktop/Start menu shortcuts whose target is already correct keep target, arguments and Shell identity; shortcuts with an invalid target are repaired to `$appExe`; shortcuts the user deleted are not recreated, and `$launchLink` must equal `$appExe` directly. The fixture must not write to the real desktop, Start menu, ZCode install directory or product registry.
- The full-installer smoke test still covers macro insertion points in the electron-builder generated script and a real NSIS in-place install. The isolated fixture quickly catches variable-scope, label, plugin and shortcut-semantics regressions without rebuilding the full app package.

Scenarios:

- Windows in-place update: local/Remote Host exits normally, Host needs forced exit, bundled-runtime child process leftovers, and the PowerShell query process must not match itself.
- Shortcuts: Start menu/desktop shortcut target correct, invalid, or deleted by the user; only invalid `.lnk` files are repaired.
- Finish page: with an old `.lnk` present, the exe is still launched directly from the new install directory.
- Atomic-write lock: concurrent writes to the same target; owner crash leaving a fresh lock; a lock past the stale threshold; a new token taking over during old-lock waiting must not cause the new lock to be deleted by mistake; a later empty-directory/ownerless lock must not inherit the old wait duration; an empty lock directory left by a crash before the owner was created; invalid PID/timestamps reclaimed by first observation time per lock instance.
- macOS/Linux do not enter the Windows install handoff branch; atomic-write lock behavior stays consistent across platforms.
