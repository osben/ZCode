# ZCode Feature and Third-Party Component Notices

This notice applies to the source code and build artifacts published in this repository. Features, permissions, storage locations, and network behavior differ across runtime forms; do not interpret the defaults of one form as a unified setting for the entire project.

## 1. AI Output, Execution Permissions, and Automation Risks

AI-generated code, commands, explanations, files, and recommendations may contain errors, omissions, security defects, or third-party rights issues. Check actual files, command exit statuses, tool results, and tests. A model's claim that work is "complete," "handled safely," or "authorized" is not evidence or proof of authorization. Before important actions, review the target, recipient, and impact, and keep recoverable backups.

Files, terminals, Git, Agent tools, and external processes can read and write files, start processes, and access the network within the operating-system account permissions of the system where they run. In Web or remote workspaces, an operation may run on a server, SSH host, WSL, or in a container; the device showing the current page does not establish where execution occurs. The shared Agent execution adapter does not provide a default operating-system sandbox. A working directory, workspace identity, Git worktree, browser-page isolation, or Node REPL runtime context must not be treated as a system-level isolation guarantee for all tools.

The shared runtime configuration defaults to `build` permission mode. When the standalone CLI runs a non-interactive task through `--prompt`, it uses `yolo` if `--mode` is not specified. Interactive and desktop sessions, resumed tasks, and hosts may each use their own configured, saved, or passed-in mode. Whether an action requires confirmation depends on tool declarations, permission rules, and runtime mode. `yolo` without the read-only planning constraint allows ordinary tool operations; interactive tools and tools that explicitly require confirmation still follow their own rules. Model-tool approval is not an application-wide permission switch; it does not imply that terminal operations, plugin processes, or update downloads use the same approval flow. See [CLI prompt modes](apps/zcode-cli/packages/cli/src/run.ts#L486) and [tool permission checks](apps/zcode-cli/packages/core/src/permission/service.ts#L97).

## 3. Local Data, Logs, and Credentials

Data may be stored separately on desktop devices, in browsers, on the CLI host, in SSH/WSL environments, and in external services. Desktop and server data directories depend on runtime and launch configuration and may contain settings, sessions, attachments, caches, task records, plugins, and logs. The standalone CLI's default session database is `~/.zcode/cli/db/db.sqlite`. Closing a window, signing out, uninstalling the client, or deleting one workspace should not be understood to clear all copies in other environments, independent data directories, backups, or external services.

Memory defaults and entry points differ: memory is enabled by default in the standalone CLI configuration and disabled by default in Desktop settings. When enabled, it can analyze saved sessions, persist memories, and reuse them in later tasks; related extraction or organization may create additional model requests. Automation plans, run records, and unfinished tasks also have their own persistent locations. Recovering those records does not guarantee that earlier external operations were undone or can be fully replayed.

Shared Agent model input/output logs are written locally by default in development and production, except in test environments. Logs may contain prompts, code, context, tool arguments, and model responses. Request headers and some image/video data are redacted, but not all user text is guaranteed to be redacted. Production uses rotation and truncation by default; explicitly enabling full retention changes that behavior. The Desktop main process, Host, scheduler, Web service, and remote daemon also have their own logs and crash records. A per-log limit does not establish a project-wide retention period.

Credential storage mechanisms also differ. The CLI shared credential file uses encryption, with a default key that can be derived from local environment information; the read path also accepts plaintext records. Desktop/Node service credentials likewise use locally encrypted files with configurable or environment-derived keys, not the system keychain. Web OAuth credentials may be stored in localStorage. Model configuration, environment variables, plugin/MCP settings, SSH configuration, and data synchronized to remote environments may also contain valid credentials. Do not treat all these stores as a system keychain, hardware isolation, or a guarantee that data "never leaves the local machine."

The embedded browser uses persistent browsing data; explicitly importing Cookies and LocalStorage from another browser may give it the corresponding logged-in state. Clearing the cache and clearing all site data are different operations. Browser history, downloaded files, web recording artifacts, and model logs may not be removed by the same cleanup entry point. Do not write real keys or tokens to version-controlled files. Before copying logs, submitting feedback, sharing conversations, or backing up a data directory, review the recipients and scope to avoid sending real credentials, raw sessions, or private project content to a public repository or issue report.
