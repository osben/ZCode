# Build pipeline entrypoints

## Ownership and format

The checked-out Desktop remote runtime consumes the component manifests generated by
`scripts/prepare-prebuilds.mjs`: `packages/desktop/mock-cdn/releases/<version>/manifest-<target>.json`.
That script is the single owner of remote resource generation. The standalone Server CLI `stage`
command packages a different release layout and is not a substitute for the Desktop mock CDN
pipeline. Do not add the absent Source Server release protocol as part of an entrypoint repair.

Root `prepare:remote-assets` invokes that generator; the Desktop package alias forwards to the root
script so E2E and source development use the same command; `bootstrap:with-remote` uses the root
entrypoint too. `prepare:remote-assets:linux` selects only linux-arm64 and linux-x64; the default
command retains all four POSIX targets. A completed generation writes the per-target manifests after
its component artifacts. No task/session ownership, protocol, persistence or database migration
semantics change.

```text
Desktop build / E2E / bootstrap
  → root prepare:remote-assets
    → prepare-prebuilds.mjs (single generator)
      → runtime bundles + native binaries + notices
        → component archives + per-target manifests
          → existing Desktop remote loader
```

The Desktop tsup host bundle maps `host/tasksStorageWorker` to the existing
`src/host/tasksStorageWorker.ts`; the emitted `out/host/tasksStorageWorker.js` stays colocated with
the Host code that creates the Worker.

## Acceptance

- All remote asset aliases resolve to existing source entrypoints.
- Default and Linux-only target selection preserve the established manifest layout.
- Every explicit tsup entry points to an existing source file; the storage worker keeps its existing
  output location.
- Run focused regressions and the real preparation/build commands; report missing external
  toolchains, network failures, or native artifacts separately from code failures.

## Shared-sync compatibility

A workspace build includes the Agent contracts and bootstrap, beyond the root typecheck.

Session archive wire fields are removed, as in upstream 3.16.1 (`0a1fc56d`): `session.list` params
have no `includeArchived`, and `session` info has no `archivedAt`. Both schemas stay `.strict()`. No
CLI handler implements them any more. The CLI `session.list` handler never forwarded
`includeArchived` to the store; the session mapper does not emit `archivedAt`; no storage or
migration definitions change (`specs/upstream-sync-cli-divergences.md`).

Version compatibility: a strict schema rejects the removed field when a peer still sends it (an
older Host sending `includeArchived`, or an older Agent answering with `archivedAt`). Host and Agent
ship in lockstep, so the fork accepts this, as upstream does:

- Local: production uses the Agent runtime bundled with the app; an explicit binary path is used
  only when the bundled runtime is missing (`desktop/src/main/desktopRuntimeEnv.ts`).
- Remote: the only check is string equality between the Source Server release descriptor version and
  `ZCODE_VERSION` (`desktop/src/host/sourceServerReleaseResolver.ts`, `readDescriptor`). Two builds
  sharing a version string are not told apart.

The Host's unrecognized-key retry covers only new optional fields of create, resume, send and MCP
list against an older Agent. It does not cover `session.list`.

An older Agent emits `archivedAt` only for a row with a `time_archived` value; no fork or upstream
build has a production writer of that column (only readers existed at `872ad960`, `aac47556` and
`integration`; the author's local database has 0 such rows). If such rows existed, they would now
appear in `session.list` and in the sidebar child counts and lists.

Highspeed metadata and execution fallback events in Agent contracts accept the same three reasons as
the shared schema, including `highspeed_selection_unavailable`. The synchronized Agent metadata and
execution event contracts and their public exports stay; cold hydration and persistence preserve
the selection-unavailable reason.

Background execution model policies use the current Agent session-execution owner; the toolchain
migration does not override policies supported by the synchronized Core.

The standalone Web share entry imports the existing Web theme seed module from its current location;
import-path repair must preserve initial theme selection behavior.

Agent bundling derives shared aliases from the package's declared public exports: it resolves
`@zcode/shared/sqlite-migrations` through its public source entrypoint before the generic shared
alias. The bundler must not append that subpath to `src/index.ts`; migration definitions and
checksum inputs remain unchanged.
