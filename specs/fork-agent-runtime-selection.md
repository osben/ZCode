# Agent runtime selection (Node / Rust)

Status: draft. Phase 1 (selection, Host resolver, storage preparation, hello overrides and command gate) implemented; phase 2 (UI switch) waits for the fork features below to be covered on the Rust side; phase 3 (packaged binary) is implemented: release builds ship `zcode-rs` while the default runtime stays `node`.

## Problem

The desktop Host always runs the Node agent (`zcode.cjs app-server --stdio`), which idles at ~350 MB RSS. Upstream's own Rust agent (`zcode-rs`, MBearo/ZCode-rs `packages/rust-cli`, Apache-2.0) speaks the same stdio protocol and idles at ~32 MB (measurements in `specs/rust-port-research.md` §9a). The only existing way to run another agent is `ZCODE_AGENT_SERVER_COMMAND`. With that override the Host turns off storage preparation, so startup fails with `unsupported_runtime`. That is intended for unknown custom commands, so the override stays as it is.

## Product rules

1. **Two runtimes, one choice per app process.** `node` (default) or `rust`. The choice is fixed when Main starts. Every Host that process spawns gets the same value. Changing the setting takes effect after an app restart. Windows never mix runtimes.
2. **Sources, highest first:**
   1. `ZCODE_AGENT_SERVER_COMMAND`: the upstream custom-command override, unchanged. It bypasses this feature entirely.
   2. `ZCODE_FORK_AGENT_RUNTIME=node|rust`: the shell env override. Invalid values are ignored with a `warn`. It is read from Main's own `process.env` at launch; the login-shell env patch that runs later does not change the latched choice.
   3. The fork setting `agentRuntime`.
   4. The default, `node`.
3. **Storage preparation always stays on Node.** The Rust agent is spawned only as the conversation process. Database preparation and migrations, including fork `9001_fork_*`, keep running in the Host Worker from the bundled `zcode.cjs` (`storagePreparationEntry`). If no Node bundle is available, Rust is not selectable, because a Rust agent without prepared storage would open an unmigrated database.
   - **The same step seeds the official plugins in Rust mode.** `zcode-rs` only reads the official plugin store (`platform/src/local/plugin_inventory.rs`: `cache/zcode-plugins-official/<name>/<version>` and `marketplaces/zcode-plugins-official/bundled-marketplace.json`) and has no copy of the plugin sources. Node's agent seeds that store itself on its first plugin resolution (`bundled-plugins.ts` `resolveOfficialPluginRoots`). With Rust effective no Node agent runs, so on a fresh home Rust would list no official plugin skill. The storage Worker already ships the plugin sources, so when its env has `ZCODE_FORK_AGENT_RUNTIME=rust` it runs the same `resolveOfficialPluginRoots` once the database is prepared (`bootstrap/src/fork-agent-runtime/`, called from the `prepareStorageOnly` branch of `runZCodeProtocolAgent`).
     - **Rust only.** With Node effective it does nothing, and the Node agent stays the only seeder. Measured on the dev bundle (Apple M-series, 17 plugins, 66 MB): a cold seed adds ~230 ms to the Worker, a warm one ~70 ms, because each Worker re-hashes every bundled plugin file (the hash memo is per process). Doing it in Node mode would add the warm cost to every default start for nothing.
     - **Store root.** The one the Rust agent reads (`StoragePaths::plugin_storage`): the merged `storage.dir` with `~/` expanded, a relative path resolved against the workspace, then `<cli storage root>/plugins`.
     - **Never fails preparation.** A seed error is logged at `warn` and the Worker still exits `0`; the Rust agent then sees whatever usable cache already exists. The seed writes nothing to stdout, the Host's control channel.
     - **Degraded plugins load the same cache as Node.** When a plugin's new version cannot be laid out, the seeder falls back to the last usable older cache, which Node passes to discovery beside the catalog. `zcode-rs` reads only the catalog's `cachePath`, so the seed points that entry's `cachePath` at the fallback cache (the entry keeps the bundled version). Rust and Node then load the same plugin set.
     - **Known limits (follow-ups).**
       - The Host prepares storage once, at startup, for its warm-up working directories (`hostDatabaseStartup.ts`). A workspace opened later whose `zcode.json` sets a `storage.dir` no warm-up directory uses stays unseeded until the Host restarts; Node seeds it when that workspace's app is created. Closing this needs a seed at Rust spawn time in the Host, which changes the Host's startup ownership.
       - The catalog pointer to a fallback cache is shared state. Every seed (another Host's prepare, any Node bootstrap on the same home) first republishes the entry at the bundled version. If that version is still not laid out, a Rust agent reading in between, or after a Node bootstrap, misses the plugin until the next prepare. Node does not hit this, because it computes the fallback per process. The proper fix is for `zcode-rs` discovery to fall back to the newest usable sibling version itself when `cachePath` is not usable; then the pointer is no longer needed.
     - **Same content as Node.** Seeding writes every bundled plugin, including `computer-use`; `suppressedBuiltins`, default enablement and the Node-only plugins are filtered when `zcode-rs` discovers plugins (`ext/src/plugins/select.rs`), as Node filters at discovery.
4. **No silent lie about the runtime.**
   - Main resolves which runtime is in effect. If `rust` is selected but no `zcode-rs` binary is found, Main runs Node and logs at `warn`: `selected=rust effective=node reason=binary_missing`.
   - Main writes only the effective runtime into the Host env.
   - The Host repeats the check: if its env says `rust` but there is no binary path or no Node storage bundle (the dev source-tree command), it runs Node and logs once at `warn`: `selected=rust effective=node`, `reason=binary_path_missing|no_node_bundle`.
   - Once phase 2 lands, the UI shows the effective runtime next to the switch.
5. **The Host tells the UI the truth about the runtime.** The Host's `hello` capability literals (`zcodeAgentService.ts` `helloConversationV4` and `zcodeAgentConnectionScope.ts`) claim fork capabilities statically. In Rust mode one fork helper, `forkAgentRuntimeHelloOverrides`, turns off the ones `zcode-rs` lacks; today that list is empty. (`independentPlanState` was on it until `zcode-rs` froze the plan switch per queued input; `incognitoSession` and `incognitoPromptToggles` until `zcode-rs` implemented incognito sessions. See `specs/fork-rust-agent-parity.md`.)
   - `durableFirstSubmission` stays claimed: `zcode-rs` implements the first-submission contract itself (reserve with `submissionPreparation`, activate with `preparedSessionId` + `expectedSubmissionId` and a `preparedActivation` result, completion on the first admitted `sendText`) and reports `durableFirstSubmission: true` from `runtime/capabilities`, so the Host gate `ensureDurableFirstSubmissionSupport` passes unchanged. The composer always uses the durable route (`SessionPane` passes the flag as a constant), so a runtime without the contract cannot be served by turning the hello flag off.
   - `zcode-rs` stores the marker in the same `session_entry` record the Node agent writes (`v4/fork_submission_preparation`, id `v4/fork_submission_preparation:<sessionId>`, data `{submissionId, status}`), so a session reserved by one runtime can be activated by the other after a switch.
   - The UI prewarms a new task's session with a plain `createSession` before the first send. Both runtimes keep that prewarm deferred (not in `db.sqlite`) and persist it on reservation (see "Draft prewarm in Rust mode"); `zcode-rs` adopts an existing session only when it has no marker, no messages, no queued input, no running turn, and the same workspace. A repeated reservation by the same submission returns the same session; any other existing session is refused with `proto.invalidPayload`.
   - `zcode-rs` reports `incognitoSession` and `incognitoPromptToggles` from `runtime/capabilities`, so the Host gate `ensureIncognitoSupport` admits an incognito `createSession` in Rust mode too.
   - Fork features that have no capability flag are refused by a Host command gate (rule 7) instead of silently degrading.
   - Phase 1 is env and sidecar only, meant for development. Phase 2 (the user-visible switch) waits until the table below has no "refused" or "lost" rows that users would hit.
6. **Local Host only.** Remote SSH/WSL hosts (`zcode-server.cjs`) never receive the env from Main and keep their own resolver chain. Web/server mode is unchanged.

7. **Fork features without a capability flag are refused, not dropped.** `forkAgentRuntimeCommandGateError` runs in the Host command path right after `getClient`, in Rust mode only, and fails the command with a stable error code:
   - `proto.forkRustAgent.externalAgentUnsupported` for `setExternalAgentConfigOption`, and for any `modelSelection.providerId` starting with `acp:` (in the payload, in `config`, or in `firstInput`), and for a `provider` starting with `acp:` (`switchModelConfig.provider`, `createSession.config.provider`).

## Draft prewarm in Rust mode

The Node agent keeps a prewarmed session in memory (`record.persistence: "deferred"`, runtime `sessionPersisted = false`) until the first real activity: the first prompt turn, an admitted input, or a reservation (`ensureSessionPersistedForExternalActivity`). An abandoned draft never reaches `db.sqlite`; disposal (`deleteSession`, or `session/close` with `expectedPersistence: "deferred"` from `releaseWorkspacePreparation` and `closeDeferredDraftSession`) only drops the runtime, and a CLI restart forgets it. `zcode-rs` used to insert the `session` row at `create`, so every abandoned new task left an empty row, and `session/close` ignored `expectedPersistence`.

Rule: in the app-server (`Controller::app`, the only surface with `node_desktop`), `NodeStore` defers a top-level interactive session the same way. The store owns the draft: the kernel, the session actor and the protocol keep calling the same Store methods, and the store decides whether a write is buffered, materializes the draft, or drops it. The TUI and `-p` keep writing the row at `create`.

| Store method (draft session)                                    | Behavior                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| --------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `create` (top-level `Interactive`, app-server)                  | no row; the draft (row input) is kept in memory. A create of an id that already has a row is not held: it upserts as before, so a draft never shadows a stored row (whether a repeated create is refused is the protocol's rule). Every new Store write keyed by a session (a column on the `session` row, a new record or table) must route through the drafts: it calls `drafts::persist` first (or is buffered like the config facts), never `with_db` alone, or it silently misses a draft that has no row yet.

Outside the store:

- Sessions index: Node `isDraftSession` keeps a draft out of `sessions-index` (live fan-out and cold seed). A Rust `Live` opened on a store draft asks the store (`is_rowless_draft`) before it publishes its summary and skips it while the session has no row; the first publish after materialization lists it. A dropped draft counts as rowless, so a flush from the bridge or pump that outlives a deferred close does not publish it. The cold seed (`subscribe` → kernel `workspace_sessions`, which also lists open sessions the store has no row for) skips open sessions the store reports as rowless drafts. A cold row reports the stored `title_source` as Node's cold summary normalizes it (`default`, `custom`, else `generated`), so a persisted untouched prewarm ("New session", `default`) is not reported as `generated`. The live row, which replaces the cold one, keeps that source: the session's view carries the stored `title_source` (cold load and cold snapshot), each kernel `TitleChanged` carries its source (`first_input`, `default`, `generated`, `custom` for a rename or a hook title), and the projection keeps `custom` against a later automatic title, as Node's `onSessionTitleUpdated` does. The conversation `meta` reads the same source. A disposed prewarm therefore never shows as a new task.
- First input: Node `admitInputCommand` persists a deferred session (`ensureSessionPersistedForExternalActivity`) before it accepts the input. Rust `sendText` / `sendGoalCommand`, and `createSession` with a first input, call `persist_for_input` with the input text after their refusal checks and before the `Submit`; a draft that a deferred close dropped first refuses the input (`proto.sessionNotFound`) instead of accepting and losing it. Any other persist failure fails the command like Node's admission error (`failed`, `fault.command.executionFailed`, a message without storage detail) before the input is remembered or sent, so a retry of the command id is not answered as accepted; for `createSession` the whole command fails. A `compact` on a draft is not admitted this way (it has nothing to summarize); its first commit materializes the draft like any other write. Title: like Node `persistSession(input)`, the admission writes the input's title (`first_input`, `titleFromInput(sanitizeTitleSeed(input))`: composer file, directory, plugin, session and skill mentions keep their label, bare `#sess_…` ids are dropped, the manual skill prompt template becomes its request or `$<skill>`; kernel-api `title::first_input`, which the user message commit and the actor also use; the generated title's request and its length guard read the same seed, as Node `buildTitleMessages` and `maybeStartSessionTitleGenerationFromSeed` do) with the row, and a reserved row still on "New session" (`default`) gets it at the admission (Node `applyFirstInputTitleForPersistedSession`, which runs before the hooks). The user message commit keeps it (its compare-and-set on `default` no longer matches), so an input that a `UserPromptSubmit` hook blocks does not leave "New session". The title the admission wrote reaches the session actor before the input (kernel `Command::AdoptTitle`, sent ahead of the `Submit`): the actor takes it in memory without a commit and emits `TitleChanged` (`first_input`), so the live views show the stored title before the `UserPromptSubmit` hooks, as Node emits `SessionTitleUpdated` at the persistence. A blocked first input keeps that title live, and a next committed input keeps it too (the actor's title is no longer the placeholder). A rename that reached the actor first stays.
- Attachments of a draft are artifact files, not rows: an abandoned draft can leave an uploaded image file, as on Node.

`session/close` follows Node `shouldCloseSessionForExpectedPersistence`:

- `expectedPersistence: "deferred"`: if the store still holds the session as a draft, the store drops it in the same locked step, then the bridge and the actor close and the reply is `{closed: true}`. A session that materialized first (the first send won the race) gets `{closed: false}` and stays open.
- `expectedPersistence: "immediate"`: a draft gets `{closed: false}`; a stored session closes.
- No `expectedPersistence`: Node disposes the runtime. For a draft that is all there is: the store drops it, the actor closes, `{closed: true}`. A stored session is unchanged (bridge close, `{closed: true}`).

Acceptance:

- An untouched prewarm, a prewarm with model and mode changes, and a disposed prewarm leave no `session` row; a fresh process (Rust or Node) does not list or load them. The project mode set on a draft is visible at once.
- The first send materializes the session with the model and mode chosen on the draft; Node reads it with that model and mode.
- A reservation on a prewarm (rule 5) persists it with the buffered config; a repeated reservation reads the marker from the persisted row like any stored session.
- A prewarm is absent from the sessions index (live rows and the cold seed) until it materializes, and a flush after a deferred close does not publish it.
- The first input persists the draft before the actor sees it; a later deferred close answers `{closed: false}`. An input after a deferred close dropped the draft is refused.
- The first input's admission writes its title (`first_input`, seeded like Node's `sanitizeTitleSeed`: `fix [a.ts](./src/a.ts) now` → `fix a.ts now`) to the new row, or to a reserved row still on "New session"; the open session's live title shows it before the hooks, and an input blocked by a hook keeps that title in the row and live, also after the next input.
- A session renamed and opened again reports `titleSource: "custom"` in its live sessions-index row and conversation meta after live updates.
- A create of a stored id does not hide the row behind a draft: a later delete deletes the row.
- A reservation on an untouched prewarm writes the row as "New session" (`default`) at the reservation time.
- `session/close` with `expectedPersistence: "deferred"` drops a draft and answers `{closed: false}` for a materialized session.
- Rust unit tests cover every row of the table; interop: a Rust-abandoned draft is absent for Node, a Rust-materialized draft reads the same on Node. E2E: `prewarming-queue` and the new-task specs on Rust are no worse than on Node.

## Attachments in Rust mode

`zcode-rs` ports Node's upload transaction and attachment mapping; the UI and the Host are unchanged.

- **Upload** (`attachment-upload-registry.ts` semantics): uploads are keyed by `connectionId`, `sessionId` and `uploadId`. `begin`, `chunk` and `commit` are idempotent for a repeat with the same metadata or bytes. `abort` waits for a commit in flight. A closed connection drops its uploads. Limits and `fault.attachment.*` codes match `PROTOCOL_V4_LIMITS`. Commit checks the SHA-256 and stores the bytes the way Node's `writePromptAttachment` does: a session artifact holding `data:<mime>;base64,<bytes>` as `text/plain`, referenced as `zcode-artifact://<session>/<artifact>`. Node reads it back by id.
- **Send** (`attachment-refs.ts` semantics): `sendText` reads each ref before admission:
  - an image up to 20 MiB is read and prepared for the model as described in "Image preparation" (a larger desktop image goes by path, `image_too_large`);
  - web-remote UTF-8 text up to 64 KiB is read inline; a desktop text file is read as described in "Local text files";
  - any other file, or a ref that cannot be read, keeps only its metadata.

  Web-remote refs are the session artifacts `commit` answered. Desktop refs are local absolute paths: the Host's prompt attachment transfer is zero-copy on a local Host, so the agent reads the file itself (through `rust-cli-fs`). A ref that cannot be read, or an artifact of another session, is never dropped silently, and the log names only the fault code, never the path. While a turn runs, an input with attachments is queued until that turn ends; it is never steered in.

- **One owner, the `file` part:** each attachment is a kernel `ContentBlock::File` on the user message, stored as Node's `file` part after the user's text part:
  - inline text: `mime: text/plain`, `filename`, `source.text.value` = the submitted path for a desktop file (the file name for web-remote text), `metadata.preview` (`text`, `truncated`, `originalBytes`, `startLine`, `totalLines`, and for a token-capped view `truncatedByTokenCap` and `partialViewNotice`), `storageKind: inline`, `recoverability: provider_ready` (`preview_only` when truncated);
  - image: Node's artifact shape (`persistAttachmentDataUrl`): `url` and `metadata.artifactUri` are the session artifact holding `data:<mime>;base64,<bytes>`, `storageKind: artifact`. A web-remote ref is already that artifact and is reused; a desktop image is written as a new artifact when the input is accepted. Node builds the chip's `ref` only from a `url` that is not a data URL, and reads the model image back from the artifact. If the artifact cannot be written, the part falls back to the inline data URL (`storageKind: inline`): both runtimes still read it, but the chip under Node has no ref;
  - metadata only: `recoverability: metadata_only`;
  - every part keeps the App's ref as `metadata.originalUrl`, its size as `metadata.sizeBytes`, and the App's `previewRef` as the fork key `metadata.previewRef`;
  - read back, a part without `filename` is still an attachment when it carries `metadata.sizeBytes` and no `metadata.rustCli`: Node's web-remote image and video resolvers write no `filename`. Its name is Node's chip name (`attachmentMetasOfMessage`): the last segment of a `url` that is not a data URL, else `attachment-<n>` by its place among the message's file parts. A Rust TUI image (inline with no `sizeBytes`, or an artifact with `metadata.rustCli`) stays a plain image.
  - Node's placeholder written without options (`resolvedPlaceholderAttachment` from `resolveInlineMediaAttachment` or `resolveTurnAttachment`, any `errorCode`, e.g. `attachment_image_resize_failed` or `attachment_read_failed`, any MIME) has no `filename`, `sizeBytes` or `source`: a part with an `errorCode` and `recoverability: metadata_only` is still an attachment, with chip bytes 0. Its model text is Node's live view: `[Attached <mime>: <path>]` for a local path, else `[Attached <mime>: attachment-<n>]`, sent as a user block; a source-less text placeholder (a web-remote text whose content could not be read) goes as Node's inline-text reminder around that line (`Attached inline text.`, the line, the data notice), because `shouldAddInlinePromptAttachmentReminder` comes before the failed-read skip, which drops only a text placeholder with a `source`. A named placeholder Node wrote with options (a desktop file it could not read or prepare) reads `[Attached <mime>: <path>]` too. Node's `originalUrl` of an inline content, `inline:data-url`, is not a ref: the chip has no `ref`, as in Node. Written back, the part is Node's: the `url` Node stored (an inline data URL included), no `filename` or `source`, `sizeBytes` only when Node gave one (an invalid PDF's or video's parsed size). `storageKind` and `originalUrl` follow the submitted path alone (`attachment.path ? "local_ref" : "metadata_only"`): Node's markers `inline:pdf` and `inline:data-url` in `url` or `originalUrl` are not paths, and without a path `originalUrl` is `inline:data-url` for inline content, as `safeAttachmentOriginalRef`. Node's own cold load sends a placeholder's stored data URL or artifact back as an image (`filePartToContentBlock` does not look at `errorCode`) and names other placeholders `[Attached <mime>: <filename ?? url>]`; Rust keeps the live view instead of resending bytes that failed preparation, so a reopened session's prompt matches the live one.
  - The chip name of an unnamed part is only for the chip. The model gets Node's absent filename: a media block of such a part has no name, so a non-vision endpoint or the media budget sees `[Attached <mime>]` (Node `modelMessageContentBlockToText`, cold `placeholder: source.text.value ?? filename`), and the part is written back without `filename`.

  The text part holds only the typed text; `metadata.modelInput` is not written for attachments. Both runtimes rebuild the model input from the parts: Node through `hydrateMessageHistoryFromSession`, Rust by reading the part back into `ContentBlock::File` and expanding it in `query::normalize` (the only expansion point) into Node's Read-style reminder pair, the image block, or the "Attached file" metadata reminder. An artifact-backed image part (written by either runtime) is read back when the store loads the session: the store reads the artifact and turns the block into the base64 image, before the model sees it. An artifact that is missing, of another session, larger than 5 MiB or not a data URL reaches the model as the metadata reminder. Rows stored before this change keep the reminders in `metadata.modelInput`; the bubble strips them.

- **Attachment-only input** (Node `buildUserMessageEntries` and `toAiSdkUserContent`'s `EMPTY_USER_CONTENT_FALLBACK`): Node puts the text reminders of attached text (inline text, and nothing for a failed read) in their own entries after the real user message, so an input with no typed text whose attachments are all such text leaves that message empty, and the provider request carries `(no content)` in its place. Rust expands the attachments inside one user message, so `query::normalize` puts the `(no content)` text first in such a message. With separate user messages (OpenAI-compatible protocols, which never merge them) `normalize` sends Node's entries apart instead: the real user message (typed text and every other attachment, `(no content)` when that is empty), then one user message per attached text's reminders, marked as attachment content for the media budget; this holds with typed text too. Only the request changes: the stored message, the row and the title seed have no text.
- **Local text files** (Node `resolveLocalFileAttachment` → `readTextFileForModel`, the fs adapter's `readTextFileRange` and `text-metadata.ts`): a desktop ref with a text-like extension that is not text material is read by the agent, with no 64 KiB limit (that limit is only for web-remote refs, Node `attachment-refs.ts`).
  - Encoding, in Node's order: a UTF-8 BOM → UTF-8; `FF FE` → UTF-16LE; a NUL byte, or more than 30% control bytes → unsupported; strict UTF-8; else GBK (also Node's `gb2312`), then GB18030, each accepted when it decodes and re-encodes to the same bytes after dropping 0–3 trailing bytes; else unsupported. A file up to 10 MiB is detected on its whole bytes; a larger one on its first 4096 bytes, extended only to complete a UTF-8 sequence cut at the end. The whole file is then decoded with replacement characters, and the BOM is kept.
  - Lines: `\r\n` counts as one line break; `totalLines` counts the whole file (a trailing newline ends with an empty line, as in Node).
  - A file over 256 KiB (`READ_MAX_FILE_SIZE_BYTES`) sends its first 2000 lines (`READ_DEFAULT_MAX_LINES`), not marked truncated, as in Node. A smaller file sends all its lines.
  - Token cap (`READ_MAX_OUTPUT_TOKENS` = 25,000, Node's estimate `ceil((CJK × 2 + other UTF-16 units) / 3)`, CJK = U+4E00–U+9FFF): over the cap, Node's partial view is sent (lines kept = `floor(lines × 25000 / tokens × 0.85)`, shrunk by 0.7 up to 6 times, then a character slice), with Node's `[Truncated: PARTIAL view — <path>: …]` notice, `truncated` and `truncatedByTokenCap`.
  - The model gets Node's Read-style reminders: the input names the submitted path, lines are numbered from `startLine`, and the notice comes first inside the result as a `<system-reminder>`.
  - A read that fails (missing or not a regular file, an unsupported encoding, a view that does not fit the cap) is Node's placeholder: the part has `errorCode: attachment_read_failed`, `mime: text/plain`, `recoverability: metadata_only`, and the model gets nothing for that file (Node `isFailedTextAttachmentPlaceholder`), live and on a cold load of a part written by either runtime.
  - Divergences: Node wraps the two Read reminders in one `<system-reminder>`, Rust wraps each; a reminder tag inside the body (the notice's own tags, or one in the file) is escaped by Node as `&lt;system-reminder>` and by Rust as `<system_reminder>`; web-remote text keeps Rust's Read-style reminder with the file name, where Node sends its `inline_text` reminder; a path that is not a file is a failed read, where Node sends `[Attached text/plain: <path>]` (`attachment_not_file`).
- **Text material** (`sourceKind: "topic-history" | "clipboard-text"`, Node `resolveTurnAttachment`): the body is never read into the prompt. The model gets Node's path reference with the reason `deferred_topic_history` ("topic history is provided for on-demand reading") or `deferred_clipboard_text` ("it is a pasted-text temporary attachment that is deferred to keep the model context small"), and reads the file with its tools.
  - A desktop ref (a local path) with a text-like extension is referenced in place: mime `text/plain`, size from `stat`. A non-text-like extension keeps the `binary_file` reason, as in Node.
  - A web-remote ref (an artifact holding `data:text/plain[;charset=utf-8];base64,…`) is decoded and written as a new session artifact holding the raw text (`.txt`). The part's `url`, `metadata.originalUrl` and the note name that file's local path; `metadata.sizeBytes` is the decoded length. The kernel keeps the path as `AttachedFile::stored`, so the chip keeps the App's ref.
  - When the material cannot be written (no artifact store, not that data URL, a store error), the input is refused with `fault.attachment.textMaterializationFailed` before any side effect (a `createSession` leaves no session, and a prepared session is not activated); it never reaches the model as inline text. Divergence: Node accepts the input and then fails the turn.
  - Known gap: Rust's Read asks for permission for a path outside the working directories, so the model's read of the material file (in the session artifact directory, or a desktop temp file) asks; Node's read-only tools are allowed.
  - A live row's chip keeps `sourceKind` and `messageCount` (Node puts the input refs on the live row); the stored part does not hold them, so a cold chip has neither, as in Node. `v4/attachment/read` serves `text/plain` only for a chip with one of these `sourceKind`s (Node `isPreviewable`).
- **Video** (Node `resolveLocalVideoAttachment`, the video branch of `resolveInlineMediaAttachment`, `VIDEO_INPUT_MAX_BYTES` = 30 MiB):
  - A desktop video (a local path) is read whole up to 30 MiB with the MIME of its extension (`.mp4`, `.m4v`, `.mov`, `.webm`, `.mkv`, `.avi`; else the App's MIME). A larger one goes as Node's path reference with the reason `video_too_large`; an empty or unreadable one keeps only its metadata.
  - A web-remote ref is the artifact `commit` wrote; it must hold a strict base64 `data:video/…` URL of at most 30 MiB, else the part keeps only its metadata.
  - The part has the image's artifact shape (`storageKind: artifact`, `recoverability: provider_ready`): a desktop video is written as a new session artifact, a web-remote one is reused. Unlike an image there is no inline fallback: when the artifact cannot be written, the input is refused with `fault.attachment.putFailed` before any side effect, as Node stops the turn. A cold load reads the video back from the artifact like an image. A cold load reads an artifact of any session, as Node's `filePartDataUrl` does: a forked session's parts keep the parent's artifact URIs (Node `clonePartForFork`).
  - The model gets a video block only when the endpoint has `supports_video`; otherwise Node's placeholder `[Attached <mime>: <name>]` with "…does not support video input." Wire forms: Anthropic Messages `{"type":"video","source":{"type":"base64",…}}` (Node's patched SDK), OpenAI-compatible Chat `{"type":"video_url","video_url":{"url":<data URL>}}`; the OpenAI Responses request is refused ("file part media type … is not supported"), as `@ai-sdk/openai` throws for it. Usage and compaction count a video like an image.
  - `v4/attachment/read` serves a video up to 30 MiB (`attachmentPreviewMaxBytes`).
  - Playback source (`v4/attachment/previewSource`, Node `attachmentPreviewSource` and `resolvePromptAttachmentPreviewSource`): for a `desktop-continuous` client and a video chip, the agent answers `{kind: "local_path", path, mediaType}` so the Desktop plays the file through its media protocol, with no size limit; anything else is `{kind: "chunked"}`. The chip is authorised by the row target and index when given, else by the ref a `userInput` row carries (`previewRefNotAuthorized` otherwise). A part with a session artifact plays its derived copy, `<storageRoot>/cli/video-cache/<session>/video-<first 32 hex of sha256(artifact URI)><ext>` (Node `ensureMediaAttachmentPath`: reused when it is a file, else the artifact's data URL is decoded and written atomically; the extension comes from the part's MIME, `.mp4` `.mov` `.webm` `.mkv` `.m4v` `.avi`). A MIME without an extension, an artifact that is not a video data URL, a session id that is not a plain path segment, a missing storage root or a failed write answer `chunked`: the mutable original path is never used for an artifact-backed part. A part without an artifact (a path reference, `video_too_large`) plays its absolute path. The Host authorises the path before the renderer sees it.
  - Missing, also for images: the media stripping before compaction, and the `[Image: source: <path>]` / `[Video: source: <path>]` text block Node adds after each media block (`media-attachment-path.ts`; `mixed-media-path-strip` checks it).
- **Request media budget** (Node `projectMessagesForMediaBudget`, `DEFAULT_MODEL_REQUEST_MEDIA_BUDGET_BYTES` = 40 MiB; `model/src/media.rs` `budget`, called in transport right after the capability projection, so every request — main, side and compaction — gets it):
  - Counted media: user image and video blocks and tool-result image and document blocks, each at the length of its data URL (`data:<mime>;base64,<data>`; an artifact source at its base64 length). Text never counts. Media the capability projection already replaced are text by then.
  - Protected: the image and video blocks of the latest real user message, the last user message with a block that is neither a tool result nor text starting with `<system-reminder>` (Node `findLatestRealUserMessageIndex`; Rust may merge reminders and tool results into that message, so only its own media blocks are protected, as Node keeps tool results in separate tool messages). An attachment's blocks — a `@` mention's Read result, image included — are not the user's input either: `normalize` marks them (`ApiContent::meta`, never sent) whether they are merged into the user's message or sent as their own user messages (OpenAI-compatible separate mode), and the budget neither protects them nor takes a message holding only them as the latest real one, as Node keeps them in their own entries. Two inputs with no reply between them (the first one interrupted) are two user messages in Node, which protects only the newer; `normalize` merges them (except in separate mode), so when an input joins a user message, the image and video blocks already in it are marked the same way and only the newest input's media are protected: two ~27 MiB inputs keep the newer and drop the older, never refuse.
  - At most 40 MiB: the request is unchanged. Over it: when the protected media alone exceed it, the request is refused before sending with Node's text "Current attachments are too large to send. Remove or compress attachments and try again." (`ModelError::CurrentAttachmentsTooLarge`, whose text is Node's). The failed turn carries Node's error code `MEDIA_BUDGET_CURRENT_ATTACHMENT_TOO_LARGE` (`ModelError::code` → `TurnOutcome::Failed.code` → `lastError.code`), by which the App localizes the banner; a failure without a Node code keeps `fault.turn.failed`. Otherwise the protected media are kept and the rest newest first (message, then block, then tool-result item, descending), each kept when it still fits (first fit, a large one skipped); every other one becomes Node's text `[Attached <mime>: <name>]` (or `[Attached <mime>]`) plus a line "[Media omitted from provider request to keep the request body under the configured media budget.]".
  - Only the request changes; the session history keeps every media block. A debug log `model.media_budget` records the omitted count and byte totals.
- **Image preparation** (Node `resolveLocalImageAttachment`, the image branch of `resolveInlineMediaAttachment`, `prepareImageDataUrl` and the Jimp adapter `prepareJimpImageForModel`; crate `rust-cli-image`, the `image` crate with PNG, JPEG, GIF and BMP decoding, run off the async threads):
  - Limits: `INLINE_MEDIA_ATTACHMENT_MAX_BYTES` = 20 MiB read limit (a larger desktop image goes as Node's path reference, `image_too_large`); the model budget `READ_IMAGE_MAX_BASE64_BYTES` = 5 MiB of base64 and `READ_IMAGE_TARGET_BYTES` = floor(5 MiB × 3 / 4) raw bytes, both checked; `MAX_IMAGE_ATTACHMENT_DIMENSION` = 2000 px on the longest edge.
  - Format: sniffed from the bytes (PNG, JPEG, GIF, WebP), else the App's MIME, normalized (`image/jpg` → `image/jpeg`; anything but JPEG, PNG, GIF or WebP counts as PNG).
  - WebP is never decoded: within the byte budget it is sent unchanged, whatever its size in pixels; over it, the image fails.
  - Others are decoded with the EXIF orientation applied (Jimp `attemptExifRotate`). Within 2000 px and the budget the original bytes are sent unchanged. Otherwise Node's candidate ladder, first fit wins (scaling is Catmull-Rom bicubic to the longest edge, `round(edge × scale)`, at least 1 px; JPEG drops alpha):
    1. within 2000 px: the source format (PNG at best compression; JPEG at quality 80, 60, 40, 20; GIF re-encoded);
    2. the image bounded to 2000 px: for a non-PNG source, the source format re-encoded (JPEG at quality 100) when bounding changed it, then the source format ladder when the original was over 2000 px;
    3. the bounded image as JPEG at quality 80, 60, 40, 20;
    4. the bounded image scaled by 0.75, 0.5 and 0.25: each the source format ladder (non-PNG source), then JPEG at 80, 60, 40, 20;
    5. the original bounded to 1000, 800, 600, 400, 300 and 200 px as JPEG at quality 20.
       Nothing fits, or it cannot be decoded: the image fails.
  - The part: `mime` is the prepared MIME; `metadata.image` is Node's `{width, height, originalWidth, originalHeight, maxDimension: 2000, resized, transformedSizeBytes}` (no dimensions for WebP); `sizeBytes` stays the App's size. A desktop image's artifact holds the prepared data URL. A web-remote image's artifact is reused as Node does (`existingArtifactUri`), so it keeps the original, so a cold load sends that original when its data URL fits the 5 MiB model budget, and otherwise prepares it again with the same ladder, which gives the image the first turn sent (Node sends the original unchecked, which a provider with a 5 MB image limit refuses).
  - A failed image is Node's placeholder: the model reads `[Attached <App mime>: <path, or the file name for web remote>]`; the part has the App's MIME, `metadata.errorCode` `attachment_image_resize_failed` (`attachment_image_invalid` for an empty image), `recoverability: metadata_only`, `storageKind: local_ref` for a desktop path, else `metadata_only`; a cold load reads it back the same. A web-remote one keeps the App's artifact URI as `url` and `originalUrl`, where Node first reads the artifact and stores its data URL inline (`inline:data-url`); Node's cold load reads both back as the same image (`filePartDataUrl` reads an artifact `url`), and this runtime does not copy the failed bytes into the database.
  - Not covered: TIFF decoding (Jimp decodes it; here it fails), and image results of the Read tool.
- **Path reference MIME**: the part's `mime` is the MIME the note names (`Attached <mime>: <path>`), so an oversized image keeps its image MIME and text material keeps `text/plain`.
- **Share reads** (`v4/conversation/attachmentRead` / `attachmentStat`, Node `conversationAttachmentRead` / `Stat` and the session app's `readPromptAttachment` / `statPromptAttachment`): authorised only by the `userInput` row `(rowId, entityId)` whose chip at `attachmentIndex` has the ref as `ref` or `previewRef`; otherwise `shareReadNotAuthorized` / `shareStatNotAuthorized`. The read opens the part's stored source (its artifact, or the stored text-material file), else the App's ref. A read serves any MIME up to 30 MiB in chunks; an artifact must be a strict base64 data URL (`previewArtifactInvalid`, `previewNotMedia`, `previewTooLarge`). Share uses a stat only to compare `totalBytes` with the chip's `bytes` (`artifact_changed` when they differ) and against its size limit; it does not read `mediaType`. Node's chip `bytes` is the part's `metadata.sizeBytes`, and `zcode-rs` writes the same value Node writes for the same input (one shared database, one Share): a web-remote image the UTF-8 length of the data URL it received (its artifact's content, which the part reuses), a web-remote video the decoded payload length, a desktop image or video the file's size, a desktop path reference (text material, a binary file, an image or video too large to inline) the file's `stat` size, web-remote text material the decoded text's length; `zcode-rs` does not use the App's declared `bytes` for these. Both runtimes state an artifact as Node's `statToolResultArtifact` does: the stored object's size, the content type its file name gives (`text/plain` for an attachment's `.txt`), else the part's MIME, and its `mtimeMs`. So an uploaded image's chip and stat agree (a 68-byte PNG: 114 and 114). Not covered, as in Node: a desktop image's or video's chip is the file's size while its artifact holds the prepared data URL, and a web-remote video's chip is decoded while its artifact is the data URL, so Share reports those as `artifact_changed` in both runtimes; and a web-remote image that cannot be prepared keeps the App's declared size where Node writes none. A local file reports its size and `mtimeMs`, a directory `statNotFile`. A missing source is `shareStatNotFound`, over 2 GiB `shareStatTooLarge`. Faults carry the code as the message and `data.code`. The Host refuses an untrusted connection before the agent is asked.
- **Rows and preview**: a `userInput` row, live or cold, carries chips built from its `file` parts (`{fileName, mime, bytes, ref?, previewRef?}`, Node `attachmentMetasOfMessage`); a queued input shows the refs it was sent with. `attachmentRead` serves a ref only if a row of that session carries it, so it keeps working after an agent restart. With a row target and index (the renderer sends both; Node `resolvePromptAttachment`) it reads what that row's stored `file` part holds: its artifact first, of whichever session wrote it (a fork keeps its parent's, as for `previewSource` and the cold load), else its path; the chip's ref is read only while the part is not committed yet. A later change of the local file therefore never changes a chunked preview. Without a target it reads the ref. `previewSource` answers `{kind: "chunked"}` except for a desktop video (see "Video").
- **Command correlation after a restart**: a cold `userInput` row and its turn header carry `sourceCommandId`, read from the stored `anchor.sourceCommandId` (Node writes the same anchor). The kernel keeps a `message id → command id` map: the store loads it, and the session actor adds an entry when it commits a typed user message (Human, not an interrupt, not bash output; the same filter as the store's anchor) under a command. `v4/commands/query` can still answer a pending command from the stored command facts; the row is what settles a held first-submission copy (`commandRowProjected`) and a pending entry from the snapshot alone.

## Conversation quotes in Rust mode

The App sends a conversation selection twice: as the `# userselect:` block in the text, and as `conversationQuotes` on `sendText` and `editUserQuery` (`ConversationComposer`, `SessionPane.handleEdit`). After an edit the App moves the selection out of `newText`, so `conversationQuotes` is then the only carrier. `createSession.firstInput` has no quotes.

- **Owner: the input intent.** `zcode-rs` builds Node's `TurnInputIntentMetadata` at admission (Node `inputIntentMetadata`, `bootstrap/src/zcode-protocol-v4/commands/input-intent.ts`) for every App input: `sendText`, `sendGoalCommand` and `createSession.firstInput`. Its fields: `inputOrigin` (envelope, else payload; `desktop`/`mobile` only), `conversationQuotes` (as sent: absent stays absent, `[]` stays `[]`), `sourceCommandId` (the envelope command), `queueItemId` (`queue_<command>`), `clientId` (`envelope.clientId`, else `cli`), `kind`, `text` (the typed text; a goal's objective), the payload's own `modelSelection` / `mode` / `planEnabled`, `admissionSeq` (a per-session counter from 1, in memory, like Node's `CommandInbox`), `admittedAt` (admission time, ms), `requestedDelivery` (`startNow` when absent), `admittedDelivery`, `attachmentRefs` (when sent). The intent travels with the input through the queue, a steer and the turn, and is the only source of a row's typed text and quotes; nothing parses them back out of message text.
- **Model input** (Node `withConversationQuotes`, `core/src/runtime/helpers/conversation-quotes.ts`): the input's text, a blank line, then `<conversation_quote>\n<JSON>\n</conversation_quote>`. The JSON is the quote array with keys in schema order (`text`, `path`, `senderName`, `senderId`, `messageId`, `sentAt`, `comment`, `agent`) and absent keys left out, so it is byte-identical to Node's `JSON.stringify`. When any quote has a `comment` that is not blank by JS `trim` (Node `quote.comment?.trim()`; `rust_cli_base::js::string::trim`), a blank line and Node's `QUOTE_COMMENT_GUIDANCE` sentence follow the block (the comment is the user's question about that passage; `agent` names the subagent that wrote it). With no typed text the block alone, with the guidance when present, is the text; `[]` adds no block. `runtime/capabilities.conversationQuoteComment` is `true`, so the App offers the selection-comment entry in Rust mode. The block is added after slash expansion, so `@` mentions, the command arguments and the UserPromptSubmit hook see only the typed text (Node composes `expandedInput`, `turn.ts`). Attachments see the typed text. A steer's model text composes the same way (Node `steering.ts`).
- **Stored message** (Node `persistUserPrompt`, `message-persistence.ts`): the text part is the composed text (a slash command: its display input `/name args`, then the block; the expanded text stays in `metadata.modelInput`). The message's `metadata` holds `inputIntent` (the intent), `conversationInputIntent` (Node `buildPersistedConversationInputIntent(text, intent, "drained")`: the same facts with `delivery`, `order`, `steer`, `dispatch: {state: "drained"}` and `attachments: attachmentRefs ?? []`) and `inputClientId`. Either runtime reads the row back from it, and either sends the quotes to the model on a cold resume (Node's history reads `part.text`). An input without an intent (TUI, CLI) writes no `metadata`, as before.
- **Reading an intent** (Node `transcript-hydration.ts` `inputIntentOfMessage`): a `conversationInputIntent` that passes Node's schema shape wins; else a legacy `inputIntent` with string `sourceCommandId` / `queueItemId` / `clientId`, `kind` `sendText` or `sendGoalCommand`, numeric `admissionSeq` / `admittedAt` and valid deliveries; else none.
- **Rows**: a `userInput` row, live or cold, shows `intent.text` when the intent has `conversationQuotes` or `botGroupSource` (`[]` included), else the message text, and carries the intent's `conversationQuotes` (`[]` included). A guided steer row and a queued item do the same from the intent they carry. A message whose text merely ends with a quote block, without an intent, shows its text as is and has no quote chips.
- **Queue edit** (Node `editPendingInputById`): `editQueueItem` replaces the typed text and the intent's `text`; the quotes stay.
- **Edit** (Node `canonical-intent-replay.ts` `inputIntentMetadataFromCanonical`): the new intent takes the edited message's intent (kind, deliveries, model selection, mode, plan, attachments) with the new command's `sourceCommandId` / `queueItemId` / `admissionSeq` / `admittedAt`, `text` = `newText`, `conversationQuotes` = `payload.conversationQuotes ?? the edited message's quotes` (absent keeps, `[]` removes), `provenance` = the stored provenance, else the original `sourceCommandId` / `queueItemId` / `clientId`. Node's canonical replay does not carry `botGroupSource`, so neither does an edit here.
- **Retry**: the stored input is submitted again like an edit with no changes (Node `retryTurn` → `startCanonicalIntent` with `editTarget.intent.text`): its typed text is the stored intent's `text` (a slash or skill input's `/name args`, not its stored expansion, so the session expands it again and the UserPromptSubmit hook, the new intent and the row read the typed text), with the stored quotes and attachments, a new command and admission. A stored input without an intent (TUI) is submitted with its stored text. Like an edit, it does not carry `botGroupSource`.
- **Replayed fields** (edit and retry, Node `buildCanonicalIntent`): the stored `genUiContext` is carried over. `inputOrigin` is the envelope's only: `buildCanonicalIntent` passes no `inputOrigin`, `sharedContextRefs` or `source` to `inputIntentMetadataFromCanonical`, so Node's `envelope.inputOrigin ?? canonical.inputOrigin` never falls back, and an edit from the desktop of a mobile input is a desktop input in both runtimes.
- **Send now** (Node `inputIntentMetadataFromQueueItem`): the queued item's intent unchanged.
- **Empty input**: quotes alone are an input (Node `session-flow.ts`, `fork-edit-retry.ts`); an edit whose `newText` is empty but keeps quotes is accepted.
- **Validation** (`conversationQuotesSchema`, checked before any side effect, else `proto.invalidPayload`): at most 8 quotes; each `text` at most 8000 code points; all `text`s together at most 16000 UTF-16 units; `sentAt`, when present, an RFC 3339 date-time with seconds and a `Z` or `±HH:MM` offset and a real calendar date (zod `datetime({offset: true})`); `comment` at most 2000 and `agent` at most 200 code points. The inbound validator counts every `minLength` / `maxLength` in code points, as zod 4 does.
- **Not covered**: `botGroupSource` composition (Node's bot instructions after the quote block): `zcode-rs` never receives a bot input, and a stored bot message's intent is kept as is; `highspeed`, `sharedContextRefs`, `source` and `fallbackReasonCode`, which no `zcode-rs` input produces (a stored `genUiContext` is replayed, above); the session-fallback `modelSelection` / `mode` / `planEnabled` Node writes when the payload omits them. A steer is stored as `zcode-rs`'s own `queued_command` record with the intent in its data, not as Node's `turnSteerDelivery: "guide"` user message, so under Node a Rust-written steer is still not a user row.

## Usage rollup in Rust mode

App Usage (`v4/usage/stats`, and the session totals behind `v4/conversation/usage`) reads the same `db.sqlite` tables whichever runtime wrote them. Both runtimes own the same facts in the same shape, with no new migrations:

- **raw rows** (`model_usage`, `turn_usage`, `tool_usage`) are kept forever (upstream 3.18.0, owner decision 1 in `specs/upstream-sync-3.18.0.md`); builds up to 3.17 pruned rows older than 30 days, so older history may survive only in the rollup;
- **the rollup** (`fork_usage_bucket`, `fork_usage_turn`, `fork_usage_tool`, ledger `9001_fork_usage_rollup`) holds 15-minute buckets for two years. `fork_usage_meta.watermark_ms` records the last recompute; a recompute replaces buckets from `watermark − 7 days` and keeps a bucket whose raw rows were already pruned;
- **detached and protected usage** (`fork_usage_detached_turn`, `fork_usage_protected_*`, ledger `9002_fork_usage_detached`) keeps the totals of erased sessions.

`zcode-rs` (node-store `fork_usage_rollup.rs`, `fork_usage_query.rs`, `session_tree.rs`) uses Node's DDL strings byte for byte, so the ledger checksums match. It recomputes before an App Usage read and inside the session-tree erase (followed by the detached hand-over). It does not recompute on the usage write path: a recompute there moves the watermark in the middle of a turn, and a `turn_usage` row written later with an older `started_at` (a turn longer than 7 days) then falls outside every later replace window.

**Raw retention (3.18.0).** Neither runtime deletes raw usage rows by age. The 30-day prune `zcode-rs` ran on every usage batch (bounded by the last recompute and preceded by the protected reconcile) is removed together with Node's `pruneUsage` / `pruneUsageIfDue`. The protected reconcile (`sync_protected_raw_rows`) still runs before every recompute. The rollup keeps its own two-year retention, pruned during a recompute.

Residual, shared with Node: a usage row written once at the end (`turn_usage`, `model_usage`) whose `started_at` is already older than the replace window when it is first written (a turn that waited weeks for an approval) is not rolled up: the recompute rebuilds only buckets from `align_down(watermark − 7 days)` on. The raw row stays, so the raw fallback path still counts it.

```text
usage batch (zcode-rs, one BEGIN IMMEDIATE)
  insert model_usage / turn_usage / tool_usage rows (each in its own savepoint)
commit
App Usage read  → recompute (window watermark − 7 d … now), watermark := now → rollup query (raw fallback as in Node)
session erase   → recompute → preserve detached / protected → prune rollup older than 2 years → delete
```

Acceptance:

- Rows written by `zcode-rs` give the same `v4/usage/stats` totals under Node's `queryAppUsageWithRollup` and Rust's `query_with_rollup`, for a window older than 30 days and after an erase.
- A usage write keeps raw rows of any age, including rows a recompute already rolled up (`usage_writes_keep_raw_rows_of_any_age`).
- A raw row written before any recompute is counted by the first read.
- A turn longer than 7 days that ends after a read is still counted by the next read.

## State owners

- **Setting:** the fork settings sidecar `~/.zcode/v2/fork-settings.json`. The key `agentRuntime: "node" | "rust"` goes in `FORK_SETTING_KEYS`. The default `node` is materialised by `forkAppSettingsSchema` and never written back. It must not go into `setting.json`, because upstream writes strip unknown keys.
- **Selection:** the managed Main module `desktop-fork-agent-runtime` (`packages/desktop/src/main/fork-agent-runtime/`).
  - It resolves selected → effective runtime once, before the first Host fork. It does this inside the existing `awaitFirstHostSpawnDecision` latch, reading `mainSettingService.get()` asynchronously.
  - `mainSettingService.get()` returns effective settings, with the `node` default materialised. So the logged `source` is `setting` whenever the env does not override, including on a fresh profile; `default` appears only when the read fails. Precedence is unaffected.
  - It latches the result for the rest of the process.
  - Main is the only one that decides: it deletes any inherited `ZCODE_FORK_AGENT_RUNTIME` / `ZCODE_FORK_RUST_AGENT_PATH`, then writes the decided values into the Host env, the same pattern as the Dynamic Workflow env.
- **Binary location:** Main resolves the binary, first match wins:
  1. `ZCODE_FORK_RUST_AGENT_PATH`, the explicit path. It must exist.
  2. Packaged builds: `<resources>/zcode-rs/zcode-rs[.exe]`.
  3. Dev builds: `packages/desktop/resources/zcode-rs/zcode-rs[.exe]`.

  It must not live under `resources/glm/`: `findZCodeAgentRuntimeBinary` scans that directory and would pick `zcode-rs` up as the native fallback, without storage startup.

- **Command, hello overrides, command gate:** the managed Host module `services-fork-agent-runtime` (`packages/services/src/zcode-agent/fork-agent-runtime/`). All three read the Host env (`ZCODE_FORK_AGENT_RUNTIME`), which Main writes once per Host.
- **Official plugin seed for the Rust agent:** the managed CLI module `cli-fork-agent-runtime` (`apps/zcode-cli/packages/bootstrap/src/fork-agent-runtime/`), called from the `prepareStorageOnly` branch of `runZCodeProtocolAgent` (fork patch). It reads the same Host env, inherited by the storage Worker.
- **Command:**
  - It takes the bundled Node command and returns either that same command or the Rust command: `[app-server, --stdio]`, plus `--surface desktop` added by the existing presentation step. The Rust command reuses the Node command's `storagePreparationEntry`.
  - Upstream `resolveDefaultZCodeAgentCommand` gets a one-line wrap around its bundled branch. `prepareSessionStorage` and the process manager both call that resolver, so storage preparation and agent spawn see the same decision with no further edits.

## Event order

```text
app start (Main)
  awaitFirstHostSpawnDecision ─┬─ desktop-context-prompt rollout (existing)
                               └─ forkAgentRuntimeSelection.prime()
                                    mainSettingService.get().agentRuntime
                                    + ZCODE_FORK_AGENT_RUNTIME (env override)
                                    + resolve zcode-rs binary
                                    → latched {selected, effective, rustAgentPath}   (info log once)
spawnHostProcess (every window)
  env = buildHostProcessEnv(...) − inherited ZCODE_FORK_* + latched effective values
Host (utility process)
  InitLocal → createHostDatabaseStartup
    prepareHostStorage (tasks-index)                       Node Worker
    prepareSessionStorage → resolveDefaultZCodeAgentCommand
                             → storagePreparationEntry = bundled zcode.cjs   Node Worker, migrations
                               → effective=rust: seed official plugins        same Worker, after storagePrepared, before exit
  getClient → resolveDefaultZCodeAgentCommand
               → effective=rust ? zcode-rs app-server --stdio : zcode.cjs   conversation process
```

Both resolver calls read the same immutable Host env, so storage preparation and agent spawn cannot disagree within one Host. Both processes resolve the database path from the same env (`ZCODE_DATA_BASE_DIR`, `ZCODE_STORAGE_DIR`, `ZCODE_SESSION_DB_PATH`, and the `storage` config). Acceptance scenario 4 checks that they agree.

## Source

The Rust agent lives in this repository at `packages/rust-cli`, the same path it has in MBearo/ZCode-rs:

- osben/ZCode#382 imported `packages/rust-cli` from MBearo/ZCode-rs `cfc27e0e` unmodified and added the fork patches on top. It was squash-merged, so the whole fork delta is the diff between MBearo/ZCode-rs `cfc27e0e:packages/rust-cli` and this tree. A later upstream refresh replaces the imported tree and replays that delta.
- `crates/platform/assets/zcode-builtin.json` is the fork's `config/provider/zcode-builtin.json` (the test `the_bundled_builtin_is_the_repository_copy` keeps them equal); sync it whenever the fork's catalog changes.
- The tree keeps upstream bytes. `.gitattributes` marks it `linguist-vendored` (the staged-file size check skips it) and `-whitespace` (its migration SQL feeds checksums shared with the Node agent). `.oxfmtrc.json` ignores it. Rust code is checked with `cargo fmt`, `cargo clippy --workspace --all-targets -- -D warnings` and `cargo test`. It has no `package.json`, so pnpm and the architecture check do not see it.
- CI: `pr-checks.yml` job `Rust CLI (fmt, clippy, tests)` runs `cargo fmt --check`, clippy with `-D warnings`, `cargo nextest run --workspace --retries 2` (upstream's runner and `.config/nextest.toml`) and the doctests, on the debug profile with the toolchain from `rust-toolchain.toml`, when a PR changes `packages/rust-cli/**`; it is skipped otherwise. The retries absorb the known upstream flakes (`rust-cli-fs` `exclusive::tests::only_one_holder_at_a_time`, `rust-cli-platform` `team::platform_tests::an_account_change_during_the_query_discards_the_round`), which are reported as flaky. The job fails if `build-number` changes.
- Local build: from `packages/rust-cli`, `CARGO_PROFILE_RELEASE_BUILD_OVERRIDE_STRIP=false cargo build --release -p rust-cli`, then point `ZCODE_FORK_RUST_AGENT_PATH` at `packages/rust-cli/target/release/zcode-rs`. The strip override keeps proc-macro dylib metadata on macOS. A local release build bumps the tracked `build-number` counter (upstream's version scheme); do not commit that bump.

## Packaging and licensing (phase 3)

- `fork-release.yml` builds `zcode-rs` in both release jobs (macOS arm64, Windows x64): the toolchain from `packages/rust-cli/rust-toolchain.toml`, `cargo build --release --locked -p rust-cli --bin zcode-rs` with `CARGO_PROFILE_RELEASE_BUILD_OVERRIDE_STRIP=false`.
- `scripts/fork-rust-agent/stage-resources.mjs` stages the binary into `packages/desktop/resources/zcode-rs/` (gitignored) with its license material:
  - `LICENSE`: the repository's Apache-2.0 license, which is also `zcode-rs`'s (MBearo/ZCode-rs is Apache-2.0).
  - `NOTICE.md`: the repository notice.
  - `VENDORED-THIRD-PARTY-NOTICES.txt`: `packages/rust-cli/vendor/THIRD-PARTY-NOTICES.txt`, the C and C++ sources vendored under `vendor/`.
  - `CRATE-LICENSES.md`: the licenses of the linked crates, generated by `cargo about` (0.9.3) from `scripts/fork-rust-agent/about.toml` and `about.hbs`. `about.toml` lists the accepted licenses; a crate with an unlisted license fails the release build (`--fail`) until it is reviewed.
- `electron-builder.config.js` ships `resources/zcode-rs` as `<resources>/zcode-rs/` when the staged directory exists, so local packaging without a Rust build still works and ships Node only. Main resolves the packaged binary there (rule 2 of "Binary location").
- The repository-wide `THIRD-PARTY-NOTICES.md` is not changed: it is hash-pinned by `third-party/inventory.json` and covers the JavaScript bundle; the Rust material travels next to the binary.

## Acceptance scenarios

1. Fresh profile, no env: `forkAppSettingsSchema.parse({}).agentRuntime === "node"`, logged with `source: "setting"` (see State owners). The Host env has `ZCODE_FORK_AGENT_RUNTIME=node` and no Rust path. The agent is `zcode.cjs`.
2. `agentRuntime: "rust"` stored and the binary present: the Host env has `effective=rust` and the path. `resolveDefaultZCodeAgentCommand` returns `zcode-rs` with `supportsStorageStartup: true` and `storagePreparationEntry` pointing at the Node bundle. `prepareSessionStorage` runs the Node Worker.
3. `rust` selected, binary missing: effective is `node`, logged once at `warn`, and the agent is `zcode.cjs`.
4. Database path agreement: with Rust effective and `ZCODE_DATA_BASE_DIR` set, the database the Rust agent opens has the fork migration ledger rows `9001`–`9005` written by the Node Worker. No second `db.sqlite` is created.
5. Env override: `ZCODE_FORK_AGENT_RUNTIME=node` with a stored `rust` gives `node`. An invalid value is ignored with a `warn`.
6. `ZCODE_AGENT_SERVER_COMMAND` set: the custom command is used as today, and storage startup stays `unsupported_runtime`.
7. Changing `agentRuntime` while the app runs does not change any running or newly spawned Host until restart.
8. Rust effective: a new task's first message, a follow-up and a tool turn render end to end. The first-submission overlay ("Message saved; delivery not confirmed") clears once the reply streams, and `session_entry` holds the marker with `status: "active"`. History: on 2026-11-07 the hello-override route failed here because the composer always takes the durable route; the contract was then implemented in `zcode-rs`. After a full desktop restart the reopened task shows no overlay. A card that stayed after a restart in the 2026-11-07 run came from pre-contract records: composer drafts left in the draft scope with no reservation, which the reconciliation never visits.
9. Rust effective: creating a task with an ACP agent selected fails with `proto.forkRustAgent.externalAgentUnsupported` instead of running with a different model. With Node effective the same commands are admitted. A task in an execution worktree runs in the worktree under both runtimes.
10. Rust effective, web-remote and desktop, in a fresh session: attaching a text file with a secret word on a line the model has not echoed, and asking for it, gives the word in the reply. The chip shows the file name, and the bubble shows only the typed text. After an agent restart the chip is still there and an attached image still previews. Reopening the task under `ZCODE_FORK_AGENT_RUNTIME=node` shows the same bubble and chips, and a follow-up question quoting the unechoed line exactly is answered from history.

11. Rust effective: after a full agent restart, subscribing to a task (`v4/conversation/subscribe` with `topic: conversation/<session>`, `connectionId`, `clientMode`) gives `userInput` rows and turn headers whose `sourceCommandId` equals the stored `anchor.sourceCommandId` of that input. An image attached under Rust shows a chip with a ref when the task is reopened under Node, and an image attached under Node reaches the Rust model as an image.
12. Rust effective on a fresh home (no `~/.zcode/cli/plugins`): after the first start the plugin store has `bundled-marketplace.json` and the `visualize` cache, and the first model request of a new task lists the `visualize` skill. With Node effective the storage Worker leaves the plugin store untouched.

13. Rust effective: send a message with a conversation selection, then edit it and remove another context. The edited turn's model request still carries the selection (`<conversation_quote>`), as under Node (`conversation-session-v4-attachment-layout`). The row shows the typed text and the quote, also after an agent restart and for a quoted message Node wrote.
