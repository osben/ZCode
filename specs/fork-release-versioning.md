# Fork Release Versioning (fork version scheme and outbound wire-version baseline)

## Background (current source facts)

- This repository is a fork of `zai-org/ZCode` (origin=`osben/ZCode`). Upstream releases via the root `package.json` `version` + release-it with tags `v<version>`; the fork already carries upstream tags (e.g. `v3.14.3`, `v3.15.1`; upstream has no `v3.15.3` tag). The root package version follows the upstream base used for the current build; it is now `3.16.1`, the base of the upstream tooling sync (the former fork base `3.15.3` is superseded).
- Version injection chain: root `package.json` → per-bundler `define __ZCODE_VERSION__` (desktop tsup/vite, server, web) → `ZCODE_VERSION` in `packages/shared/src/version.ts`.
- Version consumers fall into two groups:
  - **Outbound (wire)**: version strings visible to the z.ai / Zai backend — source headers (`User-Agent: ZCode/<v>`, `X-ZCode-App-Version`, see `packages/shared/src/zcode-source-headers.ts`), the `app_version` query param of the OAuth login URL (`configUtils.ts`; the website uses it to decide deep-link behavior), Start Plan billing and the coding-plan client/configs `app_version` query, the builtin provider CDN download `app_version` (`packages/provider-node/src/zcode-builtin-download.ts`), the OTel telemetry `app_version` attribute, and feedback device snapshots / log-archive headers.
  - **Local/identity**: About display, remote asset deploy identity (`remoteAssetLiveIdentity`, handshake), builtin config cache directories, ARMS/RUM tags, the dev auto-update override, etc. — these use the full version.
- Client constraints: `build-windows-browser-import-helper.mjs` validates `^\d+\.\d+\.\d+(-…)?$` (strict semver; a 4th numeric segment is rejected); `autoUpdater.ts` parses the version with `semver.parse`; electron-updater compares full semver versions.

## Product rules

- Fork version format: `<upstream-base>-fork.<N>` (e.g. `3.15.3-fork.1`). `N` starts at 1 and increments within the same base; after syncing a new upstream version the base follows upstream and `N` restarts at 1.
- **Upstream wire-version base invariant**: every version string sent to z.ai / Zai endpoints (headers, `app_version` query, telemetry `app_version`, feedback) carries the upstream base only (the `-fork.N` prerelease suffix is stripped). Local display and remote asset identity keep the full version.
  - Implementation: `packages/shared/src/version.ts` exports `stripZcodeForkVersionSuffix()` (strips strictly `-fork.N`; other prereleases such as the `0.0.0-dev` fallback pass through unchanged — dev builds must stay distinguishable to backend gating) and `ZCODE_UPSTREAM_BASE_VERSION`; headers are normalized centrally in `buildZCodeSourceHeadersFromContext`; query params / telemetry attribute / feedback reference the base directly. The CLI agent builds its own model-provider headers in `apps/zcode-cli/packages/bootstrap/src/model-config.ts` (`resolveAppVersionForHeaders`) and strips there as well; the builtin config cache paths keep the full version on purpose.
  - Motivation: the backend gates behavior by version (e.g. the OAuth website disables auto deep link based on `app_version`); under semver `3.15.3-fork.1 < 3.15.3`, so a suffixed version can be misclassified as an older client.
- Release command: `pnpm release:fork` (`scripts/release-fork.mjs`):
  - Accepts only a root version in `X.Y.Z` or `X.Y.Z-fork.N` form; prerelease bases such as `X.Y.Z-rc.1` are rejected because they cannot produce a version in the supported fork format. Strips any existing `-fork.N` to get the base; scans local git tags `v<base>-fork.*` and takes the max of (highest tag `N`, root version `N`) + 1 so a manually bumped root version can never make the next number go backwards.
  - Invokes release-it with the explicit version and changelog plugins disabled (fork releases must not edit upstream `CHANGELOG.md` — it would conflict on every upstream sync); commit/tag/push behavior comes from the root `.release-it.mjs`.
  - `--print` only prints the next version without running release-it.
- CI release pipeline: `.github/workflows/fork-release.yml`, trigger `workflow_dispatch` only (manual "Run workflow"; auto-release on every push is deliberately not enabled yet):
  - `resolve-version` (ubuntu): fetches tags, runs `node scripts/release-fork.mjs --print`, fails fast if the tag already exists on origin, exports the version as a job output — both platform jobs and the release job reuse it, so parallel builds cannot derive different numbers.
  - `build-macos-arm64` (`runs-on: macos-latest`, `ZCODE_TARGET_OS/ARCH=darwin/arm64`) and `build-windows-x64` (`runs-on: windows-latest`, `ZCODE_TARGET_OS/ARCH=win32/x64`) run in parallel, both unsigned (no `ZCODE_ENABLE_MAC_SIGN`):
    - `pnpm pkg set version=<next>` sets a build-only version — no commit is made; `package.json` in git keeps the upstream version forever, so upstream syncs stay conflict-free.
    - Both build jobs set `ZCODE_ENV=production` + `ZCODE_PREVIEW_IDENTITY=1` at job level, so the tsup/vite defines, the bundled agent, and the electron-builder step resolve the same backend environment. A build without an explicit `ZCODE_ENV` defaults to the **test** backend environment (`scripts/builtin-provider-config.mjs`), baking `X-Release-Channel: test` into every model request; the z.ai backend then rejects the production account token, so every model call fails with 401 `auth_failed` ("Provider authentication failed") while all non-model features keep working (diagnosed 2026-10-11 from `x-release-channel` in `~/.zcode/cli/rollout/model-io-sess_*.jsonl`). The Preview identity is kept deliberately: identity and backend environment are independent axes (`packages/desktop/scripts/desktop-product-identity.mjs`), and "ZCode Preview" upgrades existing fork installs in place instead of overwriting a regular `ZCode.app`.
    - `ZCODE_SKIP_REMOTE_ASSETS=1` (the installer does not bundle the dev mock-cdn remote assets) + `pnpm --filter @zcode/desktop build`, then `pnpm --filter @zcode/desktop exec electron-builder --config electron-builder.config.js --mac|--win --x64 --publish never` (canonical invocation per upstream docs; `--publish never` because the config's generic publish URL is a localhost placeholder).
    - Each job uploads its artifacts (`dist-macos-arm64`: dmg + zip; `dist-windows-x64`: nsis exe) via `actions/upload-artifact` (`if-no-files-found: error`).
  - `release` (ubuntu, needs both builds): downloads all artifacts flattened and runs `gh release create v<version> --target <sha>` — the tag and the release appear only after both platforms have built successfully, so a failed platform cannot publish a half release. It authenticates `gh` with the repository Actions secret `FORK_RELEASE_TOKEN` (fine-grained PAT restricted to this repository with Contents: write and Workflows: write). GitHub's `GITHUB_TOKEN` cannot create a release for a target commit that changes workflow files; fail clearly if the secret is absent. The secret value is never stored in the repository.
  - A concurrency group with `cancel-in-progress: false` serializes release runs so tag numbers cannot race.
- Rejected approaches (recorded to avoid re-litigating): a 4th numeric segment (violates the Windows helper regex and semver parsing); `+fork.N` build metadata (equal precedence — electron-updater cannot distinguish consecutive fork builds).
