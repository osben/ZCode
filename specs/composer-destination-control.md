# Composer destination control

This is the detailed contract for [§4 of composer branch switcher semantics](composer-branch-switcher-semantics.md#4-unified-destination-control-decided-2026-10-15-variant-switch--branch-rows).
Section references below refer to that parent specification; its acceptance scenarios,
validation and scope exclusions still apply.

Replaces the header `GitBranchSwitcher` chip AND the `ChatEmptyWorktreeTaskToggle` checkbox behind a renderer-local feature flag (`localStorage` key `zcode.fork.composerDestinationControl`, **default on** — the new control ships visible; setting `"0"` renders the old pair untouched, so rollback is instant and per-device). New component: `v4/composer/ComposerDestinationControl.tsx`.

- **Trigger chip**: project mode → the task branch (`intent ?? current`, "detached" for detached HEAD); worktree mode → violet `Worktree` (never the auto-generated name). Pipeline `creating` keeps the chip usable (it reflects state, does not block). The popover opens **upward** (`side="top"`) — it hangs under the app header.
- **Popover row 1 — New worktree + switch**: the row is quiet at rest — 2026-10-15 the at-rest location note ("created in <dir> · from settings") and the dirty-tree note ("uncommitted changes stay in this project") were removed by user decision; the location still applies from settings, it is just not displayed. The sub shows pipeline states only: "Creating worktree…", "Ready → <path>", "Failed — send again to retry"; turning the switch OFF while creating = withdraw ("Withdrawing — worktree left on disk"), never disabled.
- **Popover row 2 — Task branch / Base branch** (labels per ask-codex advice: project mode names the branch the checkout switches to; worktree mode names the base the worktree forks from): value = selected ?? current ("detached" for detached HEAD). The row is quiet at rest in both modes — 2026-10-15: the at-rest subs were removed by user decision ("current · applies on send", "switches on send" variants, "the worktree forks from it"); only the failed-list disclosure shows: "Couldn't load branches — base defaults to HEAD" (disclosed before send, ask-codex pitfall). The send-time confirm guard remains the authoritative check. Inline branch list in the same popover: search, current check + dirty count, and the base switcher's footer actions — "Create and switch to new branch…" (existing `GitBranchCreateDialog` + create-and-switch semantics, unchanged) and "View branch graph" (existing `GitGraphDialog`). **Worktree-occupied branches (2026-10-15):** a branch checked out in another worktree cannot be checked out here (git refuses), so every switch surface (`GitBranchSwitcher` and the destination list in project mode) renders it disabled with a "Checked out in <directory>" hint instead of failing on click/at send; in worktree BASE mode the branch stays selectable — a base only needs to exist. Occupancy comes from `git worktree list` via `useGitBranchSwitcher` (`worktreeOccupancy`, refreshed on open; failures degrade to the old behavior).
- **Semantics**: switch ON registers the worktree intent in the existing slot (`beginCreation` with the selected base override — falling back to the workspace's **live** current branch from the git summary; HEAD only when no branch can be named, i.e. detached HEAD; a failed branch list no longer degrades the base to HEAD because the live summary still names the current branch); branch selection writes the existing `draftBranchIntent` store; the composer send path, guard (§2), and pipeline (composer-worktree-setup-steps.md) are unchanged consumers. Toggling the mode re-labels the same value (Task ↔ Base) instead of clearing it. **Main-branch default (2026-10-18, user decision)**: switching the mode ON immediately **selects** the repository's main branch in the Base row — the point the worktree potentially forks from; a selection only, never a checkout mutation. Resolution: the project override `defaultBaseBranch` when present in the loaded local list, else the default branch derived from the merge-status probe's `baseRef` (`origin/HEAD`, e.g. `origin/main` → local `main`) when that branch exists locally, else no selection change (the existing current-branch/HEAD fallback stands). The popover-open load fetches `getBranchMergeStatus` alongside `getLocalBranches` (the service TTL-caches it; a failure degrades to no default and is debug-logged). A manual base pick survives while the mode stays on; every OFF→ON transition re-selects the main branch (a deliberate re-default of the previous stint's pick). The toggle itself issues no git RPC; detached HEAD with a resolvable main branch selects the main branch instead of the HEAD fallback.
- **Workspace isolation** (2026-10-15 fix): the control lives in the shell header and stays mounted across workspace tab switches, so all per-draft state derived from a workspace's git (cached branch list, base selection, list-failure flag, open popover/list views) resets when `workspaceKey` changes. Without this, the previous project's cached branch list survived the switch and its `currentBranchName` leaked into the next project's worktree creation as the base branch (live bug: "Base branch 'feat/Oct-15' was not found" in an unrelated project). The base fallback additionally reads the live git summary instead of the cached list, so a base can never name a branch the current repo does not have. The reused `useGitBranchSwitcher` machinery receives the control's workspace-resolved Git service (never the ambient context service), and its cached branch, occupancy, create, and switch-assist state also reset when that Git target changes, since remote workspaces on different hosts can share the same path.
- **Git repository visibility** (2026-10-15): project selection becomes active first; the composer then renders its Git destination management only after the shell's Git state belongs to that selected workspace identity and reports Git available plus a repository. Initial loading, unknown state, and non-Git projects do not render the controls. A previously confirmed repository stays rendered during a same-workspace refresh so queued worktree intent is retained; a late response for a previously selected workspace cannot satisfy the active workspace key check. Per this presence rule the chip must appear for a git-project workspace without a manual reload: if the workspace's initial Git refresh is dropped (e.g. a services identity swap during the programmatic open-workspace burst) or rejected, the Git hook self-heals — it re-applies or re-issues the refresh on its next evaluation (BUG-GWT-013, fixed 2026-10-18). Refresh failure isolation and same-target stale-state retention follow [Git refresh resilience](git-refresh-resilience.md). A rejected refresh is re-issued at most twice in a row per workspace identity/path pair (the failure changes no effect dependency, so the hook bumps an internal retry tick); after that the error state stands until the next trigger.
- **Branch list freshness (2026-10-17 fix)**: the destination popover reloads `getLocalBranches` on every open, not once per mount. A branch created and switched to through the popover must appear, and be marked current, the next time the popover opens. The previous snapshot stays rendered while the reload runs (stale-while-revalidate: no loading flicker and no empty state replace it). A response from a superseded open or from a previous workspace is dropped by a cancelled flag and never overwrites a newer result. A list-failure flag resets on each open, so a failed open retries on the next one. The reload is keyed to the open transition and the Git target only; it must not depend on the branch-list result itself, or every result would trigger another fetch.
- **Reuse**: `useGitBranchSwitcher` powers branches/create/graph machinery — the control simply never calls its `switchBranch` for list selections (intent instead).
